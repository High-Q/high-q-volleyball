# 安全管理措置 SOP

> 本 SOP は **個人情報保護法 §23 (安全管理措置)** に基づき、High Q バレーボールサークルが講じる組織的・人的・物理的・技術的の 4 領域の措置を文書化する **内部運用 SOP** である。
> 一般ユーザー向けの公開ポリシー本文は LP の `/privacy` ページに記載されており、本 SOP は公開ポリシーには載せない実装詳細・運用手順を集約する。両者は同一 PR で同時に更新する MUST。
> 本 SOP は **オーナー単独運営 (一人体制)** を前提とする。将来複数人体制へ移行する場合は本 SOP を改訂する。
> 漏洩等の事案が発生した場合の対応手順は別 SOP `13-漏洩時対応SOP.md` を参照する。

---

## 1. 組織的安全管理措置

### 1.1 個人情報取扱責任者

- **個人情報取扱責任者**: 翔太郎くん (オーナー兼開発者兼運営者)
- 連絡先: `high.q.volleyball@gmail.com`
- 現状の体制: 一人体制 (役割分掌は存在せず、責任者が全領域を兼務)

### 1.2 ロールベース権限分離

DB / アプリケーション層では以下のロールで権限を分離する。詳細な RLS 設計は [03-アクセス制御・認可設計.md](./03-アクセス制御・認可設計.md) を参照。

| ロール | 主な権限 | 該当者 |
|---|---|---|
| `admin` | 全会員データの閲覧・編集、本人確認書類の審査・削除、イベント CRUD | オーナー (翔太郎くん) のみ |
| `member` | 自分自身のプロフィール・予約・本人確認書類のみ閲覧・編集 | 認証済み会員 |
| 非会員 (anonymous) | LP 公開情報のみ閲覧 | 未認証ユーザー |

将来的に運営補佐を加える場合は新ロールを追加し、本人確認書類審査権限の付与可否を別途検討する。

### 1.3 変更履歴の管理

- 本 SOP および関連 SOP の改訂は Git コミット履歴を一次ソースとする
- 各 SOP 末尾に「改訂履歴」節を持ち、主要な改訂内容を時系列で記録する
- セキュリティに関わる仕様変更 (RLS 追加・暗号化方針変更等) は ADR (`docs/09-決定記録/`) として残す

### 1.4 規程の周知

- 一人体制のため、規程の周知対象は責任者本人のみ
- AI ペアプログラマー (Claude Code) を作業に組み込む場合、本 SOP 配下の方針が常時参照されることを `CLAUDE.md` および `openspec/project.md` で担保する

## 2. 人的安全管理措置

オーナー単独運営の前提で、責任者が自らに対して遵守を誓約する事項を以下に定める。

### 2.1 業務外目的での個人情報閲覧禁止

- 会員の個人情報 (氏名・連絡先・本人確認書類画像 等) を業務外の目的で閲覧してはならない
- 業務とは「サービス提供 / 不正調査 / 役所提出証憑準備 / 本 SOP §4 の利用目的に列挙された活動」を指す

### 2.2 退職・解散時のアクセス無効化手順

オーナーが本サービスの運営を終了する場合 (サークル解散含む) は以下の順で実施する:

1. 全会員に終了告知メールを送付し、データ削除の予告と問い合わせ窓口を案内
2. 退会希望者の対応を完了
3. Supabase プロジェクトの DB / Storage を完全削除
4. 役所提出済証憑コピーの物理廃棄 (シュレッダー処分)
5. 関連 SaaS (Supabase / Render / AWS / Vercel / GitHub) のアクセス権限・サービスを停止

### 2.3 第三者への個人情報共有時の取扱

- 法令・役所提出以外の目的で個人情報を第三者へ共有してはならない
- 友人・家族・SNS 等への会員情報の口頭・テキスト共有を禁止する
- 役所窓口への提出は対面のみとし、メール送信・USB 郵送等のネットワーク経由提出を禁止する

### 2.4 AI ペアプログラマー利用時の機密情報マスキング

Claude Code 等の AI ツールを開発作業に用いる場合、以下を遵守する:

- 個人情報の実データ (実在会員の氏名・電話・メール・本人確認書類画像) を AI に貼り付けない
- 環境変数・API キー・Supabase service_role キーを AI に共有しない (`.env` の読込・編集・コミットを禁止する `CLAUDE.md` の方針)
- 不具合調査でデータ参照が必要な場合は、Supabase Dashboard 上で SQL を実行し、結果を AI に渡さず本人が判断する
- スクリーンショット共有時は会員特定情報をマスクする

### 2.5 端末・アカウントの認証強化

- 開発・運営に用いる主要アカウント (GitHub / Supabase / Render / Google) は **二段階認証 (2FA)** を有効化する
- パスワードは使い回しを禁止し、パスワードマネージャーで管理する

## 3. 物理的安全管理措置

### 3.1 作業 PC の保護

- ログインパスワード / 生体認証を必ず設定する
- 一定時間操作なしで自動スクリーンロックされる設定にする (5 分以内推奨)
- ディスク全体の暗号化 (FileVault / BitLocker 相当) を有効化する
- OS / セキュリティアップデートは原則自動適用する

### 3.2 端末の盗難・紛失時の対応

- 紛失検知後ただちに以下を実行する:
  1. 関連 SaaS のセッション全 revoke (Google / GitHub / Supabase / Render の管理画面から)
  2. 主要アカウントのパスワードを変更
  3. 必要に応じてリモートワイプを発動 (macOS の「探す」/ Windows の Find My Device)
- 個人情報を含むデータが端末上に同期されている場合は §13-漏洩時対応SOP.md のフローを起動する

### 3.3 印刷物の取扱

- 個人情報を含む書類の物理印刷は **原則禁止**
- 役所提出のために物理印刷が必要な場合は、印刷直後に提出窓口へ持参し、控えのみを 1 年間自宅施錠保管する
- 不要となった控えはシュレッダー処分する
- 喫茶店・コワーキング等の共用環境での印刷は禁止する

### 3.4 作業環境

- 自宅または信頼できる環境でのみ作業する
- 公共 Wi-Fi での個人情報閲覧を伴う作業は禁止する (やむを得ない場合は VPN 経由)
- 画面の覗き見を防ぐため、移動中・公共空間ではプライバシースクリーンの使用を推奨する

## 4. 技術的安全管理措置

技術的措置の実装詳細は領域ごとの専用 SOP に集約されている。本節は概要と参照リンクのみを記載する。

### 4.1 アクセス制御 (RLS)

Supabase Row Level Security ですべてのテーブルに行レベルのポリシーを設定する。本人と admin のみが該当行にアクセスできる。

→ 詳細: [03-アクセス制御・認可設計.md](./03-アクセス制御・認可設計.md)

### 4.2 保管情報の暗号化

Supabase Storage は at-rest 暗号化を提供する。本人確認書類バケット (`identity-documents`) は private 設定 + 追加 RLS でアクセス制限。

### 4.3 通信経路の暗号化

すべての通信は TLS 1.2 以上で暗号化される (Render / Supabase / AWS のホスティング標準)。HTTP での通信は許可しない。

### 4.4 認証

- 会員: Supabase Auth のメールマジックリンク認証
- admin: 同方式 + アプリ層での admin ロール判定
- API キー: クライアントは anon key のみ使用。`service_role` キーはサーバ含め未使用

### 4.5 マイナンバー保管禁止

- 個人番号 12 桁のテキスト保管を禁止する (`CLAUDE.md` セキュリティルール)
- マスク済み画像のみ受付。通知カードは一切受け付けない

→ 詳細: [08-本人確認書類取扱SOP.md](./08-本人確認書類取扱SOP.md)

### 4.6 監査ログ

Supabase のクエリログ・アクセスログを定期確認する。

→ 詳細: [05-監査・モニタリング.md](./05-監査・モニタリング.md) / [07-ロギング方針.md](./07-ロギング方針.md)

### 4.7 個人情報のロギング除外

ログには個人情報の値を含めない (氏名・メール・電話・本人確認書類パス等)。エラーコード・操作種別のみ記録する。

→ 詳細: [07-ロギング方針.md](./07-ロギング方針.md)

# 管理者アカウント ブートストラップ手順

## 目的

High Q の admin アプリ (`apps/admin`) はオーナー（翔太郎くん）のみアクセスできるが、初回セットアップ時には admin role を持つメンバーが DB に存在しない。本書は最初の admin アカウントを発行するワンタイム手順を定義する。

関連: #84（管理者ログイン・認証）/ #147（DB スキーマ・本ドキュメント新設）

---

## 前提

- Supabase プロジェクトは作成済み（`high-q` ap-northeast-1）
- Migration `20260426000000_init_high_q.sql` および `20260428143738_db_schema_foundation.sql` が適用済み
- `members` テーブルが存在し、`role` 列が `'member'` / `'admin'` の enum 制約を持つ

---

## 手順

### Step 1. Supabase Auth でユーザーを発行

オーナー（翔太郎くん）のメールアドレスでサインアップする。方法は 2 つ:

**A. admin アプリの本番 / プレビュー環境からサインアップ**

1. [https://admin.high-q.club](https://admin.high-q.club)（あるいは Render プレビュー URL）にアクセス
2. メールアドレスを入力 → 「マジックリンクを送る」
3. 受信したメールのリンクをクリック → サインイン完了
4. この時点で `auth.users` に行が作成され、トリガー `on_auth_user_created` により `public.members` に同 ID で行が作成される（`role = 'member'` がデフォルト）

**B. Supabase Dashboard から直接ユーザー発行**

1. Supabase Dashboard → Authentication → Users → "Add user" → "Send invitation"
2. オーナーのメールアドレスを入力
3. 受信したメールから初回パスワード設定 / マジックリンクで完了

### Step 2. members 行の placeholder 値を正式値で UPDATE

`on_auth_user_created` トリガーは `display_name = ''` / `birthday = current_date` の placeholder で行を作成する（design.md D4）。これらを正式値で更新する。

Supabase Dashboard → SQL Editor で以下を実行:

```sql
update public.members
set
  display_name = '<オーナーの表示名>',  -- 例: '翔太郎'
  birthday     = '<生年月日>',           -- 例: '1990-01-01'
  phone        = '<電話番号 任意>',      -- 例: '090-1234-5678'
  experience_level = 'experienced'      -- オーナーは経験者
where email = '<オーナーのメールアドレス>';
```

### Step 3. role を `'admin'` に昇格

```sql
update public.members
set role = 'admin'
where email = '<オーナーのメールアドレス>';
```

### Step 4. 確認

```sql
select id, email, display_name, birthday, role
from public.members
where role = 'admin';
```

→ 1 行返り、`role = 'admin'` であることを確認。

---

## セキュリティ上の注意

- **本手順を踏めるのは Supabase プロジェクトの所有者のみ**（service_role 相当）。CLAUDE.md ルール「`service_role` キーをクライアントサイドで使わない」と整合。
- 第三者が admin role を取得しないよう、Supabase プロジェクトのメンバー権限管理は慎重に。
- 自己昇格は RLS で禁止されている。一般 member が `update members set role = 'admin' where id = auth.uid()` を試みても拒否される（[openspec/specs/rls-policies/spec.md](../../openspec/specs/rls-policies/spec.md) の `members_update_self` policy 参照）。

## トラブルシュート

### Q. Step 1 の後に members 行が見当たらない

トリガー `on_auth_user_created` が動作していない可能性。Migration の `handle_new_auth_user` 関数 + トリガー定義を再確認。Phase 1 暫定でトリガーが SQL Editor から直接 RUN されていない場合、`select * from auth.users` で auth.users にだけ行があるかも。手動で:

```sql
insert into public.members (id, email, display_name, birthday, role)
select id, email, '翔太郎', '1990-01-01', 'admin'
from auth.users
where email = '<オーナーのメールアドレス>';
```

### Q. admin アプリにログインしても画面が見れない

- ブラウザのコンソールで auth エラーがないか確認
- `members.role = 'admin'` であることを再確認
- アプリ側の認証ガード middleware（#84 で実装）が正しく `is_admin()` をチェックしているか

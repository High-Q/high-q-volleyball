# 管理者アカウント ブートストラップ手順

## 目的

High Q の admin アプリ (`apps/admin`) はオーナー（翔太郎くん）のみアクセスできるが、初回セットアップ時には admin role を持つメンバーが DB に存在しない。本書は最初の admin アカウントを発行するワンタイム手順を定義する。

関連: #84（管理者ログイン・認証）/ #147（DB スキーマ・本ドキュメント新設）

---

## 前提

- Supabase プロジェクトは作成済み（`high-q` ap-northeast-1）
- Migration `20260426000000_init_high_q.sql` および `20260428143738_db_schema_foundation.sql` が適用済み
- `members` テーブルが存在し、`role` 列が `'member'` / `'admin'` の enum 制約を持つ
- 下記「Supabase Dashboard 事前設定」が完了している（#84 で必須化）

---

## Supabase Dashboard 事前設定（#84 で確立）

admin アプリの認証フロー（マジックリンク + TOTP MFA + AAL2 + idle timeout）を機能させるため、以下を Dashboard で設定する。Blueprint やコードでは管理しない（運用作業）。

| 設定箇所 | 値 | 目的 |
|---|---|---|
| Authentication → URL Configuration → **Redirect URLs** | `http://localhost:5173/**`（dev）+ Render プレビュー URL の `/**` + 本番 admin URL の `/**` | マジックリンクの戻り先 |
| Authentication → Email Templates → Magic Link → **OTP Expiry** | `900`（15 分） | リンク傍受時の悪用ウィンドウ短縮 |
| Project Settings → API → JWT settings → **JWT expiry** | `1800`（30 分） | デバイス紛失時の侵害ウィンドウ短縮 |
| Authentication → Providers → **MFA → TOTP を ON** | enabled | 二要素認証必須化（メールアカウント単独陥落耐性） |

これらの値はコードに焼き込めない（環境変数や migration で表現できない Supabase 側設定）ため、**Dashboard と本ドキュメントが真実の源**となる。

## 手順

### Step 1. Supabase Auth でユーザーを発行

オーナー（翔太郎くん）のメールアドレスでサインアップする。方法は 2 つ:

**A. admin アプリの本番 / プレビュー環境からサインアップ**

1. [https://admin.high-q.club](https://admin.high-q.club)（あるいは Render プレビュー URL）にアクセス
2. メールアドレスを入力 → 「マジックリンクを送る」
3. 受信したメールのリンクをクリック → サインイン完了
4. この時点で `auth.users` に行が作成され、トリガー `on_auth_user_created` により `public.members` に同 ID で行が作成される（`role = 'member'` がデフォルト）

**B. Supabase Dashboard から直接ユーザー発行**

1. Supabase Dashboard → Authentication → Users → "Add user" → "Send invitation"
2. オーナーのメールアドレスを入力
3. 受信したメールから初回パスワード設定 / マジックリンクで完了

### Step 2. members 行の placeholder 値を正式値で UPDATE

`on_auth_user_created` トリガーは `display_name = ''` / `birthday = current_date` の placeholder で行を作成する（design.md D4）。これらを正式値で更新する。

Supabase Dashboard → SQL Editor で以下を実行:

```sql
update public.members
set
  display_name = '<オーナーの表示名>',  -- 例: '翔太郎'
  birthday     = '<生年月日>',           -- 例: '1990-01-01'
  phone        = '<電話番号 任意>',      -- 例: '090-1234-5678'
  experience_level = 'experienced'      -- オーナーは経験者
where email = '<オーナーのメールアドレス>';
```

### Step 3. role を `'admin'` に昇格

```sql
update public.members
set role = 'admin'
where email = '<オーナーのメールアドレス>';
```

### Step 4. 確認

```sql
select id, email, display_name, birthday, role
from public.members
where role = 'admin';
```

→ 1 行返り、`role = 'admin'` であることを確認。

### Step 5. admin 画面で初回ログイン → MFA Enrollment（#84 で確立）

1. admin 画面（`http://localhost:5173` または本番 URL）にアクセスし、`/login` で Step 1 のメールを入力 → マジックリンク送信
2. メール内のリンクをクリック → `/auth/callback` を経由して **`/mfa/setup`** に自動リダイレクト
3. 画面の QR コードを認証アプリ（推奨: [Authy](https://authy.com/) / [Google Authenticator](https://support.google.com/accounts/answer/1066447) / [1Password](https://1password.com/)）でスキャン
4. アプリに表示される 6 桁コードを入力 → **「確認」** で AAL2 に到達 → `/`（home）に到達
5. 以降のログインは `/login` で メール送信 → `/auth/callback` → **`/mfa`** で 6 桁入力 → `/`

これで TOTP factor が `auth.mfa_factors` に verified 状態で登録される。次回以降の再ログインは setup ではなく challenge ページに飛ぶ。

---

## セキュリティ上の注意

- **本手順を踏めるのは Supabase プロジェクトの所有者のみ**（service_role 相当）。CLAUDE.md ルール「`service_role` キーをクライアントサイドで使わない」と整合。
- 第三者が admin role を取得しないよう、Supabase プロジェクトのメンバー権限管理は慎重に。
- 自己昇格は RLS で禁止されている。一般 member が `update members set role = 'admin' where id = auth.uid()` を試みても拒否される（[openspec/specs/rls-policies/spec.md](../../openspec/specs/rls-policies/spec.md) の `members_update_self` policy 参照）。

## トラブルシュート

### Q. Step 1 の後に members 行が見当たらない

トリガー `on_auth_user_created` が動作していない可能性。Migration の `handle_new_auth_user` 関数 + トリガー定義を再確認。Phase 1 暫定でトリガーが SQL Editor から直接 RUN されていない場合、`select * from auth.users` で auth.users にだけ行があるかも。手動で:

```sql
insert into public.members (id, email, display_name, birthday, role)
select id, email, '翔太郎', '1990-01-01', 'admin'
from auth.users
where email = '<オーナーのメールアドレス>';
```

### Q. admin アプリにログインしても画面が見れない

- ブラウザのコンソールで auth エラーがないか確認
- `members.role = 'admin'` であることを再確認
- アプリ側の認証ガード middleware（#84 で実装）が正しく `is_admin()` をチェックしているか
- AAL2 に到達していない場合（MFA 未完了）は `/mfa` または `/mfa/setup` にリダイレクトされる仕様。これは正常動作

### Q. TOTP factor を登録した端末を紛失した（#84 で確立）

オーナーがログインできなくなった場合の運用:

1. Supabase Dashboard → Authentication → Users → 該当ユーザーを選択
2. **Multi-Factor Authentication** セクションで該当 factor を **削除**
3. 該当ユーザーに「次回ログイン時に再 setup される」と通知（自分自身の場合はそのまま再ログイン）
4. admin 画面で再度メール送信 → リンククリック → AAL1 + factor 未登録となるので **`/mfa/setup`** へ自動誘導 → 新しい認証アプリで QR スキャン

リカバリーコード生成は MVP1 では未実装。複数台で同 factor を登録する運用（推奨：認証アプリのバックアップ機能 = Authy のクラウド同期等）でリスク低減する。

### Q. メール送信時に「このメールアドレスは管理画面へのアクセスを許可されていません」

`auth.users` 未登録 + `shouldCreateUser:false` で発生する `otp_disabled` エラー。Step 1 を未実施の状態で `/login` から送信した場合に出る。Step 1 を完了させてから再試行する。

### Q. JWT 30 分 / idle 15 分が体感的に短い

セキュリティ要件のため固定値（design.md D12）。長時間の連続作業中は SDK の autoRefreshToken で透過的に更新されるが、無操作 15 分で auto signOut される。短すぎる場合は `apps/admin/src/features/auth/composables/useIdleTimeout.ts` の `IDLE_LIMIT_MS` を変更（要 PR）。

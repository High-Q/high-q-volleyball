# ロギング方針

## 基本原則

1. **個人情報・認証情報をログに含めない**（絶対）
2. **本番環境では `console.log` を出力しない**（デバッグログはビルド時に除去）
3. **エラーは握りつぶさずログに記録する**
4. **構造化ロギング**を意識し、機械可読な形式を使う

---

## ログレベルの使い分け

| レベル | 用途 | 例 |
|--------|------|-----|
| `console.error` | ユーザー操作に影響するエラー | API失敗、認証エラー、バリデーション違反 |
| `console.warn` | 警告（動作は継続するが問題の可能性） | deprecatedなAPI使用、フォールバック発動 |
| `console.info` | 重要な状態変化 | ログイン成功、イベント予約完了 |
| `console.debug` | 開発時のみ（本番では無効化） | データフロー追跡、描画タイミング確認 |

---

## フロントエンドのログ方針

### 開発・本番の切り替え

```typescript
// src/utils/logger.ts
const isDev = import.meta.env.DEV;

export const logger = {
  error: (msg: string, context?: unknown) => console.error(`[ERROR] ${msg}`, context),
  warn:  (msg: string, context?: unknown) => { if (isDev) console.warn(`[WARN] ${msg}`, context); },
  info:  (msg: string, context?: unknown) => { if (isDev) console.info(`[INFO] ${msg}`, context); },
  debug: (msg: string, context?: unknown) => { if (isDev) console.debug(`[DEBUG] ${msg}`, context); },
};
```

### 必ずログに残す事象

- API リクエスト失敗（ステータスコード・エンドポイント、リクエストボディは含めない）
- 認証失敗（ユーザーIDのみ。パスワードは絶対に含めない）
- 想定外エラー（catch で握りつぶすことを禁止）
- 管理者による重要操作（イベント削除・ユーザー停止等）

```typescript
// ✅ Good
try {
  await supabase.from('events').delete().eq('id', eventId);
  logger.info('イベント削除', { eventId });
} catch (e) {
  logger.error('イベント削除失敗', { eventId, error: String(e) });
  throw new AppError('DELETE_FAILED', 'イベントの削除に失敗しました');
}

// ❌ Bad
try {
  await supabase.from('events').delete().eq('id', eventId);
} catch { /* 握りつぶし */ }
```

### ログに含めてはいけない情報

- パスワード・トークン・APIキー
- 氏名・電話番号・メールアドレス（フルテキスト）
- 本人確認書類の内容
- Supabase の service_role キー

## バックエンドのログ方針

### メール送信ログ（Edge Function 経由）

Supabase Edge Functions からの SMTP 送信（`supabase/functions/_shared/mailer.ts` 経由の Auth メール / 予約完了通知メール等）は、成功 / 失敗の両方を `console.log` / `console.error` に出力する。

ログに **含めて良い** 識別子:

- 送信種別（`signup` / `reservation-confirmed` / `reservation-cancelled` 等）
- 会員 ID（auth.users.id / members.id の UUID）
- 予約 ID
- SMTP / nodemailer から返ったエラーメッセージ（メッセージ文字列は通常メールアドレスを含まないが、内容に PII が混ざる場合は呼び出し側でマスクしてからログに乗せる）

ログに **含めない**:

- 会員のメールアドレスのフルテキスト
- 認証コードやワンタイムトークンの値
- メール本文のフルダンプ（件名のみは識別子として残してよい）

抑制モード（`MAIL_SUPPRESS_SEND` / `MAIL_ALLOWED_RECIPIENTS`）が dev / preview で発火したときは `[mailer] suppressed: to=... subject=...` を `console.log` で残し、抑制された送信であることを後追いできるようにする。

### 既存 AWS 環境（LP）

- API Gateway / Lambda のログは CloudWatch に自動収集
- エラーは CloudWatch Logs Insights で `filter @message like "ERROR"` でフィルタ
- アラーム設定: エラー率 > 1% で通知（設定方法は `docs/03-アーキテクチャ/03-インフラ・CICD構成.md` 参照）

### 新規 Supabase 環境

- Supabase Dashboard → Logs → API Logs でリクエストログを確認
- PostgreSQL の `pg_audit` 拡張で DDL 操作（テーブル変更・削除）を記録
- Edge Function のログは Supabase Dashboard → Edge Functions → Logs

## 監視・モニタリング連携（Sentry）

### 原則: 「通知 = 即アクション」

Sentry の通知が来た時点で、翔太郎くんは即座に対処が必要な事象が起きていると確信できる状態を維持する。個別事象の破棄一辺倒では「ノイズパターンの急増」「4xx 異常値」のような重大シグナルを見落とすため、**「個別 issue の通知可否」軸と「集約異常値の検知」軸を独立して設計する**。

### Sentry プロジェクト構成

- プロジェクト: `high-q-volleyball` 1 件に集約
- 識別タグ: `environment`（`dev` / `prd`）と `project_name`（`lp` / `admin` / `reservation` / `edge`）
- DSN: フロント 3 アプリは Render 環境変数 `VITE_SENTRY_DSN`（sync:false、PR Preview は dev 値を `previewValue` で固定）。Edge Function は Supabase Edge Function Secrets の `SENTRY_DSN`
- Inbound Filter: `localhost` / `127.0.0.1` / Web Crawler のみ入口破棄。browser extension は SDK 側で `level:info` 降格扱い

### 送出ポリシー (2 軸)

**軸 1: 個別 issue としての通知可否**

- `Result<T, AppError>` の `Err` 経路は Sentry に送出しない（UI フィードバックで完結する正常系）
- `captureException` を呼ぶのはフレームワークが補足する未捕捉例外 / try-catch で意図的に握った技術エラー / Edge Function の HTTP ハンドラレベル例外のみ

**軸 2: 集約異常値の検知**

| エラー種別 | level | fingerprint | sampleRate |
|---|---|---|---|
| 401 | `warning` | `['auth-denied', '401', '<endpoint>']` | 0.2 |
| 403 | `warning` | `['auth-denied', '403', '<endpoint>']` | 0.2 |
| 404 | `info` | `['not-found', '<url-path>']` | 0.05 |
| 400 / 422 | `info` | `['validation', '<endpoint>']` | 0.05 |
| その他 4xx | `warning` | `['client-error', '<status>', '<endpoint>']` | 0.2 |
| 5xx | `error` | デフォルト | 1.0 |
| ネットワーク失敗 / AbortError | `error` | `['network-error']` | 1.0 |
| ResizeObserver loop / Script error. / extension | `info` | `['known-noise', '<pattern>']` | 0.05 |
| 未捕捉例外（status 抽出不能） | `error` / `fatal` | デフォルト | 1.0 |

`<endpoint>` / `<url-path>` は path template 化（例: `/api/events/:id` のような placeholder 化）し、個別 ID で fingerprint group が爆発しないようにする。

SDK の `ignoreErrors` で完全破棄するのは `Non-Error promise rejection captured` のみ。

### fingerprint カテゴリ規約

配列の第 1 要素は以下のいずれかとする。第 2 要素以降に集約軸を並べる:

- `auth-denied` / `not-found` / `validation` / `client-error` / `network-error` / `known-noise`

5xx と未捕捉例外（status 抽出不能）は fingerprint を指定せず、Sentry のデフォルト算出に委ねる。

### アラート 2 系統運用

**A. 即時通知系**

| 条件 | アクション |
|---|---|
| `environment:prd AND level:[error, fatal] AND is:unresolved AND age:-5m` の新規 issue | `high.q.volleyball@gmail.com` に通知（件名 `[Sentry][prd][<project_name>] <title>`）|
| `resolved` にした issue が再発（リグレッション） | 同送信先に通知 |

**B. 異常値通知系**（fingerprint group ごとの event count threshold）

| fingerprint group | 初期閾値 | 検知意図 |
|---|---|---|
| `auth-denied:401:*` | 5min で 30 件超 | ブルートフォース疑い |
| `auth-denied:403:*` | 1h で 50 件超 | 認可リグレッション |
| `not-found:*` | 1h で 100 件超 | URL 構造破壊 / リンク切れデプロイ事故 |
| `validation:*` | 1h で 50 件超 | API 契約破綻 / schema ズレ |
| `known-noise:*` | 1h で 1000 件超 | ノイズ急増（フィルタ見直し合図）|
| `network-error` | 5min で 20 件超 | 外部依存障害疑い |

すべて `environment:prd` 限定。dev 環境のアラートルールは作成しない（ダッシュボード目視のみ）。

初期閾値は本番ローンチ後 2 週間の観測結果で見直す。

### サンプリング率

- `sampleRate`（error イベント）: 両環境 1.0（個別サンプリングは `beforeSend` の level 別降格で実施）
- `tracesSampleRate`: dev `1.0` / prd `0.1`
- 月次使用量アラート: 80%（4000 events / month）で発火

### PII 取扱

`beforeSend` で以下を破壊的に除去する:

- `request.cookies` / `request.headers.authorization` / `request.headers.cookie`
- `extra` / `contexts` / `request.data` のキー名 denylist（`email` / `name` / `phone` / `tel` / `mynumber` / `document` / `password` / `token` / `secret` / `authorization` / `cookie` / `address` / `zip`）に該当する値を `[REDACTED]` に置換
- スタックトレース URL のクエリ文字列
- `user.email` / `user.username`（`user.id` のみ保持）

### 保守ルール

新規 PII キー名や新規ノイズパターン、新規 fingerprint カテゴリが必要になった場合の更新手順:

1. Sentry ダッシュボードで受信イベントを目視し、漏れたキー名 / 急増する未分類パターンを特定
2. 真実の源は `packages/shared/src/observability/constants.ts`（フロント 3 アプリ）。`PII_KEY_PATTERNS` / `KNOWN_NOISE_PATTERNS` / `LEVEL_SAMPLE_RATES` を更新
3. Edge Function 側の `supabase/functions/_shared/sentry.ts` は workspace import 不可のため**手動同期**。差分は `supabase/functions/_shared/sentry.test.ts` 相当の Deno test で規約整合性を担保
4. ロギング方針（本ドキュメント）の表を更新
5. 異常値通知 (B 系) の閾値見直しは Sentry ダッシュボードの Stats から判断（過去 2 週間の baseline と比較）

### コードレビュー観点

- `Result.Err` を返す経路で `captureException` を呼んでいないこと（ビジネス異常系を Sentry に流さない）
- 新規 try/catch で `captureException` を呼ぶ際、`status` / `endpoint` を `CaptureContext` 経由で渡しているか（fingerprint 集約が機能する前提）

### Supabase 側

- **Supabase Alert**: DB エラー率・レスポンスタイム超過は Supabase Dashboard 側で別途設定（Sentry の責務外）
- 詳細は `docs/06-品質・セキュリティ/05-監査・モニタリング.md` 参照

## テストにおけるログ

テスト実行中に `console.error` / `console.warn` が出力された場合はテスト失敗とみなす。
Vitest の設定でモック化し、意図しないエラーを検出する。

```typescript
// vitest.setup.ts
vi.spyOn(console, 'error').mockImplementation((msg) => {
  throw new Error(`Unexpected console.error: ${msg}`);
});
```

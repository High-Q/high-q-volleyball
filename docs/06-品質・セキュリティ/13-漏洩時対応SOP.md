# 漏洩時対応 SOP

> 本 SOP は **個人情報保護法 §26 (漏洩等の報告)** および同法施行規則に基づき、個人データの漏洩・滅失・毀損 (以下「漏洩等」) が発生した場合の対応手順を定義する。
> 本 SOP は **有事に開く緊急ランブック** であり、検知時刻からタイマーが回る前提で記述している。判断に迷う場合は安全側に倒し、§3.4 の事前相談窓口を活用する。
> 平時の安全管理体制は [12-安全管理措置.md](./12-安全管理措置.md) を参照する。
> 本 SOP に記載する報告対象判定・タイムラインは個人情報保護委員会の現行規則・ガイドラインに基づく。法令改正時は本 SOP を改訂する。

---

## 0. 5 ステップ概要

漏洩等の検知から再発防止までを以下の 5 ステップで実施する。

| ステップ | 概要 | 想定所要 |
|---|---|---|
| 1. 検知 | 漏洩等の事実を認識し、検知時刻を記録する | 即時 |
| 2. 暫定対応 | 拡大防止 (アクセスキー rotate / 公開設定見直し / 影響範囲特定 / 証跡保全) | 検知から 24 時間以内 |
| 3. 個人情報保護委員会への報告 | 報告対象判定 + 速報 + 確報 | 速報: 概ね 3〜5 日以内 / 確報: 30 日以内 (要配慮個人情報等を含む場合は 60 日以内) |
| 4. 本人通知 | 漏洩した本人への通知 | 速やかに (報告と並行可) |
| 5. 再発防止策 | 原因分析と恒久対策の実装 | 確報期限までに対策案、その後実装 |

---

## 1. ステップ 1: 検知

### 1.1 検知契機の代表例

- Supabase Dashboard のアクセスログ・クエリログで異常な大量取得・想定外の IP からのアクセスを観測
- 第三者からの通報 (会員からの「自分の情報が他人に見えていた」等の指摘、外部リサーチャーからの脆弱性報告)
- アクセス監査 ([05-監査・モニタリング.md](./05-監査・モニタリング.md)) の定期確認時に異常を発見
- 開発・運用作業中に意図せず公開設定 (Storage バケット public 化等) になっていることを発見
- 端末の盗難・紛失
- フィッシング・マルウェア感染の疑い
- 本人確認書類画像の Storage に個人番号未マスクのものが長期保管されていたことが発覚 ([08-本人確認書類取扱SOP.md](./08-本人確認書類取扱SOP.md) §6 連携)

### 1.2 検知時刻の記録

検知した瞬間に以下を最優先で記録する (タイムライン管理の起点となる):

- 検知日時 (タイムゾーン明記、JST が原則)
- 検知契機 (上記のどれに該当するか)
- 検知者 (本 SOP では原則オーナー本人)
- 検知時に得ていた一次情報 (画面スクリーンショット / ログ抜粋 / 通報文面 等)

記録先: 専用 Issue を private リポジトリに作成するか、ローカルの暗号化フォルダにテキスト保存する。GitHub Public リポジトリの Issue には記載しない MUST。

---

## 2. ステップ 2: 暫定対応

検知から 24 時間以内に拡大防止を完了することを目標とする。

### 2.1 アクセスキー・セッションの即時 rotate

- 漏洩経路にアクセスキーが関与した可能性がある場合 (.env 流出疑い・GitHub Token 漏洩・Supabase service_role 漏洩 等):
  - Supabase: API キー再生成、必要に応じて DB パスワード変更
  - GitHub: Personal Access Token / Deploy Key の revoke + 再発行
  - Render: API Token revoke + 環境変数の再設定
  - Google アカウント: パスワード変更 + 全セッション revoke + 2FA バックアップコード再発行
- セッション漏洩の疑いがある場合: Supabase Auth の対象 user のセッション全 revoke

### 2.2 公開設定の見直し

- Storage バケットが意図せず public 化していないか確認 (`identity-documents` は private 必須)
- Supabase テーブルの RLS が無効化されていないか確認
- Render / GitHub Pages 等の公開設定の確認

### 2.3 影響範囲の特定

以下を順に確認する:

1. 漏洩したデータの種別 (要配慮個人情報・本人確認書類画像・連絡先・予約履歴 等)
2. 漏洩した件数 (人数・レコード数)
3. 漏洩した期間 (いつから露出していたか)
4. 漏洩した相手・経路 (特定の第三者・不特定多数・外部公開 等)
5. 二次被害の可能性 (財産的被害・なりすまし・ハラスメント等の懸念)

不確実な点は推測ではなく「不明」と記録する。

### 2.4 証跡保全

- アクセスログ・クエリログ・関連 Issue・通報メールを別フォルダに退避し、改竄されない形で保管
- Supabase の自動ログ保管期限 (無料枠は短い) を考慮し、必要なログは早期にエクスポートする
- スクリーンショット・画面録画も同フォルダに集約

## 3. ステップ 3: 個人情報保護委員会への報告

### 3.1 報告対象案件の判定

以下のいずれかに該当する場合、個人情報保護委員会への報告 + 本人通知の義務が発生する (個人情報保護法施行規則 §7 に基づく代表パターン):

1. **要配慮個人情報** が含まれる漏洩等 (病歴・障害・犯罪歴 等)
2. **財産的被害が発生するおそれ** がある漏洩等 (クレジットカード番号 / 銀行口座 / マイナンバー 等)
3. **不正の目的をもって行われたおそれ** がある漏洩等 (外部からの不正アクセス・内部不正 等)
4. **本人の数が 1,000 人を超える** 漏洩等

最終判定根拠は個人情報保護委員会の現行規則・ガイドラインによる SHALL。本 SOP の例示は判断補助であり、規則改正時は委員会発表が優先する。

### 3.2 報告タイムライン

| 報告区分 | 期限 | 内容 |
|---|---|---|
| 速報 | 検知から **概ね 3〜5 日以内** | 暫定的に把握している事実 (発生日時・概要・被害人数の暫定値・原因の暫定 等) を報告 |
| 確報 | 検知から **30 日以内** (上記 §3.1 の 1 / 3 に該当する場合は **60 日以内**) | 確定した事実・原因・再発防止策を含む詳細報告 |

検知した時点で **その日を 0 日目としてカウントダウン** を開始する。確報の日数算定は土日祝を含む暦日であり、営業日ベースではない点に注意する MUST。

### 3.3 報告方法

- 報告先: 個人情報保護委員会
- 提出方法: 委員会の公式サイトに掲載されている報告フォーマット (オンライン受付窓口) を使用する
- 報告内容に含める項目 (委員会フォーマットに準拠):
  - 概要 (発生日時・覚知日時・発見経緯)
  - 漏洩等した個人データの項目 (氏名 / メール / 本人確認書類 等)
  - 件数 (人数・レコード数)
  - 原因
  - 二次被害 / そのおそれの有無
  - 本人への対応の実施状況
  - 公表の実施状況
  - 再発防止のための措置
  - 連絡先 (オーナー連絡先)

### 3.4 判定が微妙な場合のエスカレーション

報告対象案件に該当するか判断が難しい場合は、自己判断で報告を省略してはならない MUST。以下のいずれかを実施する:

- 個人情報保護委員会の **PIO (個人情報保護法相談ダイヤル / 事前相談窓口)** に問い合わせる
- 弁護士 / プライバシー専門家への相談
- 安全側に倒し、報告対象として扱う

判断微妙な事案ほど時間が経過しがちだが、§3.2 のタイムラインは検知時刻から進行している点に留意する。

## 4. ステップ 4: 本人通知

### 4.1 通知対象本人の特定

- §2.3 で特定した影響範囲から、漏洩した本人を `members` テーブル等から特定する
- 特定が困難な場合 (不特定多数への漏洩 / 削除済データの漏洩) は、代替措置として公表 (LP トップ等への掲載) を検討する

### 4.2 通知方法

- 主たる通知方法: **メール** (`high.q.volleyball@gmail.com` から会員登録メールアドレス宛)
- メール送信に失敗した場合は他の連絡手段 (電話番号登録があれば電話 / SMS) を検討
- 大規模事案 (件数多 or 連絡手段不明) の場合は LP トップへの公表で代替

### 4.3 通知文面に含めるべき項目

- 概要 (何がいつ漏洩したか)
- 漏洩した本人の個人データ項目
- 原因 (確定していない段階では「現在調査中」と明記)
- 二次被害 / そのおそれの有無 と本人が取るべき対策 (パスワード変更推奨 等)
- 既に講じた対策と今後の再発防止策
- 問い合わせ窓口 (本人からの追加質問に応じる体制)
- 謝罪文

通知タイミング: 速報報告と並行して可能な限り早期に。確定情報を待ちすぎず、判明している事実のみで先行通知して構わない (続報は別途送信)。

## 5. ステップ 5: 再発防止策

### 5.1 原因分析

- 技術的原因 (RLS 設定漏れ / アクセスキー漏洩 / 依存ライブラリの脆弱性 等)
- 人的原因 (操作ミス / 周知不足 / 規程違反 等)
- 組織的原因 (一人体制ゆえの相互チェック不在 / 規程の不備 等)

の 3 軸で分析する。1 軸に偏らないこと。

### 5.2 恒久対策の実装

- 技術: コード修正・RLS 強化・監査ログ拡充・自動検知の追加
- 運用: SOP 改訂・チェックリスト追加・定期レビュー頻度の見直し
- 予防: ペアレビュー導入 (将来複数人体制移行時) / 静的解析ツール強化 / 依存更新ポリシー強化

対策ごとに担当 (一人体制では責任者本人) と完了予定日を設定する。

### 5.3 振り返り記録

- 事案ごとに事案番号 (例: `INC-2026-001`) を採番し、検知から再発防止策実装までを 1 つの記録ファイルに集約する
- 記録項目: 検知日時 / 概要 / 影響範囲 / 報告履歴 / 本人通知履歴 / 原因分析 / 再発防止策 / 完了日
- 記録ファイルは private 領域に保管 (GitHub Public リポジトリには載せない)
- 年次で全事案を振り返り、SOP の改訂要否を判断する

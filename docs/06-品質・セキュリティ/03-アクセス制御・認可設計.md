## 1. 認証方式

| 項目 | 値 |

## 2. ロール定義

| ロール | 値 | 用途 |
|---|---|---|
| 一般会員 | `members.role = 'member'`（デフォルト） | 予約サイトの一般ユーザー |
| 管理者 | `members.role = 'admin'` | サークル幹事、管理画面ユーザー |

Phase 1 暫定: 管理者の昇格は SQL 直書き運用（手順は §7 参照）。UI からの操作は Phase 2 以降。

## 3. 認可（RLS = Row Level Security）

全テーブルで PostgreSQL の RLS を有効化。クライアントから直接 PostgREST 経由で SQL を投げても、ポリシーを通過した行のみが返る。

### 3.1 events（イベント）

| 操作 | 対象ロール | ポリシー |
|---|---|---|
| SELECT | anon, authenticated | `using (true)` — 公開カレンダー |
| INSERT | authenticated（管理者のみ） | `with check (is_admin())` |
| UPDATE | authenticated（管理者のみ） | `using (is_admin()) with check (is_admin())` |
| DELETE | authenticated（管理者のみ） | `using (is_admin())` |

**根拠**: イベントは LP / 予約サイトで一般公開し、管理画面でのみ編集する。

### 3.2 members（会員）

| 操作 | 対象 | ポリシー |
|---|---|---|
| SELECT | authenticated | 自分の行のみ + 管理者は全件: `using (id = auth.uid() or is_admin())` |
| INSERT | （明示ポリシーなし） | RLS 既定で拒否。トリガー `handle_new_auth_user`（SECURITY DEFINER）経由のみ |
| UPDATE | authenticated | `using (id = auth.uid() or is_admin())` + `with check` で **role 自己昇格を禁止** |
| DELETE | authenticated（管理者のみ） | `using (is_admin())` |

**root 自己昇格防止の WITH CHECK**:
```sql
with check (
  is_admin()
  or (
    id = auth.uid()
    and role = (select role from members where id = auth.uid())
  )
)
```
「管理者は何でも可」または「自分の行で role を変えない場合のみ可」。

### 3.3 reservations（予約）

| 操作 | 対象 | ポリシー |
|---|---|---|
| SELECT | authenticated | 自分の予約 + 管理者は全件 |
| INSERT | authenticated | `with check (member_id = auth.uid() or is_admin())` — なりすまし防止 |
| UPDATE | authenticated | 自分の予約は `reserved` / `cancelled` への変更のみ可、管理者は全 status 可 |
| DELETE | authenticated（管理者のみ） | `using (is_admin())` |

**`attended` / `no_show` は管理者のみ更新可能**。一般会員が「自分が出席した」と偽装することを防ぐ。

## 4. ヘルパー関数 `is_admin()`

```sql
create or replace function public.is_admin()
returns boolean
language sql
security definer
set search_path = public
stable
as $$
  select exists (
    select 1 from public.members
    where id = auth.uid() and role = 'admin'
  );
$$;
```

- **SECURITY DEFINER**: 関数所有者の権限で実行 → `members` への RLS を経由しないため循環参照を回避
- **引数なし**: SQL injection 経路を作らない（auth.uid() のみで判定）
- **STABLE**: 同一トランザクション内では同じ値を返すと宣言しオプティマイザに最適化を許す

## 6. 攻撃シナリオと防御

| 攻撃 | 防御 |
|---|---|
| 一般会員が他人の予約を閲覧 | RLS SELECT で `member_id = auth.uid()` を強制 |
| 一般会員が自分を admin に昇格 | RLS UPDATE WITH CHECK で role 変更を拒否 |
| 一般会員が他人を予約させる | RLS INSERT WITH CHECK で `member_id = auth.uid()` を強制 |
| 一般会員が「出席した」と偽装 | RLS UPDATE WITH CHECK で `status` を `reserved`/`cancelled` のみ許容 |
| 削除済みユーザーの履歴消失 | events / members への FK は `ON DELETE RESTRICT`（reservations から） |
| サインアップ時の members 自動作成失敗 | トリガー失敗時は auth.users INSERT もロールバック（PostgreSQL のトランザクション保証） |
| 公開キーの不正利用 | RLS が機能していれば anon key 公開可。万一 RLS にバグがあっても CHECK 制約 + 監視（Phase 2）で多層防御 |

## 7. 管理者ユーザー作成手順（Phase 1 暫定）

UI が未実装なので手動運用:

```sql
-- 1) 通常通り Email + Password でサインアップ（admin 画面 or Auth UI）
-- 2) Supabase Dashboard → SQL Editor で以下を実行
update public.members
set role = 'admin'
where email = '<your-email@example.com>';
-- 3) 反映確認
select id, email, display_name, role from public.members
where email = '<your-email@example.com>';
```

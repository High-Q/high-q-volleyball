# ADR-0006: Feature Sliced Design（FSD）の採用

- **日付**: 2026-04-25
- **状態**: 承認済み

## 背景

水平分割（`types/ services/ composables/ components/ pages/`）を当初採用していたが、以下の問題が想定された。

- 機能追加のたびに5ディレクトリ以上にファイルが分散する
- 「どこに何を置くか」の判断基準が曖昧になりやすい
- スケールに伴いレイヤー間の依存方向が崩れやすい
- 業務レベルの設計基準として強度が不足

## 決定

全アプリに **Feature Sliced Design（FSD）** を採用する。

FSD は Layers → Slices → Segments の3階層で構成されるフロントエンド向けアーキテクチャ手法。依存方向を一方向に強制し、スライス間の独立性を保証する。

## 採用するレイヤー構成

```
app → pages → widgets → features → entities → shared
```

（詳細: `docs/03-アーキテクチャ/04-開発・コーディング規約.md`）

## 理由

- 機能ごとにすべての関連ファイルが同一ディレクトリに集約される（変更局所性）
- 依存方向がフォルダ構造として可視化されるため、アーキテクチャの崩れを防ぎやすい
- Vue 3 の Composition API / Pinia / TanStack Query と自然に統合できる
- 個人開発から複数人開発へのスケールアップに対応できる
- 業界での採用実績があり、参照できる資料・事例が豊富

## 却下した代替案

- **水平分割維持**: 小規模時は問題ないが、機能増加に伴いファイル分散が深刻になる
- **フル DDD（Hexagonal Architecture）**: Entity / Aggregate / Repository の実装コストがプロジェクト規模に対して過剰

## トレードオフ

- 初期の学習コストあり（特に `widgets` と `features` の境界判断）
- 小さいうちは水平分割より冗長に感じる場合がある
- Cross-import ルール（同一レイヤー間の直接参照禁止）を意識する必要がある

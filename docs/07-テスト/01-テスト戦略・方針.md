# テスト戦略・方針

## 基本方針

- **TDD（テスト駆動開発）を原則とする**: ビジネスロジックは RED → GREEN → REFACTOR の順で実装する。
- **カバレッジ数値ではなく振る舞いをテストする**: 「この関数が何をすべきか」を起点にテストを書く。
- **テストなし実装タスクは Task フェーズで承認しない**: 全 Apply タスクに対応するテストタスクを必須とする。

---

## テスト種別・ツール・タイミング

| 種別 | ツール | 対象 | タイミング |
|------|--------|------|-----------|
| ユニットテスト | Vitest | composable・service・型ガード | 実装前（TDD）|
| コンポーネントテスト | Vitest + @vue/test-utils | Vueコンポーネント | 実装と並行 |
| APIモック | MSW (Mock Service Worker) | Supabase・外部API | テスト・開発両用 |
| E2Eテスト | Playwright | 主要ユーザーフロー | 機能完成後 |
| 手動テスト | ローカル + Renderプレビュー | UI/UX・エッジケース | PR作成前 |

---

## テストファイル配置

実装ファイルと同一ディレクトリに配置する（共存方式）。

```
src/composables/useEvents.ts
src/composables/useEvents.spec.ts   ← 必須

src/services/eventService.ts
src/services/eventService.spec.ts   ← 必須

src/components/EventCard.vue
src/components/EventCard.spec.ts    ← UIテストが意味を持つ場合
```

## ユニットテスト方針（Vitest）

### テスト対象の優先順位

1. **composable** — アプリケーションロジック（状態管理・エラーハンドリング）
2. **service** — 外部APIとのやり取り（MSWでモック）
3. **型ガード・バリデーション関数** — ドメインルールの境界
4. **Vueコンポーネント** — 複雑なロジックを持つ場合のみ（表示だけならスキップ可）

### テストケース設計の必須観点

| 観点 | 内容 |
|------|------|
| 正常系 | 期待する入力で期待する結果が返る |
| 異常系 | 不正入力・API失敗・ネットワークエラー |
| 境界値 | 文字数上限・0件・最大件数・日付境界 |
| 副作用 | storeの状態変化・emitのタイミング |

### エラー結果の検証

エラーを握りつぶすテストは無効。Result型で正常・異常を分けて検証する。

```typescript
// ✅ Good
const result = await fetchEvents();
expect(result.ok).toBe(false);
expect(result.error.code).toBe('NETWORK_ERROR');

// ❌ Bad
const result = await fetchEvents();
expect(result).toBeDefined(); // エラー内容を確認していない
```

## コンポーネントテスト方針（@vue/test-utils）

コンポーネントテストは以下の場合のみ作成する（無闇に量を増やさない）:

- ユーザー操作に応じた状態変化がある
- emit / slot の動作確認が必要
- 条件付きレンダリングの分岐が複雑

```typescript
// 例: イベントクリックでモーダルが開く
it('イベントをクリックするとダイアログが開く', async () => {
  const wrapper = mount(EventCalendar, { props: { events: mockEvents } });
  await wrapper.find('.event-item').trigger('click');
  expect(wrapper.find('[data-testid="event-dialog"]').isVisible()).toBe(true);
});
```

### マウントルール

- `shallowMount` を基本とし、子コンポーネントの動作が必要な場合のみ `mount`
- Vuetify コンポーネントは `global.plugins` で登録

## APIモック方針（MSW）

- 外部APIへの実リクエストはテストで発生させない
- MSWのハンドラーは `src/mocks/handlers/` に集約
- 開発時（`dev` モード）にも MSW を有効化し、Supabase 未整備の機能を開発可能にする

```typescript
// src/mocks/handlers/events.ts
http.get('/api/events', () => {
  return HttpResponse.json({ data: mockEvents });
});
```

---

## E2Eテスト方針（Playwright）

対象は「ユーザーが最も重要視する主要フロー」のみ。網羅性より信頼性を優先する。

| 優先度 | シナリオ |
|--------|---------|
| 高 | 会員登録・ログイン |
| 高 | イベント予約（正常フロー） |
| 中 | 管理者ログイン・イベント作成 |
| 低 | エラー系・細かいUI確認 |

E2Eテストは CI で main ブランチへのマージ時のみ実行（PR の unit/component テストとは分離）。

---

## 手動テストチェックリスト（PR前）

Apply 完了後、PR 作成前に必ず確認する。

- [ ] ゴールデンパス（主要フロー）を実際に操作した
- [ ] エラー系（API失敗・入力バリデーション）を確認した
- [ ] モバイル表示（375px / Chrome DevTools）を確認した
- [ ] Loading / Empty / Error 状態を確認した

---

## ロギングとの関係

テストにおいてログ出力（`console.error` 等）が発生した場合はテスト失敗扱いとする。
ログ方針の詳細は `docs/06-品質・セキュリティ/07-ロギング方針.md` を参照。

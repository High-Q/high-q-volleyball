# テスト戦略・方針

## 基本方針

- **TDD（テスト駆動開発）を原則とする**: ビジネスロジックは RED → GREEN → REFACTOR の順で実装する。
- **カバレッジ数値ではなく振る舞いをテストする**: 「この関数が何をすべきか」を起点にテストを書く。
- **テストなし実装タスクは Task フェーズで承認しない**: 全 Apply タスクに対応するテストタスクを必須とする。

---

## テスト種別・ツール・タイミング

| 種別 | ツール | 対象 | タイミング |
|------|--------|------|-----------|
| ユニットテスト | Vitest | composable・service・型ガード | 実装前（TDD）|
| コンポーネントテスト | Vitest + @vue/test-utils | Vueコンポーネント | 実装と並行 |
| APIモック | MSW (Mock Service Worker) | Supabase・外部API | テスト・開発両用 |
| E2Eテスト | Playwright | 主要ユーザーフロー | 機能完成後 |
| 手動テスト | ローカル + Renderプレビュー | UI/UX・エッジケース | PR作成前 |

## テストファイル配置

実装ファイルと同一ディレクトリに配置する（共存方式）。

```
src/composables/useEvents.ts
src/composables/useEvents.spec.ts   ← 必須

src/services/eventService.ts
src/services/eventService.spec.ts   ← 必須

src/components/EventCard.vue
src/components/EventCard.spec.ts    ← UIテストが意味を持つ場合
```

## ユニットテスト方針（Vitest）

### テスト対象の優先順位

1. **composable** — アプリケーションロジック（状態管理・エラーハンドリング）
2. **service** — 外部APIとのやり取り（MSWでモック）
3. **型ガード・バリデーション関数** — ドメインルールの境界
4. **Vueコンポーネント** — 複雑なロジックを持つ場合のみ（表示だけならスキップ可）

### テストケース設計の必須観点

| 観点 | 内容 |
|------|------|
| 正常系 | 期待する入力で期待する結果が返る |
| 異常系 | 不正入力・API失敗・ネットワークエラー |
| 境界値 | 文字数上限・0件・最大件数・日付境界 |
| 副作用 | storeの状態変化・emitのタイミング |

### エラー結果の検証

エラーを握りつぶすテストは無効。Result型で正常・異常を分けて検証する。

```typescript
// ✅ Good
const result = await fetchEvents();
expect(result.ok).toBe(false);
expect(result.error.code).toBe('NETWORK_ERROR');

// ❌ Bad
const result = await fetchEvents();
expect(result).toBeDefined(); // エラー内容を確認していない
```

## コンポーネントテスト方針（@vue/test-utils）

コンポーネントテストは以下の場合のみ作成する（無闇に量を増やさない）:

- ユーザー操作に応じた状態変化がある
- emit / slot の動作確認が必要
- 条件付きレンダリングの分岐が複雑

```typescript
// 例: イベントクリックでモーダルが開く
it('イベントをクリックするとダイアログが開く', async () => {
  const wrapper = mount(EventCalendar, { props: { events: mockEvents } });
  await wrapper.find('.event-item').trigger('click');
  expect(wrapper.find('[data-testid="event-dialog"]').isVisible()).toBe(true);
});
```

### マウントルール

- `shallowMount` を基本とし、子コンポーネントの動作が必要な場合のみ `mount`
- Vuetify コンポーネントは `global.plugins` で登録

## APIモック方針（MSW）

- 外部APIへの実リクエストはテストで発生させない
- MSW のハンドラーは `src/test/mocks/handlers/` に集約し、`src/test/mocks/server.ts` で `setupServer(...handlers)` を export する
- `src/test/setup.ts`（lp は `setup.js`）で `beforeAll` / `afterEach` / `afterAll` に `server.listen` / `resetHandlers` / `close` を登録する（Vitest `setupFiles` から読み込む）
- 開発時（`dev` モード）にも MSW を有効化し、Supabase 未整備の機能を開発可能にする

```typescript
// src/test/mocks/handlers/index.ts
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/sample', () => HttpResponse.json({ ok: true })),
];
```

## E2Eテスト方針（Playwright）

対象は「ユーザーが最も重要視する主要フロー」のみ。網羅性より信頼性を優先する。

| 優先度 | シナリオ |
|--------|---------|
| 高 | 会員登録・ログイン |
| 高 | イベント予約（正常フロー） |
| 中 | 管理者ログイン・イベント作成 |
| 低 | エラー系・細かいUI確認 |
| 低（smoke） | LP トップページ表示・主要セクション・カレンダー widget root 存在（#79 で導入、データ非依存） |

E2Eテストは CI で master ブランチへのマージ時のみフル実行（PR の unit/component テストとは分離）。PR では smoke のみ走らせる「PR=smoke / master=full」のトリガー分離方針（後述）。

### E2E 環境構成（#79 で確立）

- ランナー: `@playwright/test`（root の devDependencies、apps/* には置かない）
- ブラウザ: chromium のみ（Phase 1 minimal、必要になったら拡張）
- テスト配置: `e2e/<app>/*.e2e.ts`（Vitest の `*.spec.ts` と完全分離）
- 起動方式: Playwright の `webServer` で `pnpm --filter @high-q/lp build && vite preview --port 4173 --strictPort` を起動し、本番ビルドに対して E2E を回す
- 実行: ローカル `pnpm test:e2e`（CI 統合は #136 で対応）
- セットアップ: 初回 `pnpm exec playwright install chromium` でブラウザバイナリを取得

## 回帰試験戦略

本プロジェクトでは「回帰試験」を**独立した工程としては設けない**。代わりに以下のレイヤーで回帰を自動的に検出する:

| レイヤー | 検出対象 | 実行タイミング |
|---|---|---|
| typecheck（`vue-tsc --noEmit`） | 型レベルの破壊的変更 | CI 全 PR |
| lint（ESLint） | 規約違反 | CI 全 PR |
| unit / component test（Vitest） | ロジック・UI 部品の挙動 | CI 全 PR |
| build（`vite build`） | バンドル可否・依存解決 | CI 全 PR |
| E2E（Playwright） | 主要ユーザーフロー | CI master push 時にフル / PR 時に smoke（#136 で実装） |
| 手動 UI 確認（Render Preview） | ビジュアル・UX | PR 前必須 |

つまり**コミット単位で全テストを実行することで回帰検出を担保**する。「回帰試験フェーズ」を別途持たない。

カバレッジが薄い領域は「[TEST] 既存機能への E2E 適用 catch-up」（#135）等で漸進的に補強する。

### 将来検討する回帰試験

| 種別 | 戦略候補 | 想定 Phase |
|---|---|---|
| スキーマ回帰 | Supabase migration 試験（既存データ・既存クエリが migration 後も動くか） | Phase 1 後半 〜 2 |
| ビジュアル回帰（VRT） | Playwright スクリーンショット比較 / Chromatic / Percy | Phase 2 |
| パフォーマンス回帰 | Lighthouse CI / size-limit | Phase 2 |

これらは Phase 1 では手動確認 / 後追い対応とし、必要性が顕在化した時点で別 Issue で導入する。

## E2E スケーラビリティ運用ルール

E2E は無計画に増やすと**スイートが肥大化し開発のボトルネック化**する典型的な失敗パターンがある。導入時点で以下の運用ルールを定めて腐敗を防ぐ。

### 1. テストピラミッド原則の厳守

E2E は最後の砦であり、量で勝負しない。

```
       ┌─────┐
       │ E2E │   ← 全体の 5-10%。critical path のみ
       └─────┘
     ┌─────────┐
     │ comp+int │  ← 30-40%。コンポーネント / 統合
     └─────────┘
   ┌─────────────┐
   │ unit / type │ ← 50-60%。ロジック単体 / 型
   └─────────────┘
```

**原則**: component test で取れるなら component に降ろす、unit test で取れるなら unit に降ろす、E2E でしか取れない場合だけ E2E に書く。

### 2. 機能あたりの E2E 件数上限

| 種別 | 上限 | 内容 |
|---|---|---|
| 1 機能あたり E2E | **1〜2 件** | happy path 1 件 + 主要 edge case 1 件まで |
| 詳細バリエーション | 0 件 | component / unit test に押し下げる |

### 3. CI トリガー分離（PR=smoke / master=full）

| トリガー | 走る E2E | 目的 |
|---|---|---|
| **PR push** | 軽量 smoke のみ（`@smoke` tag、5-10 件、~1分） | 開発の feedback loop を保つ |
| **master push** | フル E2E（全件、~5分まで許容） | リリース前の最終回帰 |
| **nightly（任意）** | フル + 重い試験（VRT 等） | 補完 |

実装は #136（Playwright を GitHub Actions CI に統合）で対応。

### 4. 並列実行（Playwright shards）

CI 上で Playwright `--shard=N/M` を使った物理的時間短縮を方針とする。詳細は #136 で設計。

### 5. 四半期リトラクト

四半期に 1 回（または機能数が一定数を超えた時）、E2E を見直して**意識的に削る**:

- 重複している E2E
- 同じ機能を component test でもカバーしている E2E
- フレーク多発で価値より維持コストが高い E2E

「テストは増やすもの」と思い込みがちなため、**意識的に減らす機会**を運用に組み込む。

### 6. ハードリミット閾値

健全性指標。危険ゾーンに入った時点で**最適化 Issue を切る**運用とする。

| 指標 | 健全 | 警告 | 危険 |
|---|---|---|---|
| PR の CI 全体時間 | < 3分 | 3-5分 | > 5分 |
| master の E2E フル時間 | < 5分 | 5-10分 | > 10分 |
| 機能あたり E2E 件数 | 1-2 | 3-4 | 5+ |
| E2E のフレーク率 | < 1% | 1-3% | > 3% |

フレーク率 3% を超えると「テスト = 信頼できない」認識が定着し回帰検出力が崩壊するため要警戒。

## 手動テストチェックリスト（PR前）

Apply 完了後、PR 作成前に必ず確認する。

- [ ] ゴールデンパス（主要フロー）を実際に操作した
- [ ] エラー系（API失敗・入力バリデーション）を確認した
- [ ] モバイル表示（375px / Chrome DevTools）を確認した
- [ ] Loading / Empty / Error 状態を確認した

## ロギングとの関係

テストにおいてログ出力（`console.error` 等）が発生した場合はテスト失敗扱いとする。
ログ方針の詳細は `docs/06-品質・セキュリティ/07-ロギング方針.md` を参照。

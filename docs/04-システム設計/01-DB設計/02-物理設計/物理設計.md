## 1. プラットフォーム

- **DB**: Supabase（PostgreSQL 16 系・マネージド）
- **リージョン**: `Northeast Asia (Tokyo)` ＝ AWS `ap-northeast-1`（Supabase が AWS 上で運用）
- **プラン**: Free（500 MB DB / 50,000 MAU）
- **接続**: クライアントは `@supabase/supabase-js` v2.45+ 経由、`packages/shared/src/api/supabase.ts` のラッパー単一エントリポイント

## 2. 列型と制約

### 2.1 events

| 列 | 型 | NULL | デフォルト | 制約 |
|---|---|---|---|---|
| id | uuid | NOT NULL | `gen_random_uuid()` | PK |
| name | text | NOT NULL | - | - |
| description | text | NULL | - | - |
| start_at | timestamptz | NOT NULL | - | `start_at < end_at`（CHECK） |
| end_at | timestamptz | NOT NULL | - | 同上 |
| location | text | NULL | - | - |
| capacity | smallint | NULL | - | `capacity is null or capacity > 0`（CHECK） |
| status | text | NOT NULL | `'scheduled'` | `in ('scheduled','cancelled','closed')`（CHECK） |
| created_by | uuid | NULL | - | FK auth.users(id) ON DELETE SET NULL |
| created_at | timestamptz | NOT NULL | `now()` | - |
| updated_at | timestamptz | NOT NULL | `now()` | BEFORE UPDATE トリガー `set_updated_at()` |

**インデックス**:
- `events_start_at_idx` on (start_at) — カレンダーのレンジクエリ用
- `events_status_scheduled_idx` on (start_at) WHERE status = 'scheduled' — partial index、公開カレンダー高速化用

### 2.2 members

| 列 | 型 | NULL | デフォルト | 制約 |
|---|---|---|---|---|
| id | uuid | NOT NULL | - | PK + FK auth.users(id) ON DELETE CASCADE |
| email | text | NOT NULL | - | UNIQUE |
| display_name | text | NOT NULL | - | - |
| role | text | NOT NULL | `'member'` | `in ('member','admin')`（CHECK） |
| profile | jsonb | NOT NULL | `'{}'::jsonb` | - |
| created_at | timestamptz | NOT NULL | `now()` | - |
| updated_at | timestamptz | NOT NULL | `now()` | BEFORE UPDATE トリガー `set_updated_at()` |

**インデックス**: PK と email UNIQUE のみ（Phase 1 規模では十分）

**特殊**:
- `auth.users` へ INSERT 時にトリガー `on_auth_user_created` が `handle_new_auth_user()` を呼び、`members` に同じ id で行を自動作成する
- `display_name` 初期値はメールアドレスの `@` 前部分（後でユーザー編集可能）

### 2.3 reservations

| 列 | 型 | NULL | デフォルト | 制約 |
|---|---|---|---|---|
| id | uuid | NOT NULL | `gen_random_uuid()` | PK |
| event_id | uuid | NOT NULL | - | FK events(id) ON DELETE RESTRICT |
| member_id | uuid | NOT NULL | - | FK members(id) ON DELETE RESTRICT |
| status | text | NOT NULL | `'reserved'` | `in ('reserved','cancelled','attended','no_show')`（CHECK） |
| note | text | NULL | - | - |
| created_at | timestamptz | NOT NULL | `now()` | - |
| updated_at | timestamptz | NOT NULL | `now()` | BEFORE UPDATE トリガー `set_updated_at()` |

**追加制約**:
- UNIQUE (event_id, member_id) — 1 イベント・1 会員に対し 1 行

**インデックス**:
- `reservations_event_id_idx` on (event_id)
- `reservations_member_id_idx` on (member_id)
- `reservations_member_status_idx` on (member_id, status) — マイページ等で会員自身の予約を status でフィルタ

## 3. トリガー / 関数

### 3.1 set_updated_at()

events / members / reservations すべてに `BEFORE UPDATE` トリガーで適用。アプリ層のセットし忘れを防ぐ（design.md D6）。

### 3.2 handle_new_auth_user()

`auth.users` への INSERT 時にトリガー `on_auth_user_created` から呼び出され、`public.members` へ同じ id で行を自動作成する。SECURITY DEFINER のため、auth スキーマからの INSERT が public.members への RLS を経由せずに通る（design.md D3）。

### 3.3 is_admin()

RLS ポリシー内の管理者判定で使用。SECURITY DEFINER により呼び出し元の RLS を経由せず members を読めるため、members への RLS と循環しない（design.md D7）。引数なし関数で SQL injection 経路を作らない。

## 4. RLS（Row Level Security）

詳細は `docs/06-品質・セキュリティ/03-アクセス制御・認可設計.md` を参照。

各テーブルとも `enable row level security` 済み（`pg_class.relrowsecurity = true`）。

| テーブル | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| events | 全員（anon, authenticated） | admin のみ | admin のみ | admin のみ |
| members | 自分の行のみ + admin 全件 | （明示ポリシーなし＝既定で拒否、トリガー経由のみ） | 自分の行（role 変更不可）+ admin 全件 | admin のみ |
| reservations | 自分の予約 + admin 全件 | 自分の member_id のみ + admin | 自分の予約（reserved/cancelled のみ）+ admin 全件 | admin のみ |

## 5. 容量見積もり（Phase 1）

| テーブル | 想定行数 | 1 行サイズ目安 | 合計目安 |
|---|---|---|---|
| members | 〜100 | 〜500 B | 〜50 KB |
| events | 〜200/年 | 〜1 KB | 〜200 KB/年 |
| reservations | 〜2,000/年 | 〜500 B | 〜1 MB/年 |

Supabase Free 枠 500 MB に対して数年間は余裕。

## 6. バックアップ・障害対応

- **Supabase Free 枠**: 自動バックアップなし。Pro プラン（$25/月）で日次バックアップ
- **Phase 1 暫定**: 重要データは少ないため、必要なら SQL Editor で `pg_dump` 相当のクエリを手動実行してエクスポート
- **Phase 2 以降**: 利用ユーザー増・予約データ蓄積に伴い、Pro プラン移行 or 自前バックアップ運用を検討

## 7. マイグレーション運用

- `supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql` 形式で git 管理
- **Phase 1**: Dashboard SQL Editor へ手動貼り付けて RUN（design.md D10）
- **Phase 2**: GitHub Actions + `supabase db push` で CI 自動化（Issue #80 と連携）
- ロールバック: 該当リソースを `drop` する SQL を別ファイルで作成して手動実行

## 8. パフォーマンス目標（Phase 1）

| クエリ | 目標 |
|---|---|
| events のカレンダー表示（月絞り込み） | < 50 ms |
| reservations のマイページ表示 | < 100 ms |
| auth サインアップ → members 自動作成 | < 500 ms |

これらは Supabase Free 枠でも十分達成可能と想定。Phase 2 で本格運用に入ったら EXPLAIN で実行計画を確認してインデックス追加を検討。

# UI 設計方針

## UI スタック

| アプリ | UI スタック | 着色レイヤー |
|--------|------------|------------|
| `apps/lp` | Vuetify 3 + `@high-q/ui`（部分利用） | Vuetify テーマトークン + HQ CSS 変数（移行検討中） |
| `apps/admin` | `@high-q/ui`（意匠系） + shadcn-vue（機能系） + Vue Router | `@high-q/tailwind-preset` utility + HQ CSS 変数 |
| `apps/reservation` | 同上 | 同上 |

3 アプリ共通の真実の源は **`@high-q/design-tokens`** パッケージ。色・書体・spacing・radius・shadow は HQ object（TS）と `--hq-*` CSS 変数の両方で配布される。

`apps/admin` / `apps/reservation` は `@high-q/tailwind-preset`（`packages/tailwind-preset`）を `tailwind.config.ts` の `presets` に取り込んで HQ tokens を utility class（`bg-paper` / `text-ink` / `text-accent` / `font-jp` / `p-hq-4` / `rounded-hq-md` 等）として利用する。`hq-` prefix で Tailwind デフォルト（`p-4` 等）と明示的に区別する設計。

### `@high-q/ui` と shadcn-vue の棲み分け

意匠系プリミティブと機能系プリミティブは責務を分けて 2 つの提供元を併用する:

| 提供元 | 何を置くか | 例 |
|---|---|---|
| **`@high-q/ui`**（packages/ui） | **HQ 独自のデザイン言語を体現する意匠系プリミティブ**。`var(--hq-*)` で着色、Tailwind / shadcn-vue 非依存。3 アプリ共通利用。 | `Button` / `Kicker` / `Badge` / `Photo` / `RemainBar`、将来の `EventCard` / `EventDateBlock` / `StickyCTA` |
| **shadcn-vue**（apps/<app>/src/shared/ui/） | **a11y 完璧な機能系プリミティブ**。radix-vue + Tailwind preset utility ベース。各アプリで配置・改変。 | `Input` / `Label` / `FormField` / `Dialog` / `Dropdown` / `Combobox` / `DataTable` / `Toast` / `DatePicker` |

**`Button` は `@high-q/ui` の単一責務**（CTA の見た目を 3 アプリで完全統一するため、shadcn-vue の `Button` は取り込まない）。

両者とも着色は HQ デザイントークン経由のみ。マジックナンバー（直接 `#xxxxxx` / `rgb()` / `rgba()` の埋め込み）禁止。

shadcn-vue プリミティブは必要になった時点で `npx shadcn-vue@latest add <component>` を該当アプリで実行して取り込む（先取り取り込みはしない）。

## デザイントークン（Design Tokens）

マジックナンバー（ハードコードされた色・サイズ値）の使用を禁止する。

3 アプリ共通の真実の源は **`@high-q/design-tokens`** パッケージ（`packages/design-tokens/`）。すべてのトークンは TypeScript named export と CSS variables（`:root` で `--hq-*`）の双方で配布される。詳細仕様: `openspec/specs/design-tokens/spec.md`。

```typescript
// TypeScript から
import { HQ } from '@high-q/design-tokens';
HQ.color.paper // '#f7f3ea'

// CSS から（apps/lp/src/main.js で tokens.css を import 済み）
.foo { background: var(--hq-color-paper); }
```

## コンポーネント設計原則

### 階層と責務分離

```
pages/         ← ルーティング単位。データ取得・composable 呼び出しのみ
  EventPage.vue
components/    ← 表示に特化。props で制御し、副作用を持たない
  EventCard.vue         ← 単一イベントの表示
  EventCardSkeleton.vue ← ローディング時のプレースホルダー
  EventList.vue         ← EventCard のリスト管理
composables/   ← アプリケーションロジック・状態管理
  useEvents.ts          ← イベント取得・状態
services/      ← 外部API・Supabase との通信のみ
  eventService.ts
```

### コンポーネント設計ルール

1. **1 コンポーネント = 1 責務**。表示ロジックと取得ロジックを混在させない。
2. **Props は読み取り専用**。コンポーネント内で props を変更しない（emit で親に伝える）。
3. **内部状態を最小化する**。`v-model` や `ref` は本当に必要な場合だけ使う。
4. **ビジネスロジックをコンポーネントに書かない**。composable または service に置く。

```vue
<!-- ✅ Good: 表示のみに集中したコンポーネント -->
<script setup lang="ts">
defineProps<{ event: EventSummary }>();
const emit = defineEmits<{ click: [id: string] }>();
</script>

<!-- ❌ Bad: コンポーネント内でAPIを呼ぶ -->
<script setup lang="ts">
const events = await supabase.from('events').select('*'); // NG
</script>
```

### Composable 設計ルール

```typescript
// ✅ Good: 明確な責務・Result型でエラーを表現
export function useEvents() {
  const events = ref<Event[]>([]);
  const isLoading = ref(false);
  const error = ref<string | null>(null);

  async function fetchEvents(): Promise<void> {
    isLoading.value = true;
    const result = await eventService.getAll();
    if (result.ok) {
      events.value = result.data;
    } else {
      error.value = result.error.message;
    }
    isLoading.value = false;
  }

  return { events: readonly(events), isLoading: readonly(isLoading), error: readonly(error), fetchEvents };
}
```

## 状態設計（必須の4状態）

すべてのデータ取得 UI は以下の4状態を必ず実装する。

| 状態 | 条件 | 表示 |
|------|------|------|
| **Loading** | `isLoading === true` | スケルトンスクリーンまたはスピナー |
| **Empty** | `items.length === 0` | 「データがありません」などの案内 |
| **Error** | `error !== null` | ユーザー向けメッセージ（技術詳細は非表示） |
| **Success** | データあり・エラーなし | 通常表示 |

```vue
<template>
  <div v-if="isLoading">
    <EventCardSkeleton v-for="i in 3" :key="i" />
  </div>
  <v-alert v-else-if="error" type="error">{{ error }}</v-alert>
  <div v-else-if="events.length === 0" class="empty-state">
    予定されているイベントはありません
  </div>
  <EventList v-else :events="events" />
</template>
```

## レスポンシブデザイン

### ブレークポイント（Vuetify / Tailwind 共通）

| 名前 | 幅 | 対象デバイス |
|------|-----|------------|
| `xs` | 〜599px | スマートフォン（縦） |
| `sm` | 600〜959px | スマートフォン（横）・タブレット（縦） |
| `md` | 960〜1279px | タブレット（横）・小型デスクトップ |
| `lg` | 1280px〜 | デスクトップ |

### モバイルファースト

- スタイルはモバイル（375px〜）を基本とし、`sm` 以上でレイアウトを拡張する
- タッチターゲット最小サイズ: **44×44px**（iOS HIG 準拠）
- テキストサイズはモバイルで `body: 16px` を下回らない

## アクセシビリティ（a11y）

### 必須要件

- **コントラスト比**: テキスト AA（4.5:1）以上
- **インタラクティブ要素**: すべてキーボードで操作可能
- **画像**: 装飾以外は `alt` 属性を必ず設定
- **フォーム**: `label` と `input` を紐付ける（`for` / `aria-labelledby`）
- **モーダル**: 開いた際にフォーカスをモーダル内に移動し、ESC キーで閉じる
- **エラーメッセージ**: `role="alert"` または `aria-live="polite"` で通知

```vue
<!-- ✅ Good -->
<v-btn aria-label="イベントを閉じる" icon @click="close">
  <v-icon>mdi-close</v-icon>
</v-btn>

<!-- ❌ Bad: アイコンのみでラベルなし -->
<v-btn icon @click="close"><v-icon>mdi-close</v-icon></v-btn>
```

## フォームデザイン方針

- **バリデーションはリアルタイム**（blur 時 + submit 時の二重チェック）
- **エラーメッセージはフィールド直下**に表示（ページ上部への集約はしない）
- **送信ボタンは処理中に disabled + ローディング表示**
- **成功フィードバックは `v-snackbar`** でトースト通知（3秒で自動消去）

### admin / reservation のフォーム実装ルール (HQ FormField 規約・厳守)

`apps/admin` / `apps/reservation` のすべての入力フィールドは MUST `shared/ui/FormField` widget でラップする。生 `<label>` + `<input>` / `<textarea>` を直書きすることを禁止する。

**初期表示で赤枠を出さない**: `FormField` は `error` prop に値が入ったときだけ赤色の error メッセージ + `aria-invalid=true` を起動する。空文字や未入力状態を「invalid 扱い」して赤枠表示するのは規約違反 (ユーザーの操作前にエラーを出す UX 悪化)。

| 状態 | 表示 |
|---|---|
| 初期 (空 / 未入力) | grey hairline border + grey hint メッセージ。**赤枠は出さない** |
| 入力中 (有効値) | focus 時 accent ring (青系)、border は hairline 維持 |
| invalid (制約違反) | `aria-invalid="true"` で border-danger + error メッセージを `role="alert"` 付きで表示 (赤色) |

**必須マーク `*` は使わず**、ラベルに「(必須)」と書くか hint で表現する SHALL。CTA disabled 制御は composable の computed (例: `canSubmit`) で行い、UI 側の見た目で「必須エラー風」を出さない。

参考実装: `apps/reservation/src/pages/SignupProfilePage.vue` (FormField + Input + `:error="fieldErrors.xxx"` 駆動)

## ナビゲーション規約 (admin / reservation 共通・厳守)

### パンくず (PageBreadcrumb)

- パンくず UI は MUST `apps/<app>/src/widgets/page-breadcrumb/PageBreadcrumb` widget のみで実装する。各 Page / Widget で `<nav aria-label="パンくず">` を独自に書くことを **禁止** SHALL。
- 配置場所は MUST Page header (Page コンポーネントの最上部) の **1 箇所のみ**。Widget 側 (TopBar 等) で重複してパンくずを描画してはならない。
- 構造ルール:
  - 第 1 セグメント: **`Workspace`** (固定)、`to: { name: 'events' }` で **admin TOP へのリンク化** MUST (admin / reservation 共通)
  - 第 2 セグメント: 機能カテゴリ名 (例: `Events` / `Identity Documents`)。**英語の Pascal Case** を使用 (FSD のスライス名 / URL に整合)。一覧画面では現在地としてリンク無し、孫ページからはリンク付き
  - 第 3 セグメント: 個別ページ名 (例: `詳細` / `新規作成` / `編集`)。**日本語**を使用、末尾現在地のためリンク無し
- h1 見出し (`<h1 class="font-jp-display text-lg text-ink">`) は breadcrumb の直下に配置し、画面の主目的を **日本語**で簡潔に書く (例: 「イベント」「本人確認書類」「書類詳細」)

### Page header の左右レイアウト

```
[ breadcrumb + h1 ]                              [ 横遷移リンク群 + ログアウト ]
```

- **左**: PageBreadcrumb + h1
- **右**:
  - 同階層への横遷移リンク (例: events list ⇄ identity-documents) は `<RouterLink>` で配置
  - ログアウトボタンは右端 (常に固定位置)
- 双方向遷移の対称性を MUST 確保する SHALL: `/A` から `/B` への横遷移リンクを置いたら、`/B` から `/A` へ戻る経路 (パンくず or 別リンク) も必ず用意する

### Widget 内 TopBar の責務

Widget 内の `XxxDetailTopBar.vue` 等は、**現在のレコードの内容サマリのみ** を表示する。パンくず / グローバルナビ / ログアウト等のアプリ全体ナビゲーション要素は Page 側で扱い、Widget は責務を侵さない。

参考実装: `apps/admin/src/widgets/event-detail/ui/EventDetailTopBar.vue` (パンくず無し、イベントサマリのみ)

### 違反検出

PR レビュー時に以下を grep で確認:

```bash
# Page 以外で <nav aria-label="パンくず"> を書いていないか
grep -rEn 'aria-label="パンくず"' apps/admin/src/widgets/ apps/reservation/src/widgets/

# PageBreadcrumb を経由しない breadcrumb 実装が無いか
grep -rE '<nav[^>]*breadcrumb' apps/admin/src/ apps/reservation/src/ | grep -v 'PageBreadcrumb.vue'
```

ヒットした場合は規約違反、修正必須。

### 新規 Page / Widget 実装前の既存踏襲ルール

新規 Page (例: 新しい詳細画面) や Widget (例: 新しい sticky bar) を実装する前に、**必ず既存の同種 Page を Read で先に読み**、レイアウト構造 / breadcrumb 構造 / header 配置 / TopBar 責務分離を踏襲する MUST。独自解釈で書き起こすことは禁止。

理由:
- breadcrumb の重複描画や独自 `<nav>` 実装などの規約違反は「既存を見ずに書き始めた」結果として発生する
- 同じアプリ内で Page ごとにヘッダ構造がブレると IA が崩れる

参考実装の例 (admin):
- `apps/admin/src/pages/EventDetailPage.vue` (詳細画面の標準形)
- `apps/admin/src/widgets/event-detail/ui/EventDetailTopBar.vue` (TopBar の責務範囲)

新規 Page を書く前に該当 Page / Widget を最低 1 件 Read してから着手する。

## アニメーション・トランジション方針

- ページ遷移: `v-fade-transition`（100ms）
- リスト追加・削除: `v-slide-y-transition`
- モーダル開閉: Vuetify の `v-dialog` デフォルトトランジション
- `prefers-reduced-motion: reduce` を尊重し、過剰なアニメーションを無効化

```css
@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}
```

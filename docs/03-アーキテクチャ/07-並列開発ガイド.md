# 並列開発ガイド (worktree + 2 Claude セッション)

> 2 並列で別 Issue を進めるとき、誰でも同じ手順で立ち上がれるようにする運用規約とツール。

---

## 1. 概要

翔太郎くんと別 Claude セッションが同時に異なる Issue / OpenSpec change を進めたいとき、本ガイドのスクリプトと Skill を使うことで以下を機械化する。

- worktree ディレクトリ作成 / ブランチ切り / `pnpm install`
- ポート割当 (admin / reservation の dev server)
- master 占有回避の運用ルール案内
- dev Supabase / OpenSpec の衝突回避ルール案内
- 動作確認案内テンプレ (URL / 主要シナリオ / 探索的試験観点)

個別 memory ではなく Skill / スクリプト / docs に固定することで、別端末・別人・別セッションでも同じ運用に乗れる状態を担保する。

---

## 2. ディレクトリ配置

```
~/Desktop/
├── high-q-volleyball/              ← メイン (常駐の作業ディレクトリ)
├── high-q-volleyball-wt-<issue>/   ← 2 本目以降の worktree (Issue 番号で識別)
└── high-q-volleyball-wt-<issue>/   ← 必要なら 3 本目以降 (運用上は 2 並列推奨)
```

- worktree ディレクトリ名は `<repo-name>-wt-<issue番号>` で固定
- リポジトリ root の **親階層** に置く (兄弟ディレクトリ扱い、エディタ / shell 補完が効きやすい)
- 3 本以上は未保証 (ポート / Skill は対応するが、衝突管理が複雑化するので非推奨)

---

## 3. ブランチ運用

### 3.1 master を 2 箇所で握らない (最重要)

`git worktree` は同一ブランチを 2 箇所で checkout できない仕様。そのため、

- **メイン作業ディレクトリも常に feature ブランチに居る**
- master は誰も checkout していない状態を維持する

これを守ると、各 worktree から `git fetch origin && git merge origin/master` で最新を取り込める。違反すると、もう片方が master を握っているために worktree 側の merge が破綻する。

### 3.2 ブランチ命名

| 用途 | prefix | 例 |
|---|---|---|
| 機能追加 | `feature/` | `feature/329-add-foo` |
| バグ修正 | `fix/` | `fix/330-event-overflow` |
| 雑務・インフラ | `chore/` | `chore/328-parallel-worktree-infra` |

slug は kebab-case (`[a-z0-9-]+`)。先頭に Issue 番号を必ず入れる。

### 3.3 最新取込

```bash
# 各 worktree で
git fetch origin
git merge origin/master
```

rebase ではなく **merge** を使う。理由: push 済みブランチへの force push を避け、PR 履歴を素直に保つため。

## 4. ポート規約

| Worktree | admin | reservation |
|---|---|---|
| メイン (`high-q-volleyball`) | 5173 | 5174 |
| wt-N (N = 既存 worktree 数。新規分が N 番目) | `5173 + 100*N` | `5174 + 100*N` |

例:

- メインのみ → admin 5173 / reservation 5174
- 2 本目 worktree (N=1) → admin 5273 / reservation 5274
- 3 本目 worktree (N=2) → admin 5373 / reservation 5374

### 4.1 起動コマンド

`vite.config.ts` は触らず、起動時 `--port` フラグで上書きする。

```bash
# メイン
pnpm --filter @high-q/admin dev --port 5173
pnpm --filter @high-q/reservation dev --port 5174

# 2 本目 worktree
pnpm --filter @high-q/admin dev --port 5273
pnpm --filter @high-q/reservation dev --port 5274
```

setup-worktree.sh が新規 worktree 作成時にポートを自動計算して案内する。

## 5. dev DB (Supabase) 衝突回避

dev Supabase プロジェクトは **1 個しかない** (費用ゼロ運用の方針)。そのため:

- **migration を含む change を 2 並列で走らせない**
- 進行中の change の `tasks.md` を grep し `supabase/migrations/` 配下を触るタスクが残っていないか確認
- 両方が migration を必要とする場合は、片方を先に完了 + `pnpm db:push` 後にもう片方を着手

技術的にブロックする手段は無い (Skill 警告のみ)。事故時は片方の change を一時停止 + migration 再 apply で復旧可能。

## 6. OpenSpec 衝突回避

| 禁止 | 理由 |
|---|---|
| 同名 change ディレクトリを 2 本同時に作る | Git で同一ファイルになり merge 衝突必至 |
| 同一 capability の spec を 2 並列で編集する | spec deltas の整合が崩れ、archive 時に header not found エラー |
| 進行中 change と同 capability の specs/ を 2 本目で触る | 上と同じ |

確認手順:

```bash
# 進行中の change と Capabilities を一覧
ls openspec/changes/ | grep -v archive
cat openspec/changes/<name>/proposal.md | grep -A 5 "Capabilities"
```

衝突候補があれば、片方の change で capability を分割するか、順序入れ替えで回避する。

## 7. スクリプト使い方

### 7.1 `scripts/dev/setup-worktree.sh`

```bash
scripts/dev/setup-worktree.sh <issue番号> <slug> [--type=feature|fix|chore] [--force-main] [--open-vscode]
```

実行内容:

1. メインが master + dirty か検証 (dirty なら `--force-main` 無しで中断)
2. `git fetch origin` で `origin/master` 最新化
3. 同 Issue 番号の worktree / 同名ブランチ既存チェック
4. `git worktree add ../high-q-volleyball-wt-<issue> -b <type>/<issue>-<slug> origin/master`
5. worktree 内で `pnpm install`
6. ポート計算 (既存 worktree 数 N から `BASE + 100*N`)
7. `--open-vscode` 指定時は worktree を新規 VS Code ウィンドウで起動 (`code -n`)
8. 起動コマンド / URL / 注意事項を整形表示

引数検証:

- Issue 番号: `^[0-9]+$`
- slug: `^[a-z0-9-]+$`
- type: `feature|fix|chore` (デフォルト `feature`)

`--open-vscode` (`--code` でも可) の挙動:

- PATH 上の `code` → `/Applications/Visual Studio Code.app/.../bin/code` → `open -na "Visual Studio Code"` の順にフォールバック
- VS Code が見つからなければ WARN を出してスキップ (worktree 作成自体は成功扱い)
- 手動で開きたい時は `code -n ../high-q-volleyball-wt-<issue>` でも可

### 7.2 `scripts/dev/teardown-worktree.sh`

```bash
scripts/dev/teardown-worktree.sh <issue番号> [--force]
```

実行内容:

1. 対象 worktree のパスを特定 (`../high-q-volleyball-wt-<issue>`)
2. ブランチ名を取得し、`origin/master` にマージされているか検証
3. 未マージかつ `--force` 無し → エラー終了 (作業損失防止)
4. `git worktree remove <path>` + ローカルブランチ削除
5. 結果サマリ表示

`--force` 時のみ未マージ削除可。マージ済みなら `git branch -d` で安全削除、強制時は `-D`。

### 7.3 `scripts/dev/dev-login.mjs` (メール送信なしログイン / #339)

```bash
SUPABASE_URL=https://<ref>.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=<dev service_role key> \
  node scripts/dev/dev-login.mjs --app <admin|reservation> [--email <addr>] [--port <n>]

# 例 (メイン worktree の reservation):
pnpm dev:login --app reservation
# 例 (wt-247 の admin ポート):
node scripts/dev/dev-login.mjs --app admin --port 5273
```

`auth.admin.generateLink` (service_role) で **メール送信ゼロ回**のログイン用 action_link を生成する。Supabase 組み込みメールの送信回数制限で dev のマジックリンクメールが詰まる問題を回避するための開発ツール。

- `--app` でアプリ切替 (callback / デフォルトポート: admin=5173 / reservation=5174)
- `--email` 省略時は owner、`--port` で worktree ポート (5173/5174 main, 5273/5274 wt-247) に対応
- **service_role キーは実行時環境変数で渡す** (`.env` 非依存、クライアントには絶対置かない)
- admin は出力リンク後に MFA 6 桁が要る / reservation は MFA 無しで完全ログイン
- redirect_to (`http://localhost:<port>/auth/callback`) が dev Supabase の Redirect URLs に登録済みであること

詳細は `.claude/skills/start-parallel-dev/SKILL.md` / `.claude/skills/verify-locally/SKILL.md`。

## 9. トラブルシューティング

### 9.1 「メインリポジトリが master + dirty」エラーで setup が止まる

メインで未コミット変更を commit / stash するか、メインも先に feature ブランチへ切り替える。どうしても続行するなら `--force-main` を付けるが、後で master に未コミット変更が残るので非推奨。

### 9.2 同 Issue 番号で worktree が既に存在するエラー

前回作業の残骸が残っている。teardown で掃除:

```bash
scripts/dev/teardown-worktree.sh <issue番号>
# 未マージで残っているなら
scripts/dev/teardown-worktree.sh <issue番号> --force
```

### 9.3 ポートが衝突する

`git worktree list` でクリーンアップ漏れの worktree を確認し teardown する。それでも衝突する場合は、別アプリ (apps/lp 等) や他プロセスが同ポートを掴んでいる可能性。`lsof -i :<port>` で確認。

### 9.4 worktree で `pnpm install` が失敗する

メインの `pnpm-lock.yaml` と worktree の状態がズレている可能性。worktree 内で:

```bash
git fetch origin && git merge origin/master
pnpm install
```

を再実行。

### 9.5 別 Claude セッションが master を握ってしまった

メイン (またはもう片方の worktree) で:

```bash
git checkout <feature-branch-name>
```

で feature ブランチへ退避。これで master は誰も握っていない状態に戻る。

# 開発ワークフロー（人間 × Claude 協働プロセス）

## 全体フロー

```
[1] 依頼           人間 → Claude に変更内容を伝える
[2] 提案           Claude が Proposal + Design + Task を同時生成
[3] レビュー・承認  人間が3ファイルを確認 → 合意の合図で次フェーズへ
[4] Apply実装      Claude が Task リスト順に TDD 実装（1タスク1コミット）
[5] ローカル確認   人間がローカル環境で動作確認 → 合意の合図で次フェーズへ
[6] PR作成         Claude が GitHub PR を作成
[7] プレビュー確認  人間が Render プレビュー環境で確認
[8] 本番デプロイ   人間が Render で master にマージ → 自動デプロイ
[9] Sync & Archive Claude が仕様を docs に反映し Change をアーカイブ
```

---

## 各ステップの詳細

### [1] 依頼

人間は自然言語で変更内容を伝える。フォーマットは不問。

> 例: 「予約キャンセル機能を追加したい。予約者本人だけが自分の予約をキャンセルできる」

### [2] 提案（Proposal + Design + Task 同時生成）

Claude は `/opsx:propose` を実行し、3ファイルを**同時に**生成して提示する。

```
openspec/changes/<change-name>/
  proposal.md   ← Why・What Changes・成功基準
  design.md     ← Domain層・UI設計・テスト設計
  tasks.md      ← 実装タスク（TDDペア含む）
```

- 3ファイルは同じセッションで連続生成する（分割しない）
- 生成後、Claude は静止して承認を待つ

### [3] レビュー・承認

人間は3ファイルを確認し、問題なければ合意の合図（「承認」「OK」「進めて」「Aで」、または `/opsx:apply` の起動など、明確に同意を示す言動）で次フェーズへ進める。

- 修正依頼があれば Claude が該当ファイルを修正して再提示する
- 合意なしに Apply 着手することは禁止（literal「承認」キーワード固執は不要）

### [4] Apply 実装

Claude は `/opsx:apply` を実行し、Task リスト順に実装する。

ルール:
- **1タスク = 1コミット**（粒度を守る）
- **TDD（テスト先行）**: composable・service はテストを先に書く
- **E2E が必要な機能では Playwright 試験コードを feature change と同じ PR で提供する**（機能あたり 1〜2 件、`docs/07-テスト/01-テスト戦略・方針.md` の「E2E スケーラビリティ運用ルール」参照）
- タスク完了ごとに `tasks.md` のチェックボックスを更新する
- タスクの順序変更・スキップは禁止
- 実装中に設計上の問題を発見した場合は**一時停止して人間に報告**する

```bash
# Apply 中の commit メッセージ形式
git commit -m "feat(events): イベント取得composableを実装 (#<issue番号>)"
```

### [5] ローカル確認（人間）

Apply 完了後、人間がローカルで確認する。

確認項目（テンプレート: `docs/templates/tasks.md` の手動テストチェックリスト参照）:
- [ ] ゴールデンパス動作確認
- [ ] エラー系確認
- [ ] モバイル表示確認

問題があれば Claude に修正を依頼。問題なければ合意の合図で PR 作成へ。

### [6] PR 作成（Claude）

Claude が `gh pr create` で PR を作成する。

```
タイトル: feat: <変更内容の概要> (#<issue番号>)
本文: Summary / Test plan / 確認済みの手動テスト結果
```

- base ブランチは `master`
- CI（lint / typecheck / test / build）が全パスすることが必須

### [7] プレビュー確認（人間）

Render の Pull Request Preview URL で確認する。

- Render 側の設定: `pullRequestPreviewsEnabled: true`（render.yaml）
- Preview URL は PR コメントに自動投稿される
- 確認後、GitHub 上で PR を Approve

### [8] 本番デプロイ（人間）

人間が GitHub 上で PR を master にマージする（Squash merge 推奨）。

- Render が master への push を検知して自動デプロイ
- デプロイ完了後、本番 URL で最終確認

デプロイが連続3回失敗した場合は CLAUDE.md の「アンチループデプロイ原則」に従って原因分析を行う。

### [9] Sync & Archive（Claude）

デプロイ確認後、Claude が以下を実施する。

1. **Spec Sync**: 実装した仕様を `openspec/specs/` および関連 `docs/` に反映
2. **Archive**: `/opsx:archive` を実行して Change をアーカイブ
3. **Issue クローズ**: `gh issue close <番号>` でGitHub Issue をクローズ

---

## 承認ゲートまとめ

| チェックポイント | 承認者 | 次のアクション |
|----------------|--------|--------------|
| Proposal + Design + Task 提示後 | 人間 | Apply 実装開始 |
| Apply 完了・ローカル確認後 | 人間 | PR 作成 |
| CI パス・プレビュー確認後 | 人間 | master マージ |

---

## ブランチ・Issue 命名規則

```bash
# Issue を先に作成
gh issue create --title "feat: イベントキャンセル機能" --label "enhancement"
# → Issue #42 が作成される

# ブランチ命名
git checkout -b feature/42-event-cancel

# PR タイトル
gh pr create --title "feat: イベントキャンセル機能 (#42)"
```

---

## コミットメッセージ規則

```
<type>(<scope>): <概要> (#<issue番号>)

types: feat / fix / refactor / test / docs / chore
scope: イベント名やモジュール名（任意）
```

例:
```
feat(events): イベントキャンセルcomposableを実装 (#42)
test(events): キャンセルcomposableのユニットテストを追加 (#42)
fix(calendar): 同名イベントのクリックが誤データを表示するバグを修正 (#104)
```

## Requirements
### Requirement: 自動アクセス可否の事前確認ゲート
システムの実装着手前に、対象サイト（江東区スポーツネット）の robots.txt および利用規約を確認し、自動アクセス（プログラムによる定期照会）が許容されることを確認 MUST する。明確に禁止されている場合は本 crawl を実装 MUST NOT とし、判断を記録する。

#### Scenario: robots.txt / 利用規約で自動アクセスが禁止
- **WHEN** robots.txt の `Disallow` または利用規約が対象パスへのプログラムアクセス・自動収集を明確に禁止している
- **THEN** 本 crawl 機能は実装せず、中止判断とその根拠を記録する

#### Scenario: 自動アクセスが許容
- **WHEN** robots.txt / 利用規約に自動アクセスを禁じる条項が無い（または対象パスが許可されている）
- **THEN** 確認結果を記録したうえで実装に進み、robots.txt に `Crawl-delay` があればその値以上の間隔で照会する

### Requirement: 土日祝・バレー可能枠の定期照会と空き検知
システムは江東区スポーツネットを一定間隔（既定 20 分）で照会し、土日祝かつバレーボール利用可能な体育室の空き枠を検知 MUST する。平日枠および対象外施設は検知対象から除外 MUST する。

#### Scenario: 土日祝の空き枠を検知
- **WHEN** 対象体育室の土曜・日曜・祝日の枠に空きが存在する
- **THEN** その空き枠（会場名 / 日付 / 開始・終了時刻 / 予約 URL）を検知結果に含める

#### Scenario: 平日枠は無視
- **WHEN** 空いている枠が平日（土日祝でない）の枠である
- **THEN** その枠は検知対象に含めない

#### Scenario: 過去日・リードタイム不足の枠は除外
- **WHEN** 空き枠の日時が過去、または現在時刻から最小リードタイム未満である
- **THEN** その枠は通知対象に含めない

### Requirement: オーナーへの空き枠通知
システムは新規に検知した空き枠を、LINE Messaging API（公式アカウントのプッシュ）でオーナーへ通知 MUST する。通知には会場名 / 日時 / 予約 URL を含め MUST、複数枠は 1 メッセージにまとめて送信 SHOULD する。

#### Scenario: 空き枠が出たら通知が届く
- **WHEN** 未通知の空き枠が検知された
- **THEN** 会場名 / 日時（曜日つき）/ 予約 URL を含む LINE メッセージがオーナーに届く

#### Scenario: 複数枠はまとめて通知
- **WHEN** 同一 crawl で複数の未通知空き枠が検知された
- **THEN** 可能な限り 1 通のメッセージに集約して送信する（無料枠の通数節約）

### Requirement: 重複通知の防止と再オープン時の再通知
システムは通知済みの空き枠を記録し、同一空き枠を繰り返し通知 MUST NOT する。ただし、いったん埋まった枠が再び空いた場合は新たな空き枠として再通知 MUST する。

#### Scenario: 同一枠は一度だけ通知
- **WHEN** ある空き枠を通知した後、次回以降の crawl で同じ枠が依然として空いている
- **THEN** その枠は再通知しない

#### Scenario: 埋まった枠が再び空いたら再通知
- **WHEN** 通知済みの枠がその後の crawl で埋まっている（空きが消えた）ことを検知し、さらに後の crawl で再び空いた
- **THEN** 通知済み記録は枠が埋まった時点で解除され、再び空いた際に新たな空き枠として再通知する

### Requirement: crawl 失敗の観測
システムは crawl の失敗（対象サイトへの到達不可 / HTTP エラー / レスポンスのパース不能）を Sentry に記録 MUST し、通知パイプラインを黙って停止 MUST NOT する。パース不能は「グリッド自体を取得できない」場合に限らず、「グリッドは取得できたが空き枠を一件も抽出できない状態が継続する」場合も含め MUST、後者を「空きが無い」と誤認して黙って 0 件を返し続けること MUST NOT する。あわせてシステムは、空き検知の各段階（読めたグリッド日数 / 絞り込み前に抽出できた生の空き枠数 / 監視対象への絞り込み後の枠数 / 通知対象の枠数）の件数を毎回観測可能な形で記録 MUST し、どの段階で 0 件に落ちたかを事後に追跡できるようにする。

#### Scenario: サイトに到達できない
- **WHEN** 対象サイトへの照会がタイムアウトまたは HTTP エラーになる
- **THEN** 失敗内容が Sentry に記録される

#### Scenario: レイアウト変化でグリッドを取得できない
- **WHEN** サイトの構造変化により空き状況グリッドそのものを一日分も読み取れない
- **THEN** パース失敗として Sentry に記録される（「空きが無い」との誤認を避ける）

#### Scenario: グリッドは取れるが空き枠を継続的に 0 件しか抽出できない
- **WHEN** 空き状況グリッド（時間帯の列・会場の行）は取得できているのに、絞り込み前の生の空き枠が継続的に 0 件しか抽出できない
- **THEN** パース不能の疑いとして異常に記録し、静かに 0 件を返し続けない

#### Scenario: 空き検知 funnel を観測できる
- **WHEN** crawl が完了する（成功・失敗を問わず）
- **THEN** 読めたグリッド日数・生の空き枠数・絞り込み後の枠数・通知対象の枠数が記録され、どの段階で件数が 0 に落ちたかを追跡できる

#### Scenario: 異常送出先が未設定でも継続的な 0 件に気づける
- **WHEN** Sentry への送出先が設定されていない環境で、空き枠が継続的に 0 件になっている
- **THEN** 送出先未設定でも継続的な 0 件を検知する手段が用意されているか、または送出先の設定が運用手順として明記されている

### Requirement: crawl コアと施設アダプタの分離
システムは施設非依存の crawl コア（スケジュール制御 / 差分検知 / 重複排除 / 通知整形 / 失敗記録 / アクセス間隔制御）と、施設固有アダプタ（照会手順・レスポンスのパース・対象体育室とバレー種目の同定）を分離 MUST し、別施設（例: Bumb）を新規アダプタの追加のみで対応可能にする。

#### Scenario: 別施設をアダプタ追加で対応
- **WHEN** 別の公的施設予約サイトを対象に追加したい
- **THEN** crawl コアを変更せず、新しい施設アダプタを追加するだけで検知・通知・重複排除が機能する

## Why

本人確認書類アップロードは「仮の行を先に作る → 画像を保存 → 保存パスを本確定に UPDATE」の 3 段階で動く。最後の確定 UPDATE が失敗すると、行は仮パスのまま・画像実体は保存済みという食い違いが残り、管理画面で「画像を取得できませんでした」となる。実際に商用で同一会員の 3 件がこの状態で滞留した (実体は健在だったため手動でパスを貼り直して復旧済み)。確定 UPDATE を廃止すれば、この失敗モード自体が構造的に消える。

## What Changes

- アップロード手順から「保存後にパスを本確定する UPDATE」ステップを廃止する
- 行を作成する時点で最終的な保存パスを確定させ、画像保存が成功すれば追加の DB 更新なしで完了する構造にする
- 画像保存が失敗したときだけ、作成した行と保存済み画像を撤去する (従来どおりのロールバック)
- 「保存は成功したが確定 UPDATE だけ失敗し、仮パスの行が残る」という失敗モードと、それに対応するエラー種別を廃止する **BREAKING**（spec レベルの手順・シナリオが変わる）
- 再発を止めたことを保証する回帰テストを追加する

## Capabilities

### New Capabilities

（なし）

### Modified Capabilities

- `reservation-identity-document-upload`: アップロードの手順（行作成 → 画像保存 → パス確定 UPDATE の順序）と、確定 UPDATE 失敗時の残留挙動を規定した要件を変更する。確定 UPDATE ステップを廃し、行作成時点でパスを確定する手順へ改める。

## Impact

- `apps/reservation` の本人確認書類アップロード機能（アップロードを統括する composable と、DB / Storage への入出力を担う client）
- DB スキーマ・RLS・Storage バケット構成は変更なし（保存パスの命名規則も従来どおり）
- 管理画面・通知 Edge Function への影響なし（読み取り側は保存パスをそのまま使うだけ）
- 商用で滞留していた 3 件は復旧済みのため、本変更はデータ移行を含まず、再発防止のみを対象とする

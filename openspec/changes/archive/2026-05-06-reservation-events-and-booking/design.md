## Context

会員サイトの「探す」体験を整える局面。前段の認証・プロフィール作成 (#89) でログイン済み会員が成立する状態は揃っている。後段の予約成立 (#91) はまだ未実装で、本 change はその間に位置する「イベントを見る」までを担う。

技術判断の中心テーマは 3 つに絞られる:

1. 後続 #91 との境界をどこで切ると、両 Issue が独立して着手・マージできるか
2. MVP1 で扱える情報がイベント名・開催日時・会場・参加費の 4 項目しかない前提で、データ取得構成をどこまで簡素化できるか
3. ミニマム情報量の詳細画面に存在意義を持たせる差分要素は何か

### 関連既存仕様の確認

本 change の起票前に以下の spec を確認し、MVP1 でスコープアウトされている機能項目を全件抽出した:

- `admin-events-crud` — 定員 / 紹介文 / サムネイル画像 / キャンセル期限 / 公開状態切替 UI のすべてが MVP1 ではフォームに含まれず、対応する DB 列は NULL のまま残される。`visibility` は INSERT 時に常に「公開」固定で投入される
- `admin-events-list` / `admin-event-detail` — 中止 / 終了ステータスの切替 UI は MVP1 で提供されない。残席バーは admin 側でも実質非描画

→ この前提下で、会員サイトが扱える情報は「イベント名・開催日時・会場・参加費」の 4 項目に純化する。本 change の design はこの 4 項目を前提に組み立てる。

### 関連既存仕様（実装パターンの参照元）

- 会員サイトの認証・プロフィール完成判定（#89 で確立済）
- イベント・会場のデータモデル（venues は名前と住所を持つ）
- 管理画面のイベント一覧・詳細実装（UI / データ取得方式の参照元）

### 制約

- 既存テーブル・既存 RLS は変更しない
- 新規 DB 列を追加しない
- 新規パッケージ依存を追加しない（紹介文・写真がスコープオフのため Markdown / サニタイズライブラリ不要）
- 会員サイトのみの変更につき、Render の PR Preview は生成されない（動作確認はローカル）

## Goals / Non-Goals

**Goals:**

- 会員が「いつ・どこで・いくら」のイベントを開催日順に把握できる
- 詳細画面でイベント名・開催日時・会場（名 + 住所）・参加費を確認できる
- 詳細画面に予約導線の入口（「予約に進む」ボタン）を配置し、後続 #91 が接続できる準備状態を作る
- 4 状態 UI、双方向パンくず、アクセシビリティ AA、デザイントークン徹底使用

**Non-Goals:**

- 予約フォーム入力・予約確認・予約完了処理（#91）
- ニックネーム表示への切替（#200）
- プロフィール編集（#148）
- 紹介文 / 写真 / キャンセル期限 / 定員 / 残席表示 / 中止表示（MVP1 全体スコープアウト）
- イベント詳細 Variation B / 3 ステップ進捗バー化（MVP2）

## Decisions

### D1: 後続 #91 との境界は「予約に進むボタンの描画」で切る

詳細画面に「予約に進む」ボタンを置くが、本 change では **押下時の遷移先 (#91 が実装する確認画面) はまだルート登録されていない**。ボタンは描画するがクリック時の挙動は #91 マージ時に有効化する形を取る。

選択肢を比較:

- **案 A: ボタン非表示にし、#91 マージ時にボタン追加**: 詳細画面が #91 直前まで予約導線のないままになり、デザイン上の完成度が低い
- **案 B: ボタンを描画し、押下時に「準備中」のトーストを表示**: ユーザーは「予約機能はあるが整備中」と認識でき、デザイン的にも自然
- **案 C: ボタンを描画し、ダミーのプレースホルダ画面に遷移させる**: 案 B との UX 差はほぼなく、ルート定義の負担が増える

→ **案 B を採用**。本 change ではボタンの存在と「準備中」案内の出力までを担い、実遷移は #91 でクリックハンドラを差し替える。両 Issue が独立して着手・マージ可能になる。

### D2: 既存テーブルを直接読む（新規 SQL ビュー新設なし）

定員・残席表示がスコープアウトされているため、会員サイト側で予約数を集計する必要がない。既存の管理画面用 DTO ビューも呼ばず、会員サイトはイベント・会場テーブルを直接読み、アプリ層で「公開済み・開催予定」の条件を絞り込むシンプルな構成にする。

選択肢を比較:

- **案 A: 公開イベント専用の DTO ビューを新設**: 集計列が不要なので過剰
- **案 B: 既存の管理画面用ビューを呼ぶ**: 集計列を取得しても会員視点では使わないため、無駄な依存になる
- **案 C: イベント・会場テーブルを直接読み、アプリ層で公開フィルタ**: 採用。新規 SQL なし、最小構成。将来定員機能を入れるとき改めてビュー設計を行えばよい

→ **案 C を採用**。

### D3: ミニマル詳細画面の差分要素として「会場住所」を加える

詳細画面と一覧カードの情報差分が薄いと、ユーザーには「タップしたのに同じ情報しか出てこない」体験になる。詳細画面の存在意義を担保するため、一覧カードには出さず詳細画面でのみ出す情報として **会場住所** を加える。

選択肢を比較:

- **案 A: 詳細画面に会場住所を加え、一覧は会場名のみ**: 採用。詳細を見る価値が「行けるかどうか判断するための住所情報」として明確になる
- **案 B: 詳細画面を廃止し、一覧カードに住所まで全部のせる**: カード密度が高くなりすぎる、誤タップで予約導線に入るリスクがある
- **案 C: 地図埋め込み・アクセス情報まで詳細に加える**: 本 change のスコープを膨らませる。詳細充実化は別 Issue で別途計画

→ **案 A を採用**。venues テーブルの `address` 列を詳細画面でのみ表示する。`access_note` / `map_url` 等の追加情報は別 Issue で詳細充実化する際に検討する。

### D4: ホーム画面の役割を「ログイン後の最初の体験」としてイベント一覧に切り替える

会員ログイン直後のトップ URL は現在「準備中」プレースホルダに到達するが、本 change のリリースでイベント一覧に到達するよう切り替える。これは #89 の proposal で「後続 #90 でイベント一覧に置き換え」と既に予告されており、本 change で約束を果たすタイミング。

「準備中」プレースホルダ画面は削除する。ログアウトボタンはイベント一覧画面のヘッダ右上に移植する（管理画面と同じパターン）。

### D5: パンくず第 1 セグメントは「マイページ」とし、独立ウィジェットで実装する

会員サイト全画面に共通するナビゲーション要素として、パンくずを独立ウィジェットで持つ。第 1 セグメントの文言は **「マイページ」**（翔太郎くん指示）とする。会員視点で「自分のための領域」が明示され、admin の「Workspace」表現とも区別される。

実装は会員サイト側で新規実装し、管理画面の同名ウィジェットとは別物として並存させる（共通化の設計コストが本 change への負荷より大きいため、共通化は将来別 Issue とする）。

パンくずの第 1 セグメント「マイページ」は押下でイベント一覧へ戻る動作とする。これにより、各画面から上位画面への戻り経路が常に存在し、双方向性ルールが満たされる。

## Risks / Trade-offs

- **[Risk] 「予約に進む」ボタン押下時の "準備中" 表示が長期化する** → Mitigation: #91 を本 change マージ後に即時着手し、穴の期間を短縮する。商用リリースは両アプリ完成後の本番デプロイ Issue で揃える運用なので、「準備中」状態が本番ユーザーに見えることはない
- **[Risk] 詳細画面の情報量が少なく「タップする意味がない」と感じられる** → Mitigation: 一覧には出さず詳細でのみ出す **会場住所** を差分情報として配置することで、詳細を見る価値を担保する。地図・アクセス情報等の更なる充実は別 Issue で計画
- **[Trade-off] パンくずウィジェットの将来的な重複コスト** → Mitigation: 受容。共通化は将来別 Issue

## Migration Plan

- DB マイグレーションなし
- 既存「準備中」プレースホルダ画面の削除を伴うが、ホーム URL 自体はイベント一覧へリダイレクトされるため、ユーザーの URL ブックマークは引き続き有効
- ロールバックは PR revert で完結（DB 状態への副作用なし）

## Context

会員予約サイト (`apps/reservation`) は、キャンセル済予約 (`status='cancelled'`) と同一イベントへ再予約する際、予約 Sheet（create モード）の確定経路で UNIQUE 制約違反を検知して既存行を再活性化する仕組みを既に持つ。一方で「キャンセルした会員がその経路へたどり着く導線」は欠けている。

現状の前提を実装で確認した結果、以下が判明している:

- 履歴画面 (`/history`) は「予約中」「過去」の 2 グループ構成で、**「キャンセル済」専用グループは存在しない**。キャンセル済予約は参加済・no_show などと混在して「過去」グループに `start_at` 降順で並ぶ。キャンセルした **未来イベント** も「過去」グループに埋もれる。
- 予約完了画面 (`booking-done`) でのキャンセル成功後は無条件でイベント一覧へ遷移し、再予約導線が失われる。一方、履歴・予約詳細経由のキャンセル後は `/history` に留まる / 戻るため、履歴側に導線を置けば自動的にカバーされる。
- 再活性化による予約成立時の確認メールは、create 経路が INSERT / 再活性化を問わず `confirmed` 通知を発火するため**既に再送される**。

## Goals / Non-Goals

**Goals:**

- 再び受付可能なキャンセル済予約を履歴画面で前面化し、1 タップで再予約 Sheet に到達できる導線を提供する
- 完了画面でのキャンセル直後、受付可能なイベントに限り再予約導線を提示し、誤キャンセル・心変わりからの復帰摩擦を下げる
- 2 経路を単一の「イベント詳細起点で create Sheet を開く」仕組みに集約し、UI ロジックの重複を避ける

**Non-Goals:**

- DB スキーマ / RLS / Edge Function / メール送信ロジックの変更（既存の再活性化 UPDATE と通知をそのまま流用）
- キャンセル待ち管理 (#154)・通知設定からの再予約レコメンド (#157)・キャンセル理由分析
- 履歴・予約詳細経由キャンセル後への専用「やっぱり予約する」UI 追加（履歴の再予約導線で着地点をカバーするため不要）

## Decisions

### Decision 1: 再予約への共通着地点をイベント詳細のディープリンクに集約する

履歴の「再予約する」と完了画面の「やっぱり予約する」は、どちらも「イベント詳細を開き、create モードの予約 Sheet を立ち上げる」という同一の終着点を持つ。これを各画面で個別に実装せず、**イベント詳細画面がクエリパラメータで予約 Sheet 自動起動を受け付ける**入口に一本化する。

- イベント詳細画面はマウント時に所定のクエリを検知し、対象イベントが**受付可能なときに限り** create モードの予約 Sheet を自動オープンする
- 再オープンの再発火（ブラウザ戻る等）を防ぐため、自動オープン後はクエリを履歴から除去する
- 受付不可（受付終了 / 満席）のイベントへのディープリンクでは Sheet を開かず、通常のイベント詳細（締切表示）を見せる

**Why**: 着地点を 1 箇所に集約することで、再予約導線を増設しても Sheet 起動ロジックが分散しない。既存の予約 Sheet・受付可否判定・localStorage 復元をそのまま再利用できる。

**Alternative（不採用）**: 各画面に予約 Sheet を直接マウントする → Sheet とその状態管理が複数画面に重複し、受付可否ガードの実装も分散する。

### Decision 2: 「キャンセル済み」グループを履歴のグループ分割に新設する

履歴のグループ分割を 2 → 3 グループに拡張する。新グループ「キャンセル済み」は **`status === 'cancelled'` の予約すべて**（受付可否を問わず）を集め、過去グループから分離する。

- 過去グループは、キャンセル済みへ移った行を**除外**する（同一行を二重掲載しない）。過去グループに残るのは `attended` / `no_show` / `waitlist` / `reserved`（過去・不整合）に限られる
- 表示順は「予約中 → キャンセル済み → 過去」とする
- キャンセル済みグループ内の並びは、**受付可能（再予約可）な行を先頭に `start_at ASC`、続いて受付不可な行を `start_at DESC`** とし、再予約できる予約を上に前面化する
- 「再予約する」CTA は **受付可能な行のみ** に表示し、受付終了・満席の行には CTA を出さない（Issue 完了条件「終了・受付終了済は CTA が出ない or 非活性」に対応）

**Why**: ユーザー選択。キャンセルした予約を 1 セクションに集約しつつ（キャンセルした未来イベントが「過去」に降順で埋もれる既存の癖を解消）、再受付可能なものだけ行動喚起の文脈で前面化し再予約導線を持たせる。

**Alternative（不採用）**: 受付可能なキャンセルのみを集める「再予約可」グループ → キャンセル済予約が「キャンセル済み」と「過去」に分散し、セクション名と内容が不整合になる。

### Decision 3: 「再予約する」CTA 表示可否の述語は「未開催 かつ 非満席」を採用する

キャンセル済み行に「再予約する」CTA を出すか否かは、新規予約と同じ受付可否基準に揃える。すなわち「イベントが未開催（`start_at > now`）かつ 非満席」のときのみ CTA を出す。

- 満席判定は既存の `formatAvailability(availability).isFull` を流用する
- キャンセル可能期限（前日中）の `isCancellable` ではなく、新規予約と同じ「未開催」を採用する。再予約は新規予約と等価であり、キャンセル期限とは別概念のため
- 同述語はキャンセル済みグループ内の並び順（受付可能を先頭に出す）にも流用する

**Why**: 再予約は実質的に新規予約であり、イベント詳細の予約 CTA（締切時に「予約締切」へ切替）と挙動を一致させるのが一貫している。

### Decision 4: 完了画面はキャンセル後、受付可能時のみ遷移挙動を分岐する

完了画面でのキャンセル成功時、対象イベントが受付可能なら**イベント一覧へ遷移せず**、完了画面上に「やっぱり予約する」導線を含む結果表示へ切り替える。受付不可なら従来どおりイベント一覧へ遷移する。

- 「やっぱり予約する」は Decision 1 のディープリンクでイベント詳細へ遷移し、create Sheet を自動オープンする
- 結果表示には「イベント一覧へ」の退出導線も併存させる

**Why**: 完了画面経由のキャンセルだけが、キャンセル後に再予約導線を持つ着地点（履歴行など）へ自然に戻らない唯一の経路。ここだけ補えば 2 経路で漏れがなくなる。

### Decision 5: メール再送は既存挙動に委ね、本変更で触らない

再活性化での予約成立は create 経路を通り、既存の `confirmed` 通知がそのまま発火する。完了条件「予約完了メールが再送される」は現状で満たされるため、本変更ではメール経路に一切手を入れない。component test で「再活性化成功時に通知が発火する」既存挙動を回帰確認するに留める。

## Risks / Trade-offs

- **[受付可否のレース] 導線描画時は受付可能でも、タップ到達時に満席化している可能性** → ディープリンク先のイベント詳細がマウント時に受付可否を再判定し、不可なら Sheet を開かず締切表示を見せる。既存の予約確定経路も capacity 超過を弾くため二重防衛となる。
- **[二重メール] キャンセル直後に再予約すると `cancelled` と `confirmed` の 2 通が連続送信される** → 事実に忠実な挙動であり許容。抑制は過剰最適化のため行わない。
- **[グループ分割変更の波及] `splitReservations` を 2→3 グループに変えると統計・他参照箇所に影響しうる** → 統計 (`computeHistoryStats`) は `splitReservations` ではなく生配列を参照するため独立。分割関数の変更は履歴グループ描画のみに閉じることを実装時に確認する。
- **[受付可否述語の二重定義] 満席・未開催判定が既存ヘルパと重複する懸念** → 満席は既存 `formatAvailability` を流用し、新規述語は「cancelled かつ 未開催 かつ 非満席」の合成のみを担う薄い純関数とする。

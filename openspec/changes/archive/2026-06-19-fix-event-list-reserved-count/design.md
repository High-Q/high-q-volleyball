## Context

admin の一覧用ビューと、詳細・会員向けビューの間で残席集計の定義が分岐している。後者2つは「本人＋同伴の人数」「予約中＋チェックイン済みを母集団とする」という同一ロジックに既に統一されているが、一覧用ビューだけが旧来の「予約件数（同伴を数えない）」「予約中のみ」のまま取り残されている。一覧テーブルは残席バーへこの値をそのまま渡すため、残席が過大に見え、チェックインで一覧の数字が減るという二重バグになっている。

詳細・会員向けビューには既に「同伴含む人数」「チェックインで減らない」「会員向けと admin で同値」といった集計同値性の要件・シナリオが整備されている。本変更はそれらの既存定義を一覧用ビューにも適用する、いわば集計ロジックの一本化である。

## Goals / Non-Goals

**Goals:**

- 一覧用ビューの残席集計を、詳細・会員向けビューと文字どおり同一の定義に揃える
- 同伴者を含む正しい残席が一覧で表示され、チェックイン後も一覧の数字が減らないようにする
- 一覧テーブルの単位表記を、値の意味（人数）と整合させる

**Non-Goals:**

- 残席バーコンポーネント・型定義・RLS・テーブル権限の構造変更はしない（列名・列構成は不変）
- 詳細・会員向けビューや予約フローの挙動変更はしない
- waitlist など MVP1 でスコープオフの集計列の新設はしない

## Decisions

**決定1: 一覧用ビューを canonical 集計式へ差し替える（既存式の流用）。**
詳細・会員向けビューが共有する集計式をそのまま一覧用ビューの集計サブクエリへ適用する。独自の中間表現や共通関数の新設はしない。理由は、すでに2つのビューで実証済みの式をコピーするのが最も低リスクで、3ビュー間の「同値であるべき」という spec 要件を満たす最短経路だから。共通の SQL 関数へ括り出す案も検討したが、ビュー定義のインライン式が3箇所で完全一致していれば spec の同値性シナリオで担保でき、関数化は今回のスコープに対して過剰と判断した。

**決定2: ビューはインプレース再定義（列構成は不変）。**
列名・列順・型・セキュリティ属性を一切変えずに集計サブクエリの中身だけ差し替える。型契約（一覧 row DTO）は変わらないため TypeScript 型定義の変更は不要。残席バーへ渡す値の「意味」だけが件数→人数に変わる。

**決定3: 単位表記の修正は定員未設定分岐のみ。**
定員ありのイベントは残席バーが「残 N / 定員」を表示するため単位の見え方は変わらない。定員未設定イベントだけが値を素のテキストで表示しており、その単位が件数前提になっているため、人数前提の単位へ直す。表示ロジックそのもの（どの分岐で何を出すか）は変えない。

## Risks / Trade-offs

- [集計式の3ビュー間ドリフト再発] → spec に「3ビューで同一集計ロジックを共有する」旨を明記し、集計シナリオを人数ベースで揃える。将来いずれかを変える際は3つ同時に見直す前提を残す。
- [既存テストの期待値が件数前提のまま緑になっている] → 一覧テーブルと関連 fixture の期待値を人数ベースへ更新し、修正が表示に効いていることをテストで固定する。
- [本番ビュー再定義のリスク] → ビューは `create or replace` でインプレース更新。テーブル・データ・権限に触れないため影響は表示値のみ。rollback は旧定義への `create or replace` 差し戻しで完結（migration にロールバック手順コメントを残す）。

## Migration Plan

1. 一覧用ビューを canonical 集計式で再定義する migration を追加（インプレース、列構成不変、セキュリティ属性維持）
2. data-schema spec の一覧用ビュー要件本文・集計シナリオを人数ベースへ MODIFIED
3. 一覧テーブルの単位表記修正と関連テストの期待値更新
4. dev DB へ適用して一覧表示を確認 → PR → 本番反映

rollback: 直前の旧ビュー定義を `create or replace` で再適用すれば表示は元の件数ベースへ戻る（データ移行を伴わない）。

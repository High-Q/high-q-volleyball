## Context

Issue #200 は会員サイトのアイデンティティ表現にニックネームを導入する。現状、会員サイト上で会員自身の名前を表示している箇所は存在せず、会員エンティティが持つ自己呼称も氏名のみである。後続 Issue（プロフィール編集 / 履歴 / 予約サマリ強化）で会員自身の名前を画面に出していくときに、各画面が機械的にニックネーム優先で描画できる土台を本 change で先に整える。

ステークホルダーは PO 兼開発者（翔太郎くん）、想定利用者は MVP1 期間中の会員 1 名（同一人物）であり、本番リリース後にサークル参加メンバーが順次拡大する想定。Phase 移行・dev/prd 分離方針 (`docs/08-移行/01-環境戦略・本番リリース計画.md`) は本 change のスコープには影響しない（dev のみへの migration 適用で完結）。

## Goals / Non-Goals

**Goals:**

- 会員エンティティに任意のニックネーム属性を追加し、文字種・文字数の妥当性を DB 制約とアプリ層バリデーションの二重で担保する
- 会員登録フォーム段階 2 で任意入力欄を提供する（空欄送信を許容、必須マークを付けない）
- 「ニックネームがあればニックネーム、なければ氏名」を会員視点表示の正準ルールとして spec に固定する
- 既存 dev 環境の会員 1 名に対し migration で初期値を投入し、開発時に手動操作なしで動作確認できる状態を作る

**Non-Goals:**

- ニックネームの**変更 / 削除 UI**（後続 #148 で対応）
- ニックネームの**一意性チェック**（同名 OK の運用）
- 管理画面の表示変更（admin は氏名表示のまま）
- 会員サイトの既存ページでの実際の表示切替（現状切替対象画面が 0 件のため、本 change 内では UI に手を入れない）
- ニックネーム以外のプロフィール属性追加（自己紹介文 / Avatar 等）

## Decisions

### D1. 任意属性 + 空欄許容、未設定時は氏名 fallback

ニックネームは任意項目とし、入力なしでの登録完了を許容する。会員視点の名前表示は「ニックネームがあればニックネーム、なければ氏名」を正準ルールとする。

- **検討した代替案**: 必須化案（全会員必ずニックネームを持つ）
- **不採用理由**: Issue #200 が任意項目として明示しており、PO 確認でも「ニックネームを設定しない人は氏名で利用してもらう」方針が確定した（2026-05-07）。MVP1 期間中の会員数が極小であり、必須化による登録摩擦のほうがデメリットが大きい
- **トレードオフ**: 「氏名は会員サイトには出さない」というドメインルールは存在しない前提で運用する。将来氏名秘匿の要望が出た場合は後続 Issue でニックネーム必須化を再検討する

### D2. 文字種制約は DB CHECK + アプリ層バリデーションの二重で持つ

ニックネームの文字種（日本語 + 英字のみ、絵文字・数字・記号は不可）と文字数（1〜15 文字）を DB の CHECK 制約で強制し、同じ規則をアプリ層の Smart constructor でも検証する。

- **検討した代替案**: アプリ層のみ / DB のみ
- **不採用理由**:
  - アプリ層のみ: admin が DB を直接操作する可能性があり、admin 経由の不正値混入を防げない
  - DB のみ: クライアント側でリアルタイムにエラーを返せず、ユーザー体験が劣化する（API 往復後にしかエラーがわからない）
- **トレードオフ**: 同じルールを 2 箇所で表現するため、変更時には両方を同時に更新する規律が必要。将来制約を緩める / 厳しくする際は migration とアプリコードを同一 PR に含める運用とする

### D3. 文字種の正規表現定義

「日本語 + 英字のみ」をひらがな・カタカナ・漢字（CJK 統合漢字基本ブロック）+ 半角英字 ASCII の和集合として定義する。具体的な文字範囲は tasks.md 側で固定する。

- **検討した代替案**: Unicode カテゴリベース（`\p{L}+`）/ 漢字を CJK 拡張ブロックまで含める / 全角英字も許可
- **不採用理由**:
  - `\p{L}` 系は絵文字や記号系の一部を文字としてマッチしてしまうケースがあり、Issue #200 の「絵文字・数字・記号禁止」を厳密に満たしにくい
  - CJK 拡張ブロックは MVP1 の現実的な日本人会員には不要で、過剰許容の余地を作る
  - 全角英字の許可は半角と区別がつきにくく表示揺らぎを招く
- **トレードオフ**: 旧字体・人名漢字の一部が CJK 統合漢字基本ブロック外に存在する場合、入力できないニックネームが出る可能性がある。MVP1 では会員数が極小で実害がないと判断。後続で要望が出た時点で範囲拡張する

### D4. UI 上の任意表示

入力欄ラベルには必須マーク `*` を付けず、ヒント文で「未入力時は氏名で表示されます」を併記する。プロジェクト UI 規約「初期表示で赤枠を出さない」「必須マークは使わずラベル表記」（`docs/05-インターフェース/01-UI設計方針.md`）に従う。

- **検討した代替案**: ラベルに「(任意)」を付ける / 説明文を出さない
- **不採用理由**: ラベルに「(任意)」を付けると他の必須項目との対比でラベル表記が揺らぐ。説明文なしだと「未設定だと何が起きるか」が会員に伝わらず、後で混乱を生む
- **トレードオフ**: ヒント文を 1 行追加することでフォームが縦に伸びる。UI 規約上ヒント文は許容されているため受容

### D5. 既存 dev 会員への初期値投入は migration で実施

migration 内で `nickname='たろ'` を翔太郎くん 1 名に UPDATE する。本番環境では当該行が存在しないため副作用なし、dev 環境では migration 適用と同時に動作確認可能な状態が作られる。

- **検討した代替案**: 初期値投入を migration ではなく seed スクリプト / 手動操作で行う
- **不採用理由**: 初期値投入を migration に含めることで「dev DB を再構築すればテスト用ニックネームが必ず存在する」状態が再現可能になり、後続テストや動作確認の手間が消える。本番 DB に対しては該当行が無いため UPDATE が 0 件にしかならず、安全性に問題はない
- **トレードオフ**: migration 内に「特定 1 行への UPDATE」が混ざるためデータ操作と DDL の分離原則からは逸脱する。MVP1 の dev のみ運用フェーズという特殊性で受容し、本番 Supabase 作成時の初期データ投入は別 Issue で seed として扱う

### D6. 会員視点表示ルールは spec に固定し、本 change では UI 切替を行わない

「ニックネームがあればニックネーム、なければ氏名」というルールを `reservation-member-auth` capability の MODIFIED Requirement として固定する。本 change 内では会員視点で名前を表示する画面が存在しないため UI コード変更は行わず、後続 Issue（#148 / 履歴 / 予約サマリ強化）で各画面が本ルールを参照する形で漸進実装する。

- **検討した代替案**: 既存ページに preemptive にルール適用箇所を作る / data attribute 等で保持しておく
- **不採用理由**: 表示対象が無い状態で UI コードに名前表示ロジックを埋めると「使われないコード」が残り、後で改修時に文脈を失う。spec に規約として固定するほうが将来の Issue の判断材料として強い
- **トレードオフ**: 後続 Issue 実装者がルールを忘れる懸念があるため、spec に明確な scenario として残し、後続 Issue の Design レビューで本 spec への参照を必須化する

## Risks / Trade-offs

- **リスク**: 既存 dev 会員への初期値投入を含む migration がローカル環境で繰り返し適用される際、二重 UPDATE になっても冪等であることを保証する必要がある
  → **緩和**: UPDATE は条件節で「ニックネームが NULL の行のみ」を対象にする。再適用時は 0 行 UPDATE で安全に終了する
- **リスク**: 後続 Issue 実装者が「ニックネームがあればニックネーム、なければ氏名」ルールを参照せず、各画面で独自に氏名直書きしてしまう
  → **緩和**: ルールを `reservation-member-auth` の Requirement として明示的に scenario 付きで固定し、後続 Issue の Design レビューで「member 名表示箇所がある場合、本 Requirement に従っているか」を確認項目とする
- **リスク**: アプリ層と DB の文字種制約の表現が将来ズレる
  → **緩和**: tasks.md 内で「両者を同一 PR で更新する」を運用ルールとして残し、Apply 時のテストで両者が同じ正常 / 異常パターンに反応することを担保する

## Migration Plan

1. dev Supabase へ列追加 + CHECK 制約 + 初期値投入の migration を適用する
2. アプリ層（会員エンティティ・Smart constructor・取得 / 更新ロジック・登録フォーム）を実装し、テストで両者の整合を確認する
3. ローカル `pnpm --filter @high-q/reservation dev` でフォーム動作・既存ニックネーム表示準備（API レスポンスへの含有）を確認する
4. PR を作成。`apps/reservation` のみの変更ではないが（DB migration を含むため）、会員サイト UI の動作確認は Render Preview ではなくローカル起動で行う運用とする

ロールバック: migration を逆向き migration（DROP COLUMN）で取り消し可能。ニックネーム列の DROP は他テーブルから参照されないため安全。

## Context

LP のイベント一覧は既に Supabase の `events` テーブルを直接参照しており（AWS からの移行は完了済み）、`events.capacity`（定員）は anon でも読める。しかし残席の核心である「予約数の集計」は `event_availability_view`（集計のみ・個人情報なし）に集約され、現状は authenticated 限定で、`rls-policies` spec が「LP / anon は呼ぶな」と契約で禁じている。この禁止は個人情報保護のためではなく、MVP1 で anon 向け集計経路を作らなかったというスコープの線引きである。

予約サイト（apps/reservation）は同じ view を使い、「あと N 名 募集」「満員」という残席表現を既に持つ。LP でもこの表現を統一して出すのが今回のゴール。

制約:
- LP は `#310` 完了まで FSD 機械検知の対象外だが、FSD 構造（entities / widgets / pages / shared）には従う。
- LP は Vuetify ではなく `@high-q/ui` + Tailwind preset + デザイントークン。
- 集計の真実の源を二重化しない（予約サイト・admin と同じ式を共有する）。

## Goals / Non-Goals

**Goals:**
- LP の各イベントに「あと N 名 募集」「満員」「N 名 予約中」（無制限時）を予約サイトと完全統一した文言・トーンで表示する。
- 残席集計を anon に公開する（個人情報を含まない集計に限る）。集計の真実の源は単一に保つ。
- 残席取得の失敗をイベント表示全体の失敗から切り離す（残席だけ伏せて一覧は出す）。

**Non-Goals:**
- リアルタイム更新（WebSocket 等）。取得時点のスナップショットで十分。
- LP でのキャンセル待ち人数の表示（待ち人数は会員向け情報。LP は「満員」までに留める）。
- 予約サイト側の残席表現の変更。
- LP でのキャンセル待ち人数の表示（待ち人数は会員向け情報）。
- 集計ビューの定義・集計式そのものの変更。
- DynamoDB / AWS リソースの停止判断。

## Decisions

### 決定1: 既存ビューを anon に開放し、新ビューは作らない

`event_availability_view` に anon の SELECT 権限を付与し、`rls-policies` spec の「LP / anon 禁止」契約を「個人情報を含まない集計に限り anon も可」に改訂する。

- **理由**: ビューは `(event_id, capacity, reserved_count)` の集計のみで、個別予約行・予約者 ID 等の個人情報を構造的に含まない。anon に開いても漏れるのは集計値だけで、これはまさに LP に出したい情報そのもの。集計式は `#319` で予約・admin・一覧の3経路を canonical に統一済みであり、ここに anon 用の別ビューを足すと式が二重化し、ずれの温床になる。
- **代替案**: anon 専用の別ビューを新設して多層防御を維持する案。集計ロジックが二重化し DRY を損なうため棄却。残席という同一概念に2つの真実の源を持つことの保守コストが、多層防御の利点を上回る。

### 決定2: 残席は events とは別クエリで取得し、クライアントで突き合わせる

LP は既存のイベント取得（events テーブル）に加え、表示対象イベント ID 群に対する残席集計をビューから取得し、ID をキーにクライアントで結合する。予約サイトの残席マップ取得（ID 配列 → 集計）と同じ構造を踏襲する。

- **理由**: events の取得クエリは確立済みで触りたくない。ビューは event_id キーの集計で、PostgREST の埋め込み結合に頼るより ID 突き合わせの方が確実かつ単純。取得は TanStack Query でキャッシュする。
- **代替案**: events クエリにビューを埋め込み結合する案。ビュー埋め込みは関係検出に依存し脆いため棄却。

### 決定3: 残席表現ロジックは予約サイトの規則に完全準拠する（LP 固有分岐なし）

表示文言・トーン・満員判定は予約サイトの残席表現規則に完全準拠する: 募集中「あと N 名 募集」、満員「満員」、無制限「N 名 予約中」、「席」表記禁止、80% 以上で警告トーン。LP 固有の分岐は設けない。

- **理由**: 「N 名 予約中」は予約者数の集計であって個人を特定する情報ではなく（誰が予約したかは出ない）、anon に出してもプライバシー上の問題はない。むしろ無制限イベントの賑わいを示すソーシャルプルーフとして集客に効く。当初は無制限のみ伏せる案だったが、予約者数の人数表示を「個人情報の露出」とみなすのは過剰で、表現を完全に揃える方が一貫性・保守性ともに優れる。
- **共通化の扱い**: 規則が完全一致するため共通パッケージ化が自然だが、apps 間共有は `packages/shared` 等への移設を伴いスコープが広がる。本変更では LP 配下に予約サイトと同じ規則を写したロジックを置くに留め、共通パッケージ化は別 Issue とする（過剰な抽象化を本変更に持ち込まない）。

### 決定4: 満員イベントの CTA は遷移を維持しつつ文言で誤解を防ぐ

満員イベントでも予約サイト（キャンセル待ち登録が可能）への遷移は維持する。ただし CTA 文言は満員時にキャンセル待ちへ向かうことが分かる表現に切り替え、「予約する」のまま満員へ送る誤解を防ぐ。

- **理由**: 予約サイトにキャンセル待ち登録機能が既にあるため、満員でも遷移に価値がある。文言だけ誠実にする。

### 決定5: 残席取得失敗時はグレースフルに劣化させる

残席集計の取得が失敗したイベントは、残席表現を伏せてイベント本体（日付・名前・会場・CTA）は通常どおり表示する。残席の欠如で一覧全体を Error 状態にしない。

- **理由**: 残席は付加情報であり、欠けてもイベント告知という LP の主目的は果たせる。一覧全体を落とす方がユーザー損失が大きい。

## Risks / Trade-offs

- **集計値が anon に見える** → 受容。ビューは集計のみで個人情報を含まず、これは公開意図そのもの。spec に「anon に公開してよいのは個人情報を含まない集計に限る」と明記し、将来ビューに列を足す際の歯止めとする。
- **LP と予約サイトで残席ロジックが二重化（無制限分岐の差異）** → 文言・満員判定の規則出所を spec で一本化し、両アプリのテストで同一入力に対する表示を固定。共通化は別 Issue として明示的に残す。
- **残席のスナップショットが古くなる** → TanStack Query の再取得（フォーカス時等）で許容範囲に収める。リアルタイム性は Non-Goal。
- **ビュー GRANT 変更の本番反映漏れ** → migration として明示し、ロールバック手順（権限の revoke）をコメントで残す。dev → prd は CI の apply 承認ゲート経由で適用する。

## Migration Plan

1. `event_availability_view` に anon の SELECT 権限を付与する migration を追加（ロールバック: anon からの revoke をコメントで明記）。新規テーブルではなく既存ビューへの権限変更のため、テーブル作成や RLS 新設は伴わない。
2. dev に適用して LP（anon）から残席が取得できることを確認。
3. PR マージ後、prd-db-push の承認ゲートを通して prd に適用。LP・予約サイトが同一プロジェクトの同一ビューを参照するため、適用は1回で両アプリに反映される。
4. ロールバックは anon への GRANT を revoke すれば、残席は LP 側のグレースフル劣化（残席非表示）に戻り、イベント告知自体は継続する。

## Open Questions

- 満員時の CTA 文言（「キャンセル待ちへ」等）の最終文言は Apply 時の UI レビューで確定する。挙動（遷移維持）は本 design で確定済み。

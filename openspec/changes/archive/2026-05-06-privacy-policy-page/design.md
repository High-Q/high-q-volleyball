## Context

個人情報保護法 §17-§22 は、個人情報取扱事業者に対し、取得項目 / 利用目的 / 第三者提供 / 保管 / 安全管理 / 本人開示請求対応等を「公表」または「本人通知」する義務を課している。High Q は会員からメール / プロフィール / 電話番号 / 経験レベル、加えて **本人確認書類画像（運転免許証等の極めてセンシティブな情報）** を取得・保管しており、本義務の履行は #92 (reservation 本人確認書類アップロード) の本番 ship のための法務ブロッカーである。

現状、reservation の `PolicyFooter.vue` は `RouterLink to="/privacy"` で内部ルートを期待しているが、当該ルートは未実装で 404 を返す。同コンポーネントは SignupIdentityPage / SignupProfilePage の双方で利用されており、reservation 単独で本対応するなら reservation 内に `/privacy` を持たせるのが自然だが、外部送信ポリシー (#192) の対応で「法令文書は LP 集約」という前例が確立されているため、本対応もそれに従う。

ステークホルダー: 翔太郎くん（オーナー兼開発者・個人情報取扱事業者の代表者）。法律家レビューはオプション扱いで、MVP1 は翔太郎くん起草版で ship する。

## Goals / Non-Goals

**Goals:**
- 個人情報保護法 §17-§22 が要求する記載要素を `/privacy` 1 ページで網羅し、3 アプリ共通の単一 source of truth とする
- LP に集約することで、法令文書の更新時に 1 箇所で済む構造を維持し、外部送信ポリシーと記載スタイル / レイアウト / 更新運用を揃える
- reservation の PolicyFooter からの導線を実機能化し、SignupIdentityPage / SignupProfilePage の同意リンクを 404 → 200 にする
- 開示・訂正・利用停止等の請求窓口（メール）をページに明示し、本人請求を受け付け可能な状態にする

**Non-Goals:**
- 法律家による文面レビュー（Issue 完了条件で「オプション、推奨」。MVP1 では翔太郎くん起草版で ship。レビュー入手後に sync で更新）
- 多言語対応（日本語のみ）
- 開示請求受付フォーム / Web UI 化（メール窓口のみで MVP1 を満たす）
- ログイン後の会員向け「自分のデータ一覧」「ダウンロード」機能（個人情報保護法上は窓口提供で十分。Web UI 化は将来検討）
- Cookie 同意 UI / 外部送信先テーブル（既に #192 で対応済、本ページは「外部送信先の詳細は外部送信ポリシーへ」と相互参照する）
- admin / reservation 内に `/privacy` ルートを持たせること（LP に集約）

## Decisions

### 1. ポリシーページの実装場所: LP に集約

3 案検討: (A) LP に集約 / (B) reservation 内に実装 / (C) 各アプリで個別実装。

**採用: A**。理由:
- 外部送信ポリシー (#192) で確立した「法令文書は LP 集約」前例に従い、UX / 運用を一貫させる
- 法令文書は更新時に 1 箇所で済むのが最大価値（ズレリスクを最小化）
- LP は本番稼働中で URL 安定性が高く、未認証アクセス可で会員登録前ユーザーも閲覧できる
- admin / reservation からは外部リンク扱い（別オリジン）になるが、ポリシーページは純情報表示のため認証コンテキスト不要で問題ない

却下した理由:
- B: 既存 reservation spec の前提と一致するが、外部送信ポリシーと配置がズレ法令文書の見つけ方が一貫しない
- C: 3 重メンテによる内容ズレリスク（法令文書として致命的）

### 2. PolicyFooter のプライバシーリンクを外部リンク化

現状 reservation の `PolicyFooter.vue` は `<RouterLink to="/privacy">` だが、配置先を LP に変更したことで内部遷移は不可能になる。外部送信ポリシー側で確立済の `<a target="_blank" rel="noreferrer" :href="...">` パターンに揃える。

`apps/reservation/src/shared/lib/externalLinks.ts` に既存の `EXTERNAL_TRANSMISSION_URL` と並ぶ `PRIVACY_POLICY_URL` 定数を追加し、PolicyFooter から同様に参照する。

### 3. ページの記載構成

個人情報保護法 §17-§22 の構造に対応した 8 セクション構成:

1. **はじめに**: 団体表記（団体名: High Q バレーボールサークル＝江東区社会教育団体 / 活動拠点 / 連絡先メール）、適用範囲（lp / admin / reservation すべて）
2. **取得する個人情報の項目**: 認証情報（メール）/ プロフィール（氏名・生年月日・電話番号・経験レベル）/ 本人確認書類画像（マスク済みマイナンバーカード含む）/ 予約・参加履歴 / アクセスログ（IP / User-Agent）
3. **利用目的** (法 §17): 本人確認 / 連絡 / 役所提出証憑（江東区・東京都へのスポーツ団体登録）/ サービス提供（予約・参加管理）/ 障害・不正利用調査
4. **第三者提供** (法 §27): 法令に基づく場合および運営者による役所への団体登録証憑提出のみ。業務委託は「外部のクラウドサービス事業者に委託」レベルの概要記載に抑え、個別 SaaS 名は本文に出さない（具体名は本人からの個別問い合わせで開示する運用）
5. **保管期間と退会後の処理**: 在籍中は継続保管 / 退会時は会員データ削除（本人確認書類画像含む）/ 役所提出済の証憑コピーは法令保管期限まで分離保管
6. **安全管理措置**: 「アクセス制御」「保管情報の暗号化」「通信経路の暗号化」レベルの概要記載のみ。個別技術名（RLS / TLS / Storage 暗号化方式等）は安全上の理由から本文に出さない（攻撃者へのヒント漏えい回避）。組織的措置は本人確認書類取扱 SOP（`docs/06-品質・セキュリティ/08`）の運用 / マイナンバー 12 桁テキスト保管禁止 / 閲覧権限最小化を記載
7. **開示・訂正・利用停止請求の窓口** (法 §32-§35): メール窓口（`high.q.volleyball@gmail.com`）。本人確認のうえ合理的期間内に対応
8. **外部送信ポリシーへの相互参照 / 改定履歴 / 最終更新日 / お問い合わせ**

### 3a. 主体表記の方針: 「事業者」ではなく「江東区社会教育団体」

個人情報保護法上の用語「個人情報取扱事業者」をそのまま主体表記として転記すると、High Q が株式会社や個人事業主と誤認される。実態は **任意団体（江東区の社会教育団体登録）** であり、ボランタリーに運営されている。本ページの「はじめに」では団体名・活動拠点・お問い合わせ窓口の 3 点を記載し、「事業者」という用語は法令引用以外では用いない。

### 3b. 公開粒度の方針: 個別 SaaS 名・個別技術名は非掲載

**判断**:
- 個人情報保護法は「業務委託先の名称」公表を義務付けていない（§27）。外国にある第三者への提供（§28）でも、本人への情報提供義務はあるが、ポリシーで先に固有名を掲載する形式までは要求されない。
- 安全管理措置（§23）は「概要」公表で足り、ガイドライン上も「組織的・人的・物理的・技術的・外的環境」の 5 カテゴリで概要記述すればよい。実装名（RLS / TLS 1.3 等）の開示義務はない。
- 一方、本サービスは本人確認書類画像という極めて影響度の高い情報を扱うため、**攻撃者にスタック構成のヒントを与えないこと** の優先度が高い。

**運用**:
- ページ本文: 「クラウドサービス事業者」「アクセス制御」等の抽象表現
- 内部 SOP（`docs/06-個人情報保護方針.md`）: Supabase / Render / AWS / RLS / TLS 等の具体名を保持（運用上の真実）
- 本人問い合わせ: メール窓口で個別に開示する余地を残す（誠実性の担保）

**外部送信ポリシー（`/external-transmission`）との関係**:
外部送信ポリシーは改正電気通信事業法 §27の12 上、外部送信先の名称公表が必須なため Google Tag Manager / Google Analytics / Supabase / Render / AWS API Gateway 等を明示している。プライバシーポリシーから固有名を消しても外部送信ポリシー側で一部判明はするが、両者は対象が異なる（外部送信ポリシー = 外部送信される情報の送信先 / プライバシーポリシー = 取得した個人情報の保管・委託先）。プライバシーポリシーで本人確認書類画像の保管先まで具体名を出す必要はなく、両ポリシーで開示粒度が異なることは法令整合的。

### 4. UI スタックと実装場所

`apps/lp/src/pages/privacy/`（`/external-transmission` と同階層）に Vuetify 製ページを実装。FooterLine.vue（LP の共通フッター）に「プライバシーポリシー」リンクを追加する。

admin / reservation 側はそれぞれ既存の `widgets/app-footer/` に LP オリジンへの外部リンクを追加するだけで済む。

### 5. ページ本文と docs/06-品質・セキュリティ/06 の関係

現状 `docs/06-品質・セキュリティ/06-個人情報保護方針.md` は 0 byte の空ファイル。本対応で内部運用ポリシーとしてもまとまった文書を必要とするため、両者を以下の役割で運用する:

- **`/privacy` ページ**: 一般ユーザー向け（外部公開、簡潔・読みやすさ重視）
- **`docs/06-品質・セキュリティ/06`**: 内部運用 SOP（具体運用手順・監査用、社内向け）

両者は記載項目が一致するべきだが、表現の粒度は異なる。ページの sync 時に docs 側も同時更新する運用とする。

### 6. ルート公開アクセス

`/privacy` は未認証でも閲覧可能（公開ルート）。会員登録前のユーザーが同意判断のために事前確認できる必要があるため。

### 7. 法律家レビューの取扱

Issue で「オプション、推奨」となっているレビューは MVP1 では実施せず、翔太郎くん起草版で ship する。レビュー実施判断は Phase 2 以降の専用 Issue として切り出す。レビュー結果で文面修正が入った場合は、ページ本体 + `docs/06-品質・セキュリティ/06` を同時に更新し、最終更新日を改める。

## Risks / Trade-offs

- [法律家未レビュー版で ship するリスク]: 文面の不備・記載漏れにより法令違反指摘を受ける可能性 → **緩和**: 翔太郎くん承認・Issue 完了条件でも「オプション」明記。法第 17 条以下の必須項目をチェックリスト化して網羅性を担保。レビュー後の差し替えは sync で容易
- [3 アプリ非同時デプロイで一時的に 404 リンク発生]: LP デプロイ前に admin / reservation のフッターリンクが 404 を返す可能性 → **緩和**: LP 先行デプロイ。外部送信ポリシーで確立した「リンク先 404 でも単独受入可」方針を踏襲
- [docs/06 と /privacy の文面ズレ]: 一方だけ更新すると内部運用と外部公表がズレる → **緩和**: 同一 PR で両方更新するルールを spec に明記。sync 時にもチェック
- [開示請求の運用負荷]: メール窓口で受付後に翔太郎くんが本人確認 + 対応する手作業発生 → **緩和**: MVP1 想定会員数（数十人）では年数件レベルで運用可能。フォーム化は Phase 2 で検討
- [本人確認書類画像の削除フローが手動]: 退会時の Storage オブジェクト削除を Web UI 化していない → **緩和**: 別 Issue（退会フロー）で対応予定。本ページでは「退会時は削除する」と方針表明のみで足りる
- [admin の app-footer 未存在の可能性]: 確認済（`apps/admin/src/widgets/app-footer/` 既存）→ リスクなし

## Migration Plan

1. LP に `/privacy` ページ + フッターリンクを実装し**先行デプロイ**
2. reservation の `externalLinks.ts` に `PRIVACY_POLICY_URL` 追加 / `PolicyFooter.vue` の RouterLink を `<a target="_blank">` に変更 / app-footer にリンク追加
3. admin の app-footer にリンク追加
4. `docs/06-品質・セキュリティ/06-個人情報保護方針.md` をページ本文と整合する内部運用ドキュメントとして執筆
5. 3 アプリ揃ったところで本番マージ

ロールバック: LP 単体の追加と reservation/admin のフッター変更のみで、既存挙動を変える破壊的変更なし。問題発生時は revert で旧挙動（PolicyFooter の RouterLink → 404 状態）に戻すだけで済む。

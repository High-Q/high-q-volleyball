## Why

Epic #170 のユーザージャーニーは「予約 → 確認メールの情報で会場へ → 当日参加」と続くが、現状の予約完了画面はブラウザを閉じた瞬間に会場情報・予約番号・LINE 動線が会員の手元から消える。当日朝に確認しようとした会員は予約サイトに再ログインしないと情報に辿り着けず、結果として LINE オープンチャットへの当日連絡経路も失われやすい。

Issue #170 が MVP1 と定義している以上、「予約サイト経由でメール通知が届く」は当日参加体験の前提条件であり、本来 MVP1 で先送りできない領域だった。本 change で既存仕様の「メール送信はスコープアウト」記述を更新し、予約完了とキャンセル完了の 2 イベントを通知メールでカバーする。

## What Changes

- 予約成立イベント（新規予約 / キャンセル後の再活性化）の発生時に、会員へ予約完了メールを自動送信する
- 予約キャンセル成立イベント時に、会員へキャンセル完了メールを自動送信する
- 送信失敗が予約成立そのものを妨げないようにする（メール送信は副作用扱い、ログに残す）
- 既存 spec `reservation-booking-flow` の「メール送信文言・.ics をスコープアウト」記述を、「予約完了画面ではメール文言を載せない（メール本体は別 capability で送る）」「.ics は引き続きスコープアウト」に再表現する
- 既存 Gmail SMTP 経由の送信ヘルパー（signup フローで稼働中）を再利用し、新規送信プロバイダ採用や独自ドメイン取得は行わない
- HTML メール・リマインダー・カレンダー添付 (.ics)・一斉送信は本 change のスコープ外（別 Issue / Phase）

## Capabilities

### New Capabilities
- `reservation-notification-email`: 予約サイトの予約完了 / キャンセル完了に応答して会員へメール通知を送る責務を規定する capability。送信トリガー / 送信内容 / 失敗時の取扱い / 文面トーン / 再活性化時の再送 / セキュリティ（送信先は会員自身のメールに限定） を範囲とする。

### Modified Capabilities
- `reservation-booking-flow`: 予約完了画面の「メール文言・.ics を含めない」記述を、メール本体が `reservation-notification-email` で送られる前提に書き換える。完了画面に表示しないという UI 側の約束は維持しつつ、.ics スコープアウトは継続。

## Impact

- **Supabase Edge Functions**: 新規 function を 1〜2 本追加（予約完了通知 / キャンセル通知）。`_shared/mailer.ts` に予約完了 / キャンセル文面のレンダリングヘルパーを追加する
- **予約サイトのアプリ層**: 予約確定経路 / キャンセル経路の成功後、Edge Function を fire-and-forget で呼び出す（成立フローの応答性を落とさない）
- **環境変数**: 既存 `GMAIL_USER` / `GMAIL_APP_PASSWORD` を流用、追加の secret は不要。送信元アドレスは引き続き High Q の Gmail アカウント
- **ロギング**: 送信成功 / 失敗は Edge Function のログに集約。会員 ID とイベント ID を相関キーに含める
- **依存関係**: 既存 `npm:nodemailer` のみ。新規パッケージ追加なし
- **既存 spec / docs**: `reservation-booking-flow/spec.md` の関連 Requirement と Scenario を更新。`docs/06-品質・セキュリティ/07-ロギング方針.md` のメール送信ログ取扱いに 1 行追記する
- **後続 Issue 想定**: 開催前リマインダー、独自ドメイン + Resend 移行、HTML メール、Auth テンプレートのブランド化、一斉メール（#153）は別 Issue として継続

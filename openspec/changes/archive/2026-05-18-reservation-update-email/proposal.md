## Why

Issue #248 で予約完了 / キャンセル完了の 2 イベントは通知メールでカバーしたが、予約成立後に会員が同伴者数や連絡事項を編集した場合、最新の予約内容が会員の手元（メールボックス）には残らない。当日朝に編集後の最新人数や連絡事項を確認したい会員にとって、再ログインしないと情報に辿り着けない状況は MVP1 で塞いだ動線がまた一部復活している。

運営側にとっても「初参加です」「遅刻します」のような後追いの連絡事項を会員自身のメールにスナップショットしておくと、当日 LINE オープンチャット上での確認ワークが減る。Issue #248 の枠組みに 1 イベント (`updated`) を追加するだけで成立する低コスト改善のため、MVP2 序盤で取り込む。

## What Changes

- 予約内容変更 (edit) の確定時にも、会員へ通知メールを自動送信する
- 通知メールには変更後の同伴者数 / 連絡事項 / 合計金額および会場情報・LINE オープンチャット URL・マイページ URL を含める（完了メールと同等の当日参加情報を維持する）
- 編集が RLS 違反 / 期限切れで成立しなかったときはメールを送らない
- 既存の送信抑制モード・許可リスト設定 (#248 で導入) は新イベントでも同じく機能する
- 件名と本文の冒頭は「予約内容を更新しました」が分かる文言にし、完了メールと取り違えないようにする

> **前提**: 同伴者数 / 連絡事項に実差分がない状態では編集 BottomSheet の確定ボタン自体が既に disabled になっている (`BookingSheet.vue` の `isDirty` チェック)。したがって本 change で扱う「編集成立」はすべて何らかの差分を伴うイベントであり、「差分なし update でメールが届く」ケースは UI 層で構造的に発生しない。

## Non-goals

- 変更差分の前後表示 (before / after diff)。本メールは変更後の確定状態のみを伝える
- 変更履歴の DB 保管 / 監査ログ化
- HTML メール、リマインダー、開催前通知、カレンダー添付 (.ics)
- 編集操作以外（管理者代行修正等）のイベントへの通知拡大
- 「変更があった項目だけハイライト表示」「複数回連続 edit のスロットリング」

## Capabilities

### New Capabilities

（なし）

### Modified Capabilities

- `reservation-notification-email`: 既存の予約完了通知 / キャンセル通知に並列の「予約内容変更通知」Requirement を追加する。送信トリガー（編集成立時のみ）、本文に含める要素（変更後の同伴者数 / 連絡事項 / 合計金額 / 会場・住所・集合地点・マップ・LINE オープンチャット URL・マイページ URL）、送信抑制 / 許可リストの適用、送信失敗が編集成立そのものを妨げないこと、送信先が会員自身のメールに限定されることを規定する。

## Impact

- **Supabase Edge Function (`send-reservation-notification`)**: 受け付ける eventType に 1 値追加。バリデーション・本文レンダラ・ログ相関キーが新値に対応する
- **Edge Function 共有レンダラ**: 予約完了レンダラと同じ入力構造で文面差分のみ持つ更新通知レンダラを追加。レンダラは引き続き純粋関数として `_shared/` に配置し、ユニットテストで検証可能とする
- **予約サイト アプリ層 (`apps/reservation`)**: 編集確定 composable から fire-and-forget で Edge Function を呼び出す。送信失敗 / ネットワークエラーは編集成立フローを妨げない方針を維持
- **`reservation-notification-email` spec**: 「予約内容変更通知メールの送信」Requirement と Scenario を追加。既存 Requirement（完了 / キャンセル / 送信失敗ログ / 環境別ガード / レンダラ純粋関数化）には実質変更なし
- **環境変数**: 既存 SMTP / 抑制モード変数を流用。追加 secret 不要
- **依存関係**: 新規 npm パッケージ追加なし
- **後続 Issue 想定**: HTML メール化、開催前リマインダー、変更差分表示は別 Issue / Phase へ継続

## Context

対象は開発ツールチェーン（バンドラ・テストランナー）本体のメジャー更新であり、ブラウザ配信バンドルにも Edge Function ランタイムにも実行時には載らない。critical はテストランナーの UI サーバー稼働中に限られ、high/medium は dev サーバー限定・一部 OS 限定で、信頼された CI／ローカル環境では実害に至りにくい。それでもメジャー系統が古いままだと今後もアラートが積み上がり続けるため、サポート対象のメジャー版へ計画的に引き上げる。

本リポジトリはビルドツール構成がクリーンで破壊リスクが小さい: sass / Vuetify / 追加の vite プラグインは既に撤去済みで、各アプリが使う vite プラグインは Vue プラグイン 1 本のみ。テスト設定も `globals: false` / `environment` / `include` / `setupFiles` / `coverage`（v8）といった標準構成に収まっており、新メジャーで削除・改名された特殊オプションは使っていない。したがって設定追随は限定的で済む見込みである。

孫依存はアプリの `package.json` に直接現れないため #360 ではオーバーライドで固定したが、バンドラ本体のメジャー更新は新しいトランスパイラ解決版を連れてくるため、#360 がスコープアウトした peer 固定の孫依存はここで自然に解消される。

## Goals / Non-Goals

**Goals:**
- バンドラ・テストランナー本体をサポート対象のメジャー版へ引き上げ、残存する critical / high / medium アラートを解消する。
- 破壊的変更に対して**設定 API の追随のみ**で対応し、テスト・ビルドの挙動は現状維持する。
- 全ワークスペースのビルド・テスト・型・Lint・CI・Render Preview が緑であることを受け入れ条件とする。
- #360 で追加したオーバーライドのうち、本体更新により冗長化したものを掃除する。

**Non-Goals:**
- アプリケーションのランタイム挙動・UI の変更（純粋な依存更新であり、機能追加・改修は含まない）。
- テスト戦略・カバレッジ閾値の見直し（既存の閾値・除外設定は維持する。移設が必要なら等価に写すだけ）。
- ランタイム依存（Vue / Supabase / Sentry 等）のメジャー更新（本変更のスコープ外）。
- ESLint / Playwright 等、バンドラ・テストランナー以外のツールのメジャー更新。

## Decisions

### 1. ワークスペース横断で一括更新する（版の混在を残さない）

vite / vitest はモノレポの共有 lockfile 上で解決され、テストランナーとバンドラは peer で結びつく。ワークスペース内に旧メジャーと新メジャーを同時併存させると、共有される Vue プラグインの peer 要求が食い違い、重複インストールと解決の不安定化を招く。したがって**対象パッケージすべてを同一変更内で同一メジャーへ揃える**。

Issue の「まず 1 アプリで検証 → 横展開」は**別 PR による段階リリースではなく、同一 Apply 内での段階的検証**として解釈する（1 パッケージのビルド・テストを緑にしてから次へ進むことでデバッグ範囲を局所化する）。lockfile を跨いだ版混在の期間を作らないことを優先する。

### 2. 破壊的変更への対応は「設定 API の追随」に限定する

新メジャーで削除・改名された設定オプションや、既定値が変わって挙動が変化する箇所のみを修正する。テストの `include` / `environment` / `setupFiles` / `coverage`（v8 プロバイダ・閾値・除外）は等価を維持する。設定を書き換えた結果テストが落ちる場合は、**設定側で旧挙動へ寄せることを第一選択**とし、テストコード自体の書き換えは最小限に留める（挙動変更を混ぜない）。具体的な差分点は tasks.md で 1 パッケージずつ潰す。

### 3. peer 依存はバンドラ更新に追随して揃える

バンドラのメジャー更新は、Vue プラグイン等の peer に新しい下限を要求する。peer 警告・解決失敗が出た依存は、バンドラ新メジャーが要求する対応版へ引き上げる。バンドラが同梱・要求するトランスパイラ新メジャーによって、#360 が peer 固定ゆえスコープアウトした孫依存アラートが解消されることを、lockfile 上の解決版で確認する。

### 4. テスト実行の正は `pnpm -r test`（パッケージ個別実行）

#360 で確認済みのとおり、ルートで単一プロセスの vitest を全 workspace に走らせるとアプリ間の `@/` エイリアスが混線して大量の false-fail を起こす（本変更の範囲外の既知の実行方法問題）。したがって受け入れ判定の正規実行は `pnpm -r test`（各パッケージが自前の設定で個別に vitest を起動）とする。Issue 完了条件の「`pnpm exec vitest run` 全テスト緑」もこの正規実行で満たすものとして扱う。

### 5. #360 オーバーライドの掃除は「冗長になったものだけ」

本体メジャー更新後、#360 で `pnpm.overrides` に固定した項目のうち、新しい親（バンドラ／テストランナー）が既にパッチ版を要求するようになり冗長化したものは削除する。まだ他経路の親が古い解決を引く可能性がある項目は、lockfile で解決版を確認し、外して問題ないと確認できたものだけを掃除する。**掃除で新たなアラートが復活しないこと**を条件とし、判断がつかない項目は残す。

### 6. Render Preview を受け入れ条件に含める

バンドラのメジャー更新は出力バンドルを再生成するため、ビルドが緑でも配信物の挙動が変わらない保証はない。dev デプロイのある lp / reservation について Render Preview で実表示を確認し、初期表示・主要画面が正常であることを受け入れ条件に含める（admin は Render dev デプロイが無いためローカル確認で代替）。

## Risks / Trade-offs

- **メジャー更新に伴う設定破壊**: 既定値変更や削除オプションで設定が壊れる。→ 1 パッケージずつビルド・テストを緑にしてから次へ進み、破壊箇所を局所化する。全体の受け入れは全アプリのビルド・全テスト・CI・Preview で機械検知する。
- **出力バンドルの挙動差**: バンドラ更新でトランスパイル結果・チャンク分割が変わり、ビルドは通るが実表示が変わる可能性。→ lp / reservation を Render Preview で目視確認する。lp の manualChunks 設定は維持し、生成される vendor チャンクが意図どおりか確認する。
- **テストランナー API 変更でテストが落ちる**: モック・スパイ・タイマー系の仕様変更。→ 設定側で旧挙動へ寄せることを優先し、テスト書き換えは最小限に。挙動変更を依存更新に混ぜない。
- **オーバーライド掃除の巻き戻り**: 冗長と判断して外したオーバーライドが、別経路の古い親を通じてアラートを復活させる。→ 掃除後に lockfile 解決版を再確認し、判断がつかない項目は残す。掃除は本変更で解消するアラート一覧と矛盾しない範囲に留める。
- **CI 環境固有の flaky**: admin の router.spec は弱 runner で lazy import 解決が既定タイムアウトを超える既知事象があり、現状 timeout 拡張で安定化している。→ 新メジャーでタイムアウト設定が維持されることを確認し、必要なら等価に写す。

## Context

`docs/06-品質・セキュリティ/` 配下は個別の運用観点ごとに番号付き SOP が並んでおり、現状 11 番まで採番済 (外部送信規律対応方針)。安全管理措置については `06-個人情報保護方針.md` §6 に短い項目列挙が存在するのみで、組織的・人的・物理的措置の具体記述や、漏洩時に運営者が辿るべき具体フローは未整備。Issue #195 でこの空白を埋める。

運営はオーナー単独であり、組織体制 = 一人体制であることを正面から認める形で SOP 化する (架空の役割分掌を作らない)。漏洩時対応は「翔太郎くんが一人で初動から再発防止まで遂行する」前提で、判断順序と参照先を明文化する性格のドキュメントになる。

## Goals / Non-Goals

**Goals:**
- 個人情報保護法 §23 が要求する 4 領域 (組織的・人的・物理的・技術的) の安全管理措置を 1 ファイルで通読できる SOP を整備し、規制当局・取引先・将来の共同運営者が見たときに整っていると判断できる粒度にする
- 漏洩時対応を時系列フローと判定基準で明文化し、有事に「次に何をするか」を SOP を読むだけで決められる状態にする
- 既存 SOP との重複・矛盾を発生させず、各 SOP は単一責務に集中させる (相互参照で解決)
- 公開側プライバシーポリシーへの影響をゼロに保つ (公開側は既存記載で法令要件を満たしている)

**Non-Goals:**
- 公開側プライバシーポリシー本文の改訂 (本変更スコープ外。公開側に内部 SOP の存在を示す必要は法令上ない)
- インシデント検知のための監視・アラート実装 (運用ツール導入は別 Issue。本 SOP は検知後の手順から始まる)
- 共同運営者を想定したロール拡張 (一人体制を前提とし、将来複数人体制になった時点で別途改訂)

## Decisions

### 1. SOP を 2 ファイルに分割する (安全管理措置 / 漏洩時対応)

**選定**: 「安全管理措置 SOP」と「漏洩時対応 SOP」を別ファイルに分ける

**理由**: 安全管理措置は平時の継続運用を規定する文書、漏洩時対応は有事に開く緊急ランブック。読み手の文脈と参照タイミングが異なる。1 ファイルにまとめるとどちらの目的でも長すぎて検索性が落ちる。2 ファイルに分けることで漏洩時に該当ファイルだけを開けば必要な情報に到達できる。

**代替案**: 1 ファイルに「平時編」「有事編」として併記。読み込み時間が増える割に有事の検索性が改善しないため不採用。

### 2. ファイル番号は採番順を維持 (12 / 13)

**選定**: 既存 11 番 (外部送信規律) の続番として 12-安全管理措置.md / 13-漏洩時対応SOP.md とする

**理由**: 既存 SOP の番号は「採番順 = 整備した時系列」を示すアーカイブ的性格を持っており、トピック分類ではない。番号を入れ替えると既存ドキュメント・コミット履歴・ADR からの参照リンクが破断する。新規分は連番末尾に追加する。

### 3. 既存 `06-個人情報保護方針.md` §6 を slim 化して新 SOP へ委譲

**選定**: §6 は安全管理措置の網羅章を維持しつつ、各領域の本文は新 SOP (12-安全管理措置.md) への参照に切り替える

**理由**: 個人情報保護方針 SOP は公開ページ (`/privacy`) と整合する内部運用版という位置付け (privacy-policy-page spec が要求)。安全管理の詳細を §6 に直書きすると、新 SOP との二重管理になり改定漏れの温床になる。各領域の見出しと 1〜2 行の概要のみ残し、本文は新 SOP に集中させる。

**代替案**: §6 を完全削除して新 SOP へリダイレクト。公開ページ整合性 (取得項目 / 利用目的 / 第三者提供 / 保管期間 / 安全管理 / 開示請求) の章構成が崩れるため不採用。

### 4. 漏洩判定基準は個人情報保護委員会の規則を参照する形にする

**選定**: 報告対象案件の定義は「保護委員会規則および同委員会ガイドラインで定める要件に該当する場合」とし、具体的な該当パターン (要配慮個人情報含む / 財産的被害発生のおそれ / 不正目的の漏洩 / 1000 件超 等) を例示する

**理由**: 報告対象の正確な定義は委員会の規則・ガイドライン側で更新される性質の情報。SOP に直書きすると改正に追随できない。SOP では「該当パターンの代表例 + 委員会ガイドラインへの動的参照」で運用し、判定の最終根拠は委員会発表に置く。

### 5. 報告タイムラインは「速報 概ね 3〜5 日 / 確報 30 日 (要配慮等は 60 日)」を明記

**選定**: 個人情報保護委員会の現行規則に基づくタイムラインを SOP に明記し、初動カウントダウンとして使えるようにする

**理由**: 漏洩時の初動はタイマーが回っている状態。SOP を開いた瞬間に「今日の日付 + 残り何日」が出せる粒度の記述が必要。一般論ではなく具体日数を入れる。

### 6. 既存 SOP との相互参照は本人確認書類取扱 SOP からのみ追加

**選定**: 08-本人確認書類取扱SOP.md に「漏洩時の初動は 13-漏洩時対応SOP.md を参照」のクロスリンクを 1 行追加。他 SOP には追加しない

**理由**: 本人確認書類は最高センシティブ度 (運転免許証画像 / マイナンバーマスク画像) を扱う SOP であり、漏洩時の即時フロー参照が最も必要。他 SOP (RLS / アクセス制御 / 監査) は平時運用の SOP で、漏洩時動線への直接リンクは不要。リンクを増やしすぎると相互参照が氾濫し、改定時のメンテナンスコストが上がる。

## Risks / Trade-offs

- [新 SOP と既存 §6 の二重管理リスク] → §6 はサマリ + 参照に徹する方針を SOP 冒頭に明記し、改定時のチェックリストに「12-安全管理措置.md 改定時は 06-個人情報保護方針.md §6 のサマリも整合確認」と入れる
- [報告タイムラインの法令変更追随漏れ] → SOP 冒頭に「本タイムラインは個人情報保護委員会規則の現行規定に基づく。改正時は本 SOP も改定する」と注記し、年次レビュー対象に含める
- [一人体制を前提に書くことで将来の組織拡張時に書き直し負担が大きい] → 一人体制を前提とした記述には注釈を入れ、将来複数人体制への移行時点で改訂する旨を明示。Non-Goals でも宣言済
- [漏洩判定の自己判断リスク] → 判定が微妙なケースでは「個人情報保護委員会への事前相談 (PIO 相談窓口) を活用する」を SOP に明記し、自己判断のみで報告省略しない動線を作る

## Migration Plan

新規 SOP 追加と既存 SOP のテキスト改訂のみ。コード・DB・デプロイへの影響なし。マージ即時有効。ロールバックは git revert で完結。

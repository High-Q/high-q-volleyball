## ADDED Requirements

### Requirement: LP の主要セクションは HQ ブランド体験を体現する新構成で表示される

LP のホームページは、初訪問者の心理的ハードルを下げ、リピーターが次の予定に最短で到達できるよう、HQ ブランド体験を体現する新セクション群で構成されなければならない（SHALL）。各セクションの責務は次のとおり：
- ヒーロー：訪問者を歓迎し、温度感と主要 CTA を提示する
- 次回開催帯：直近の開催情報を上部に常設し、リピーターを最短で予約に導く
- 安心ストリップ：参加に必要な持ち物・服装・参加費を要点化して提示する
- 開催メタ：活動エリア・頻度・開催曜日を一目で示す
- 紹介：High Q の世界観と立ち位置を語る
- 特長：High Q の三つの「ちょうどよさ」を提示する
- 当日の流れ：初参加者が当日体験する手順を時系列で示す
- 不安への回答：参加前のよくある不安に短く答える
- イベント一覧：開催予定のイベントをカード形式で並べ、予約導線を提供する
- FAQ：よくある質問に折りたたみ形式で答える
- 合わない方への注記：誠実にミスマッチを伝える
- ギャラリー＆SNS：活動の雰囲気を伝えるビジュアルと SNS 動線を提供する
- 最終 CTA：会員登録・予約導線への最終的な後押しを行う
- フッター：法務・SNS・基本情報を提供する

#### Scenario: 新セクション群の表示順
- **WHEN** 訪問者がトップページを開く
- **THEN** 上記セクションが、ヒーロー → 次回開催帯 → 安心ストリップ → 開催メタ → 紹介 → 特長 → 当日の流れ → 不安への回答 → イベント一覧 → FAQ → 合わない方への注記 → ギャラリー＆SNS → 最終 CTA → フッターの順で表示される

#### Scenario: 表現要素は HQ デザイントークン経由で統制される
- **WHEN** 各セクションの色・書体・余白・角丸・影が決定される
- **THEN** すべてが HQ デザイントークン（CSS variables もしくは `@high-q/design-tokens` の TS export）経由で参照されている

### Requirement: ヒーロー直下に「次回開催」帯が常設される

ヒーローセクションの直下には、直近の開催イベントを要点化した帯が常設されなければならない（SHALL）。リピーターはこの帯から最短で予約導線に到達できなければならない（SHALL）。

#### Scenario: 次回開催情報の表示
- **WHEN** 公開中の未来イベントが少なくとも 1 件存在する
- **THEN** ヒーロー直下の帯にはその最も近い未来イベントの日付・名称・会場・時間帯と予約導線が表示される

#### Scenario: 未来イベントが 0 件のとき
- **WHEN** 公開中の未来イベントが 1 件も存在しない
- **THEN** 帯は次回開催情報を求めない別の文言（または非表示）を選択し、ユーザーに誤情報を表示しない

#### Scenario: 帯から予約導線への遷移
- **WHEN** 利用者が帯の予約導線を操作する
- **THEN** reservation サイトの所定 URL へ遷移し、対象イベントの識別子がクエリパラメータ等で渡されている（reservation 側の入口受け取り動作は別 Issue の仕様で扱う）

### Requirement: LP のイベントカードから「そのイベントの予約」への動線が提供される

LP のイベント一覧の各イベントカードには、reservation サイトの所定 URL へイベント識別子を保ったまま遷移させる動線が含まれなければならない（SHALL）。LP 側はイベント識別子を URL に乗せて渡すことのみを担い、ユーザーの認証状態に応じた reservation 側の画面選択は LP の責務外とする。

#### Scenario: イベントカードの予約アクション
- **WHEN** 訪問者がイベントカードの予約アクションを操作する
- **THEN** ブラウザは reservation サイトの所定 URL に遷移し、対象イベントの識別子がクエリパラメータ等で渡されている

#### Scenario: LP は認証状態を判定しない
- **WHEN** イベントカードの予約アクションが起動される
- **THEN** LP 側ではユーザーの認証セッション参照やリダイレクト出し分けは行われない

### Requirement: LP は reservation サイトの URL を環境変数経由で参照する

LP は reservation サイトの基底 URL を環境変数（`VITE_RESERVATION_URL`）で受け取らなければならない（SHALL）。ハードコードしてはならない（SHALL NOT）。dev / prd で異なる URL を指定可能であること。

#### Scenario: 環境変数が未設定のときの安全な振る舞い
- **WHEN** 環境変数が未設定でビルドが実行される
- **THEN** ビルド時または起動時に明確に検出可能な状態（ビルドエラー、もしくは LP の予約アクションが無効化されユーザーに伝わる）になる

#### Scenario: dev / prd で別 URL を参照できる
- **WHEN** dev 環境と prd 環境で異なる reservation URL を環境変数で与える
- **THEN** それぞれの環境でビルドされた LP は自環境向けの reservation サイトに遷移する

### Requirement: 最終 CTA は会員登録・予約導線を主動線にする

最終 CTA セクションでは、reservation サイトへの誘導を主動線（一次ボタン）として配置しなければならない（SHALL）。LINE オープンチャットへの誘導は補助動線として併設できる（MAY）。

#### Scenario: 一次 CTA は reservation サイト
- **WHEN** 訪問者が最終 CTA セクションを見る
- **THEN** reservation サイトへ遷移する一次ボタンが視覚的に主役として配置されている

#### Scenario: 補助動線としての LINE
- **WHEN** 一次 CTA に加えて補助動線を提供する
- **THEN** LINE オープンチャットへのリンクは補助的な見た目（二次ボタンまたはテキストリンク）で併設される

### Requirement: LP の主要ビューはモバイル幅を主軸に最適化される

LP の主要ビューは、ヒーローおよびすべてのセクションがモバイル幅（420px 相当を中心）で最適化されなければならない（SHALL）。タブレット・デスクトップ幅でも崩れず、読みやすい行長と余白を維持する（SHALL）。

#### Scenario: モバイル幅での表示
- **WHEN** 訪問者が 420px 前後の画面幅で LP を開く
- **THEN** すべてのセクションが縦に積まれ、行長・余白・タップターゲットが読みやすく操作しやすい寸法で表示される

#### Scenario: デスクトップ幅での表示
- **WHEN** 訪問者が幅の広い画面で LP を開く
- **THEN** モバイル設計を中央寄せした見え方か、または横方向の余白を確保した安定したレイアウトで表示される

## MODIFIED Requirements

### Requirement: ハードコードされたカラー値が CSS 内に存在しない

LP の Vue コンポーネントには、HQ デザイントークンに存在しない色値（旧 Vuetify テーマの 4 色を含む）をハードコードで含めてはならない（SHALL NOT）。すべての色は HQ デザイントークン経由（CSS variables もしくは `@high-q/design-tokens` の TS export）で参照されなければならない（SHALL）。Vuetify のテーマ定義から HQ 由来でない色を参照することも禁ずる（SHALL NOT）。

#### Scenario: HQ トークン外の色値の不在
- **WHEN** LP のコンポーネントを静的検査する
- **THEN** HQ デザイントークンに存在しない色値（旧 Vuetify テーマ色を含む）のハードコード参照が存在しない

#### Scenario: HQ トークン経由での色参照
- **WHEN** コンポーネントが色を必要とする
- **THEN** CSS variables（例：`var(--hq-color-*)`）または `@high-q/design-tokens` の TS export 経由で参照される

### Requirement: フッターは法務・基本情報・SNS を提供する

LP のフッターには、サークル名・基本紹介・SNS リンク・法務リンク群（プライバシーポリシー／外部送信ポリシー／Cookie 設定）・コピーライトが含まれなければならない（SHALL）。新デザインに合わせて視覚は HQ トークン基盤で統一される（SHALL）。

#### Scenario: フッター必須項目の表示
- **WHEN** 訪問者が LP のフッターを見る
- **THEN** サークル名・紹介文・SNS リンク・法務リンク群・コピーライト表記が確認できる

#### Scenario: 法務リンクは常設
- **WHEN** いずれの画面幅でもフッターが表示される
- **THEN** プライバシーポリシー・外部送信ポリシー・Cookie 設定の各リンクが押下可能な状態で常設されている

#### Scenario: 視覚は HQ トークン経由
- **WHEN** フッターの色・書体・余白が描画される
- **THEN** HQ デザイントークン経由で統制された値で表示されている


### Requirement: GTM は Cookie 同意取得後にのみロードされる

LP は Google Tag Manager を、ユーザーが analytics 同意を与えた後にのみ動的にロードしなければならない（MUST）。`apps/lp/index.html` の `<head>` に GTM の inline script を直書きしてはならない（MUST NOT）。新デザイン適用後も同条件を満たさなければならない。

#### Scenario: 同意前は未ロード
- **WHEN** consent 未決定または analytics 拒否の利用者が LP を開く
- **THEN** ページからは `googletagmanager.com` へのネットワークリクエストが一切発生しない

#### Scenario: 同意後にロード
- **WHEN** 利用者が「すべて受け入れる」または analytics トグル ON で同意を保存する
- **THEN** 同イベントを契機に動的 script tag が挿入され GTM がロードされる

#### Scenario: 同意済再訪
- **WHEN** analytics 同意済の利用者が再訪する
- **THEN** ページ初期化シーケンスの中で動的 script tag 経由で GTM がロードされる（inline 直書きではない）

## REMOVED Requirements

### Requirement: 各セクションがスクロール到達時にフェードインする
**Reason**: スクロール連動フェードインは、新デザインの「静謐で落ち着いた読み物的トーン」に合わず、視認性と一貫性も損なう（複数セクションが同時にフェードインする実装では演出として機能しない）。本変更ではセクションは初期状態から即時表示することとし、フェードイン仕様は廃止する。
**Migration**: `useFadeInOnScroll` 経由の `.is-visible` 切替と関連 CSS（`opacity: 0` 初期値・`transform: translateY(...)` 初期値・`transition: opacity/transform`）を全 widget から削除し、各セクションは静的に表示する。

### Requirement: Hero セクションに CTA ボタンが2つ表示される
**Reason**: 新デザインではヒーロー直下に「次回開催」帯を常設し、ヒーロー内 CTA は「最終 CTA」と連動した会員登録・予約導線に再設計される。X のアンカー CTA とイベントアンカーの 2 ボタン構成は廃止される。
**Migration**: ヒーローの主要動線は新仕様「最終 CTA は会員登録・予約導線を主動線にする」「ヒーロー直下に『次回開催』帯が常設される」へ統合する。X SNS への到達は「ギャラリー＆SNS」セクションおよびフッターで担保する。

### Requirement: ヘッダーにアンカーナビゲーションが表示される
**Reason**: 新デザインのページ構成（モバイル幅前提の縦長ストーリー）では、ヘッダー内アンカーナビは情報密度に対して過剰であり廃止する。リピーターの最短到達は「次回開催」帯で代替する。
**Migration**: 主要セクション間の到達は「次回開催」帯および各セクション間の自然なスクロール体験で代替する。

### Requirement: ヘッダーがスクロール量に応じて視覚的に変化する
**Reason**: アンカーナビ廃止に伴い、ヘッダーそのものの役割が縮小される。新デザインのモバイル幅ステータスバー的な薄いヘッダー演出に置き換えるため、旧スクロール連動挙動の仕様は撤去する。
**Migration**: 新ヘッダーの視覚仕様は本変更で導入される「LP の主要セクションは HQ ブランド体験を体現する新構成で表示される」に従う。

### Requirement: ActivitiesSection が HomePage に表示される
**Reason**: 旧 ActivitiesSection は新デザインの「特長」「ギャラリー＆SNS」セクションに分解・吸収される。
**Migration**: SNS 動線は「ギャラリー＆SNS」セクションに移管し、活動内容の語りは「特長」セクションに統合する。

### Requirement: コンセプトカードが3列横並びで表示される
**Reason**: 新デザインはモバイル幅を主軸とし、3 列横並びカードは採用しない。コンセプトに相当する語りは「紹介」「特長」セクションに分解される。
**Migration**: コンセプトの内容は「紹介」「特長」セクションに統合される。

### Requirement: 全セクションの横幅がヘッダーと揃う
**Reason**: モバイル幅主軸の新デザインでは、セクション全幅と内側余白を別に持つ設計に変わる。旧 `v-container` 横幅一致前提の制約は適用されない。
**Migration**: 新セクションは「LP の主要ビューはモバイル幅を主軸に最適化される」に従う。

### Requirement: X (Twitter) アイコンは公式ロゴで統一される
**Reason**: 新デザインで X アイコンの登場位置と表現は再定義される。「公式ロゴで統一」の規範自体は維持されるべきだが、ヘッダー／フッター／ActivitiesSection を前提とする旧シナリオは新デザインの配置に整合しないため一旦撤去する。
**Migration**: 新たに「ギャラリー＆SNS」「フッター」の SNS 表現を伴う Requirement を別 Issue で再定義する想定。本変更内では SNS リンクの最低限の存在は「フッターは法務・基本情報・SNS を提供する」で担保する。

### Requirement: フッターが3カラム構成でリッチに表示される
**Reason**: 新デザインのフッターはモバイル幅主軸で再構成される。旧 lg/md/sm 別の 3 カラム／2 カラム／1 カラム規定は適用されない。
**Migration**: フッター必須項目は「フッターは法務・基本情報・SNS を提供する」に集約される。

### Requirement: フッターが表示される
**Reason**: 同上。新フッター要件「フッターは法務・基本情報・SNS を提供する」に統合する。
**Migration**: 「フッターは法務・基本情報・SNS を提供する」を参照。

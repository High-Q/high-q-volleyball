## Context

Dependabot の open アラートを依存ツリーで全件追跡したところ、対象パッケージはすべて開発ツールチェーン（テストランナー・バンドラ・Lint・パッケージ管理）経由の孫依存であり、ブラウザ配信バンドルにも Edge Function ランタイムにも載らないことを確認済み。多くは「アルゴリズム計算量による DoS」「開発サーバー稼働中に悪意あるサイトを踏んだ場合の情報漏洩」「特定 OS 限定」のいずれかで、信頼された CI／ローカル環境では実害に至りにくい。それでもアラートが積み上がると本当に危険なものが埋もれるため、安全に潰せる分をコード変更なしで先に解消する。

孫依存はアプリの `package.json` に直接現れないため、通常の依存更新では固定できない。モノレポ全体で解決版を強制するには、ルートの依存解決オーバーライドが適切な手段となる。

## Goals / Non-Goals

**Goals:**
- 孫依存に閉じた脆弱パッケージを、現行メジャー系統の内側でパッチ版へ寄せ、該当アラートを解消する。
- アプリケーションコードを一切変更しない。
- 全アプリのビルド・テスト・CI が緑であることを解消の受け入れ条件とする。

**Non-Goals:**
- バンドラ／テストランナー本体のメジャー更新（破壊的変更を含む。後続の別変更で扱う）。
- バンドラの peer に固定された孫依存の解消（その本体メジャー更新でしか安全に解消できないため後続へ委譲）。
- 本番ランタイム依存の変更（そもそも対象アラートは本番非露出）。

## Decisions

### 1. 解決手段は「ルートの依存解決オーバーライド」

各脆弱パッケージを、現行のメジャー系統を跨がない最小のパッチ版へ寄せる。メジャーを跨ぐと親パッケージが要求する API と食い違い依存を壊すため、**同一メジャー系統内**に留めることを絶対条件とする。具体的な版番号・対象一覧は tasks.md に置く。

### 2. 同名パッケージが複数メジャー系統で併存する場合はスコープを限定する

同名で複数のメジャー版が同時にインストールされているパッケージは、脆弱範囲に該当する系統だけをオーバーライド対象にする。名前だけの一括オーバーライドは、無関係な旧メジャー系統（別の親が要求）まで巻き込んで壊すため禁止する。バージョン系統を限定したセレクタで対象を絞る。

### 3. バンドラ peer に固定された孫依存はスコープアウト

バンドラのメジャー版に peer として固定されている孫依存は、本変更で単独オーバーライドするとバンドラ内部の呼び出しを壊すリスクが高い。その系統の脆弱性は、後続のバンドラ・メジャー更新が新しい解決版を連れてくることで自然に解消される。したがって本変更では対象外とし、後続変更へ明示的に委譲する。該当アラートが「本変更では消えず後続で消える」ことを完了報告に明記する。

### 4. 独立した開発ツール由来の孫依存は best-effort

バンドラに縛られない独立ツール（型実行ツール等）が引く孫依存は、オーバーライドを試み、その親ツールが問題なく動作することをビルド・スクリプト実行で確認する。もし親ツールが壊れる場合は本変更では見送り、後続へ回す。重大度が低くツール稼働時のみ・特定 OS 限定であれば、無理に押し込まない。

### 5. lockfile の重複整理

オーバーライド適用後、依存の重複を整理して解決版を一本化する。onlyBuiltDependencies に含まれるバンドラ系パッケージはインストール時にバイナリを取得するため、オーバーライド後にインストール・ビルドが正常に完走することを確認する。

## Risks / Trade-offs

- **オーバーライドによる予期せぬ破壊**: パッチ版でも親の期待と食い違う可能性はゼロではない。→ 全アプリのビルドと全テストを回して緑を受け入れ条件とすることで機械検知する。
- **メジャー跨ぎの誤爆**: 同名複数系統のパッケージで対象を誤ると旧系統を壊す。→ バージョン系統を限定したセレクタと、適用後の各系統バージョンの目視確認で防ぐ。
- **一部アラートが残る**: スコープアウトした孫依存のアラートは本変更後も残る。→ 後続変更で解消することを完了報告で明示し、残存が「未対応の見落とし」に見えないようにする。
- **オーバーライドの恒久化**: 親パッケージが将来パッチ版へ追随したら、オーバーライドは冗長になる。→ 後続のメジャー更新時に不要になったオーバーライドを掃除する運用とする（tasks に将来の掃除条件をメモ）。

## Why

江東区スポーツネットの空き枠 crawler（#286 で稼働開始）が、本番で一度も空き枠を検知できておらず、オーナーへの LINE 通知が届いていない。実サイトには土日祝の空き枠が実在するのに、全 run が「新規通知 0 件」で推移している。ログインから結果グリッド表示までは到達できており、グリッドの器（時間帯の列・会場の行）は取得できているのに、肝心の「空き」セルだけを 1 件も拾えていない。空きを見逃し続けているだけでなく、それを黙って見逃している（誰も気づけない）ことが二重の問題になっている。

## What Changes

- 本番の実結果 HTML を取得し、パースが依拠している前提（時間帯の見出し・会場名・空きセルの判定・日送り後のグリッド再取得）のうち、どれが実サイトと食い違っているかを特定する。**診断の結果、独立した 2 つの根本原因を確定した**（下記 A / B）。
  - **原因 A（空きセルの判定）**: 空きを表す class（従来の `ok`）が実サイトから消え、空き枠は予約導線（予約ボタン画像 / onclick）だけで表現されるようになっていた。class を探すパーサは空きを永久に 0 件と誤判定していた。
  - **原因 B（検索スコープの取りこぼし）**: 結果グリッドに監視対象（6 施設 × 大体育室「半面」）が現れず、既定の 1 施設・1 室場（全面）しか検索できていなかった。オーナーが確認した実在の空き枠がグリッドに存在すらしていなかった。
- 原因 A に対し、空き判定を壊れやすい class 依存から予約導線シグナル主軸へ切り替える。原因 B に対し、追加診断で「全選択」がどのステップで落ちているかを特定し、監視対象施設・室場が結果に並ぶよう照会手順を根本修正する。応急手当てではなく、同じコアを共有する別施設アダプタ（Bumb / #287）にも波及する形で直す。
- 実 HTML を PII・セッション情報を除いた新しい回帰用 fixture に落とし、「空きセルを正しく拾う」ことを固定するテストを追加して再発を防ぐ。
- **観測性の強化**: crawl 結果に「絞り込み前の生の空き枠数」を含む段階ごとの件数を必ず残し、どの段で 0 に落ちたかを一目で追えるようにする。グリッドは取得できているのに空きが継続的に 0 件という「静かな 0」を異常として検知・記録できるようにする（従来はグリッド自体が 0 件のときしか異常扱いにならず、本件をすり抜けた）。
- 異常検知の送出先（Sentry）が未設定でも継続的な 0 件に気づけるようにするか、送出先の設定を運用手順として明文化するかを決めて反映する。
- 修正後、実際に空き枠がある状態でオーナーに LINE 通知が届くことを実 run で確認する。

### Modified Capabilities
- `court-availability-crawl`: 「crawl 失敗の観測」要件を、グリッド自体が取れないケースだけでなく「グリッドは取得できたが空き枠を継続的に 0 件しか検知できない」ケースも異常として観測できるよう強化する。空き検知の funnel（段階ごとの件数）を観測可能にすることを要件に含める。

## Impact

- **対象**: `packages/court-crawler`（江東区アダプタのパース／照会 driver、crawl オーケストレーションの結果サマリ、失敗記録、回帰用 fixture・テスト）
- **波及**: 同一 crawl コアを共有する Bumb アダプタ（#287・未着手）にパース改善が引き継がれる前提
- **運用**: GitHub Actions（既存 workflow の手動 dispatch）で実 HTML を診断ダンプ／修正後の LINE 到達確認を行う。Sentry 送出先（DSN）設定の要否を運用手順として確定
- **秘密情報**: 診断ダンプは会場名・時刻のみ（PII なし）。認証情報・セッション ID・個人情報は fixture にもログにも残さない

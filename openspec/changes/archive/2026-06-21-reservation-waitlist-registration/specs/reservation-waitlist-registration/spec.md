## ADDED Requirements

### Requirement: 満員イベント詳細のキャンセル待ち CTA 分岐

会員サイトのイベント詳細画面は、満員（`capacity` あり、かつ予約埋まり具合 >= `capacity`）のイベントに対して、当該会員の自己予約状態に応じて下部 CTA を SHALL 分岐する。

- 当該会員が当該イベントに有効な予約（`status = 'reserved'`）を持つ場合: イベント詳細画面に到達する前段（一覧 / NEXT カード）で予約詳細へ誘導される既存挙動に従い、満員 CTA 分岐の対象外とする。仮にイベント詳細に到達した場合も「キャンセル待ちに登録」CTA は SHALL NOT 描画する。
- 当該会員が当該イベントに対してキャンセル待ち登録済み（`status = 'waitlist'`）の場合: 「キャンセル待ち登録済み」と分かる無効状態の表示を MUST 描画し、再登録用の押下可能 CTA は描画 SHALL NOT する。
- 上記いずれにも該当せず未登録の場合: 無効化された「予約締切」ではなく、押下可能な「キャンセル待ちに登録」CTA を MUST 描画する。

`capacity` が NULL（満員概念が成立しない）のイベントでは本要件は適用されず、通常の「予約に進む」CTA 挙動を MUST 維持する。自己予約状態の取得に失敗した場合は安全側に倒し、満員時は従来どおり無効表示（「予約締切」相当）を MUST 維持する。

#### Scenario: 満員 + 未登録でキャンセル待ち CTA が表示される
- **WHEN** `capacity` あり・満員のイベント詳細に、当該イベントへ予約もキャンセル待ちも持たない会員がアクセスする
- **THEN** 下部 CTA は押下可能な「キャンセル待ちに登録」として描画される（「予約締切」無効表示ではない）

#### Scenario: 満員 + キャンセル待ち登録済みで登録済み表示
- **WHEN** 満員イベント詳細に、当該イベントへ既に `status = 'waitlist'` の行を持つ会員がアクセスする
- **THEN** 「キャンセル待ち登録済み」と分かる無効状態が描画され、押下可能なキャンセル待ち CTA は描画されない

#### Scenario: capacity NULL では通常 CTA を維持
- **WHEN** `capacity` が NULL のイベント詳細にアクセスする
- **THEN** CTA は通常の「予約に進む」として描画され、キャンセル待ち CTA は描画されない

#### Scenario: 自己予約状態の取得失敗時は安全側に倒す
- **WHEN** 満員イベント詳細で、当該会員の自己予約状態の取得が失敗する
- **THEN** キャンセル待ち CTA は描画されず、満員時の無効表示（「予約締切」相当）にフォールバックする

### Requirement: キャンセル待ち登録 UI

会員サイトはキャンセル待ち登録 UI を、予約確認 Bottom Sheet（`reservation-booking-flow` capability）のシェルを再利用した **waitlist 表示**として SHALL 提供する。本 UI はイベント詳細画面の「キャンセル待ちに登録」CTA から、画面下部に立ち上がる MUST。独立したルートは持たず、起動元のイベント詳細画面の URL のまま完結する MUST。

waitlist 表示は予約（create / edit）モードと以下の点で MUST 異なる:

- kicker / 見出し / 説明文をキャンセル待ち登録向けの文言とする。
- 同伴者数の入力（stepper）は提供する（admin 繰り上げ時に必要なスナップショットのため）。
- 合計金額カードは描画 SHALL NOT する（この段階で支払いは確約されないため、金額提示は誤解を招く）。
- 確定 CTA ラベルはキャンセル待ち登録向けの文言とする。
- 確定処理中は二重送信防止のため CTA を無効化する MUST。
- localStorage への入力内容の保持は行わない MUST NOT（create モードの下書き保持とは独立）。

電話番号は予約と同様に内部処理として会員プロフィールの電話番号をそのままスナップショット保存する MUST（画面表示はしない）。

#### Scenario: キャンセル待ち登録 UI の基本表示
- **WHEN** 満員 + 未登録の会員がイベント詳細で「キャンセル待ちに登録」を押下する
- **THEN** 画面下部からシートが立ち上がり、キャンセル待ち用の kicker / 説明文 / 同伴者数 stepper / 確定 CTA が描画される

#### Scenario: 合計金額カードを表示しない
- **WHEN** キャンセル待ち登録 UI が開いている状態の DOM を確認する
- **THEN** 合計金額カード（参加費 × 人数の提示）は描画されない

#### Scenario: 起動元 URL を維持する
- **WHEN** キャンセル待ち登録 UI が開いている状態
- **THEN** 現在の URL は起動元のイベント詳細画面のまま変わらない

#### Scenario: 電話番号のスナップショット
- **WHEN** キャンセル待ち登録が成功する
- **THEN** 作成された行の電話番号スナップショット列には、画面入力ではなく会員プロフィールの電話番号がそのまま保存される

#### Scenario: 確定処理中の二重送信防止
- **WHEN** キャンセル待ち登録 UI で確定 CTA を押下した直後の処理中
- **THEN** CTA は無効化され、再押下しても新たな書き込みは発行されない

### Requirement: キャンセル待ち行の作成と再活性化

会員サイトはキャンセル待ち登録の確定で、当該会員の当該イベントに対する `reservations.status = 'waitlist'` 行を SHALL 成立させる。同伴者数 / 連絡事項 / 電話番号は通常予約と同様にスナップショットする MUST。

`(event_id, member_id)` の UNIQUE 制約により既存行と衝突した場合は、既存行の状態で MUST 分岐する:

- 既存行が `status = 'cancelled'`: その行を `status = 'waitlist'` へ再活性化し、同伴者数 / 連絡事項 / 電話スナップショットを今回の入力で上書きし、キャンセル時刻を NULL に戻す MUST。
- 既存行が `status = 'reserved'` または `status = 'waitlist'`: 二重登録として扱い、行を新規作成 SHALL NOT し、UI にその旨を通知する MUST。

クライアントから `service_role` キーを使用しては MUST NOT ならない。書き込みは会員の権限と `reservations` の RLS（`rls-policies` capability）に完全準拠する MUST。

#### Scenario: 未登録からのキャンセル待ち行作成
- **WHEN** 当該イベントに既存行を持たない会員がキャンセル待ち登録を確定する
- **THEN** `status = 'waitlist'` の行が 1 件作成され、同伴者数 / 連絡事項 / 電話番号がスナップショットされる

#### Scenario: キャンセル済み行の再活性化
- **WHEN** 当該イベントに過去キャンセル済み（`status = 'cancelled'`）の行を持つ会員がキャンセル待ち登録を確定する
- **THEN** 既存行が `status = 'waitlist'` に再活性化され、同伴者数 / 連絡事項 / 電話スナップショットが今回入力で上書きされ、キャンセル時刻が NULL に戻る

#### Scenario: 既存 reserved 行があるときの拒否
- **WHEN** 当該イベントに `status = 'reserved'` の行を持つ会員がキャンセル待ち登録を試みる
- **THEN** 新規行は作成されず、「既に予約済み」相当の通知が表示される

### Requirement: 二重登録の防止

会員サイトは同一会員 × 同一イベントに対するキャンセル待ちの二重登録を、UI と DB 制約の両面で SHALL 防止する。

- UI: キャンセル待ち登録済み（`status = 'waitlist'`）の会員には押下可能な登録 CTA を描画 SHALL NOT し、登録済み状態を表示する。
- DB: `(event_id, member_id)` の UNIQUE 制約により、同一組み合わせの 2 行目の作成は MUST 拒否される。既存行との衝突は「キャンセル待ち行の作成と再活性化」要件に従って処理される。

#### Scenario: UI 上の二重登録抑止
- **WHEN** キャンセル待ち登録済みの会員が当該イベント詳細に再訪する
- **THEN** 押下可能なキャンセル待ち CTA は描画されず、登録済み状態が表示される

#### Scenario: DB 制約による二重行の拒否
- **WHEN** 何らかの経路で同一会員 × 同一イベントの 2 件目の `waitlist` 行 INSERT が発行される
- **THEN** UNIQUE 制約違反となり 2 行目は作成されない

### Requirement: 自己予約状態の取得

会員サイトのイベント詳細画面は、CTA 分岐を駆動するため当該会員の当該イベントに対する予約状態（`status` を含む）を SHALL 取得する。取得は当該会員自身の行のみを対象とし、RLS による行レベル制御に加えてアプリ層でも会員識別子とイベント識別子を明示的にクエリ条件へ含めて二重防衛とする MUST。当該会員の行が存在しない場合は「未登録」として扱う MUST。

#### Scenario: 自己の予約状態のみ取得
- **WHEN** 会員がイベント詳細にアクセスし、自己予約状態を取得する
- **THEN** 取得対象は当該会員自身の当該イベントに対する行のみであり、他会員の予約は含まれない

#### Scenario: 自己の行が無いときは未登録扱い
- **WHEN** 当該イベントに対して当該会員の行が存在しない
- **THEN** 自己予約状態は「未登録」として扱われ、満員時はキャンセル待ち CTA の対象となる

### Requirement: ホーム一覧でのキャンセル待ち登録済み表示

会員サイトのホーム（`/events`）の「他のイベント」リストは、当該会員がキャンセル待ち登録済み（`status='waitlist'` かつ未来）のイベント行に、その旨を示す表示を SHALL 描画する。これにより会員は一覧上で「予約済」と同様に自分のキャンセル待ち状態を識別できる MUST。

当該行は押下で当該キャンセル待ち予約の予約詳細画面（`/reservations/{reservationId}`）へ遷移する MUST。同一イベントに対して予約済み（`status='reserved'`）の表示が優先され、キャンセル待ち表示と二重には描画 SHALL NOT する。

#### Scenario: キャンセル待ち登録済み行の表示
- **WHEN** 当該会員が `status='waitlist'` かつ未来のイベントを持つ状態でホームを開く
- **THEN** 「他のイベント」の当該行にキャンセル待ち登録済みと分かる表示が描画される

#### Scenario: 予約済みが優先される
- **WHEN** 同一イベントに対して当該会員が `status='reserved'` の予約を持つ
- **THEN** 当該行には「予約済」表示のみが描画され、キャンセル待ち表示は描画されない

#### Scenario: キャンセル待ち行押下で予約詳細へ
- **WHEN** キャンセル待ち登録済み行を押下する
- **THEN** 当該キャンセル待ち予約の予約詳細画面へ遷移する

### Requirement: 満員イベントのキャンセル待ち受付ヒント（一覧）

会員サイトのホーム（`/events`）の「他のイベント」リストは、満員（`capacity` あり、かつ予約埋まり具合 >= `capacity`）のイベント行のうち、当該会員が未登録（予約済み・キャンセル待ち登録済みのいずれでもない）の行に、キャンセル待ち登録が可能であることを示すヒント表示を SHALL 描画する。これにより会員は一覧上で「満員＝行き止まり」ではなく、タップすればキャンセル待ちに登録できると認識できる MUST。

ヒントは満員チップ（「満員」）とは別の、行動を示唆する表示とする。当該会員が既に予約済み（「予約済」表示）またはキャンセル待ち登録済み（「キャンセル待ち」表示）の行には、ヒントを描画 SHALL NOT する（登録状態の表示が優先）。`capacity` NULL や満員でない行にも描画 SHALL NOT する。

#### Scenario: 満員 + 未登録行にヒントが出る
- **WHEN** 満員のイベントに対して当該会員が予約もキャンセル待ちも持たない状態でホームを開く
- **THEN** 当該行にキャンセル待ち受付中と分かるヒントが描画される

#### Scenario: 満員でない行にはヒントが出ない
- **WHEN** 残席のあるイベント、または `capacity` NULL のイベントの行を確認する
- **THEN** キャンセル待ち受付ヒントは描画されない

#### Scenario: 登録済み行にはヒントが出ない
- **WHEN** 満員のイベントに対して当該会員が予約済み、またはキャンセル待ち登録済みである
- **THEN** 当該行にはヒントではなく登録状態の表示（「予約済」/「キャンセル待ち」）が描画される

### Requirement: 登録後フィードバック

会員サイトはキャンセル待ち登録の確定成功時に、画面内フィードバックで SHALL 完結させる。登録 UI を閉じ、起動元のイベント詳細画面に留まったまま完了トーストを表示し、CTA を「キャンセル待ち登録済み」状態へ MUST 切り替える。登録完了メールは送信 SHALL NOT する。

#### Scenario: 登録成功のフィードバック
- **WHEN** キャンセル待ち登録が成功する
- **THEN** 登録 UI が閉じ、イベント詳細画面に留まったまま完了トーストが表示され、CTA が「キャンセル待ち登録済み」状態に切り替わる

#### Scenario: 登録完了メールを送らない
- **WHEN** キャンセル待ち登録が成功する
- **THEN** 予約完了 / キャンセル通知のようなメール送信は発火しない

### Requirement: 4 状態 UI の網羅

キャンセル待ち登録 UI は以下 4 状態を SHALL 持つ。

- 読み込み中（登録確定処理中）: 確定 CTA を無効化し処理中であることを伝える MUST
- 該当なし: 満員でない / `capacity` NULL でキャンセル待ち対象外のとき、登録 UI への入口（CTA）自体を描画しない MUST
- エラー（RLS 違反 / 二重登録 / ネットワーク等）: 登録 UI に留まり、エラー種別に応じた説明を表示する MUST
- 正常表示: 上記要件に従う

#### Scenario: 確定処理中の表示
- **WHEN** キャンセル待ち登録の確定処理中
- **THEN** 確定 CTA は無効化され、処理中であることがユーザーに伝わる

#### Scenario: エラー時は UI に留まる
- **WHEN** キャンセル待ち登録の確定がネットワークエラーで失敗する
- **THEN** 登録 UI に留まり、エラー説明が表示される

### Requirement: RLS とセキュリティ

キャンセル待ち登録のデータアクセスは `reservations` の RLS ポリシー（`rls-policies` capability）に SHALL 完全準拠する。会員はキャンセル待ち行を自分の会員識別子に対してのみ作成でき、他人の会員識別子を指定した作成は MUST 拒否される。会員が管理者専用ステータス（`'attended'` / `'no_show'`）を自己の行に設定する INSERT / UPDATE は MUST 拒否される。

#### Scenario: 自分のキャンセル待ち行のみ作成可能
- **WHEN** 会員が他人の会員識別子を指定してキャンセル待ち行の INSERT を試みる
- **THEN** RLS の WITH CHECK 違反で拒否され、UI にも失敗が反映される

#### Scenario: 管理者専用ステータスの自己設定は拒否
- **WHEN** 会員が自己の行に対して `status = 'attended'` の INSERT または UPDATE を試みる
- **THEN** RLS の WITH CHECK 句により拒否される

### Requirement: キャンセル待ちの取り消し

会員サイトは自分のキャンセル待ち登録を取り消す操作を SHALL 提供する。取り消しは予約履歴画面（`/history`）のキャンセル待ちグループの各行、および予約詳細画面（`/reservations/:reservationId`）の当該行から行える MUST。

取り消しは当該 `waitlist` 行を **DELETE** する MUST。キャンセル待ちは確定予約ではなく意思表明であり、撤回後に `'cancelled'` 行として履歴に残すと、キャンセルした通常予約と区別できず誤解を生む（リロード後は両者とも `status='cancelled'` で判別不能）ため、撤回は行削除で表現する。これにより撤回した待機は履歴から消え、再登録時の UNIQUE 衝突も発生しない。会員の「自分の `status='waitlist'` 行の DELETE」は `reservations` の RLS（`rls-policies` capability）で許可されている。アプリ層でも対象行が `status='waitlist'` であることを明示条件に含め、他人の行・状態不一致は 0 行削除として扱う MUST。

通常予約のキャンセルと異なり、キャンセル待ちの取り消しには開催日基準の期限ゲートを適用 SHALL NOT する（いつでも取り消せる）。取り消し時にメール通知は送信 SHALL NOT する（登録時に送っていないため対称）。

取り消しは確認ダイアログを経由する MUST。成功時は完了フィードバックを表示し、当該行を一覧から除去する MUST（履歴画面ではキャンセル待ちグループから消え、過去グループにも `'cancelled'` として現れない。予約詳細画面では履歴画面へ遷移する）。

#### Scenario: 履歴のキャンセル待ち行から取り消し
- **WHEN** 会員が `/history` のキャンセル待ちグループの行で取り消しを確定する
- **THEN** 当該 `waitlist` 行が DELETE され、行はキャンセル待ちグループから消え、過去グループにも `'cancelled'` として現れず、完了フィードバックが表示される

#### Scenario: 撤回した待機はキャンセル済みとして残らない
- **WHEN** キャンセル待ちを撤回した後に `/history` を再読み込みする
- **THEN** 当該イベントは履歴のどのグループにも現れない（DELETE により行が存在しないため、キャンセルした通常予約のように過去グループに残らない）

#### Scenario: 予約詳細からの取り消し
- **WHEN** 会員が `status='waitlist'` の予約詳細画面で「キャンセル待ちを取り消す」を確定する
- **THEN** 当該行が DELETE され、完了フィードバックののち履歴画面へ遷移する（当該予約詳細はもはや存在しない）

#### Scenario: 撤回後の再登録は UNIQUE 衝突を起こさない
- **WHEN** キャンセル待ちを撤回した同一イベントに対して再度キャンセル待ち登録する
- **THEN** 残骸行が存在しないため新規 INSERT がクリーンに成立する（再活性化経路を経由しない）

#### Scenario: 期限ゲートを適用しない
- **WHEN** 開催当日 / 開催以降であってもキャンセル待ちの取り消しを試みる
- **THEN** 期限切れ案内は表示されず、取り消しが成立する（通常予約のキャンセル期限ロジックは適用されない）

#### Scenario: 取り消し時にメールを送らない
- **WHEN** キャンセル待ちの取り消しが成功する
- **THEN** キャンセル通知のようなメール送信は発火しない

#### Scenario: 他人の行の取り消し試行
- **WHEN** 会員が他人の reservation_id を指定して `waitlist` 行の DELETE を試みる
- **THEN** RLS により 0 行削除となり、UI にエラーが表示される

### Requirement: 主要シナリオの自動テストカバレッジ

キャンセル待ち登録の主要シナリオは component test / unit test（Vitest + @vue/test-utils）レベルで SHALL 自動検証される。`apps/reservation` には E2E（Playwright）環境が現状存在しないため、本 capability では component test での代替を許容する MUST。E2E ハッピーパスは最小 1 件までとする。

検証対象シナリオ:

- 満員 + 未登録でキャンセル待ち CTA が押下可能に描画される
- 満員 + キャンセル待ち登録済みで登録済み状態が描画され、押下可能な CTA が描画されない
- `capacity` NULL では通常 CTA が維持される
- キャンセル待ち登録 UI に合計金額カードが描画されない
- 未登録からの `waitlist` 行作成が成功する
- キャンセル済み行が `waitlist` へ再活性化される
- 既存 `reserved` 行があるとき二重登録が拒否される
- 登録成功で完了トーストが表示され CTA が登録済み状態に切り替わる
- 自己予約状態の取得が当該会員の行のみを対象とする

#### Scenario: component test の整備
- **WHEN** `pnpm --filter @high-q/reservation test` を実行する
- **THEN** 上記シナリオに対応する component / unit テストが pass する

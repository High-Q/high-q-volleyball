## ADDED Requirements

### Requirement: キャンセルによる繰り上げの起動

システムは、予約がキャンセルされて枠が空いたときに、当該イベントのキャンセル待ち繰り上げ処理を SHALL 起動する。起動は会員サイト（自分の予約のキャンセル成功後）および管理画面（admin のキャンセル代行成功後）の両キャンセル経路から行う MUST。

起動は対象処理（Edge Function）への fire-and-forget 呼び出しとし、その失敗・例外はキャンセルの成立を妨げては SHALL NOT ならない。キャンセル待ちの**撤回**（`waitlist` 行の削除）は枠を空けないため、繰り上げを起動 SHALL NOT する。

#### Scenario: 会員のキャンセルで繰り上げが起動する
- **WHEN** 会員が満員イベントに対する自分の `reserved` 予約をキャンセルする
- **THEN** 当該イベントのキャンセル待ち繰り上げ処理が起動される

#### Scenario: admin のキャンセル代行で繰り上げが起動する
- **WHEN** admin が満員イベントの予約を `cancelled` に更新する
- **THEN** 当該イベントのキャンセル待ち繰り上げ処理が起動される

#### Scenario: 起動の失敗はキャンセルを妨げない
- **WHEN** 繰り上げ処理の起動呼び出しがネットワークエラー等で失敗する
- **THEN** キャンセル自体は成立し、UI にエラーは描画されない

#### Scenario: キャンセル待ちの撤回では起動しない
- **WHEN** 会員がキャンセル待ちを撤回する（`waitlist` 行を削除する）
- **THEN** 枠は空かないため繰り上げ処理は起動されない

### Requirement: 繰り上げ対象の選定（空きを埋め切る走査 + 同伴者数フィッティング）

繰り上げ処理は対象イベントについて、現在の空き容量に収まる待機者を SHALL 選定する。空き容量は `capacity` と現在の予約埋まり具合（本人＋同伴の人数ベース、`status IN ('reserved','attended')` をカウント）から `available = capacity - booked` として算出する MUST。

待機者は `status='waitlist'` の行を `created_at ASC`（最古が先頭）で **全件走査** する MUST。各待機者について、必要人数 `1 + guest_count` が残りの `available` 以下なら繰り上げ対象とし、`available` をその分減らして次の待機者へ進む。**必要人数が残りの `available` を超える待機者はスキップし、後続の待機者の評価を続ける MUST**（同伴者数が多くて収まらない人のために枠を空けたまま打ち切っては SHALL NOT ならない。後続のより少人数の待機者を繰り上げて枠を埋め切る方針とする）。`available` が 0 になる、または列を走査し切ったら終了する。

`capacity` が NULL のイベントは満員概念が成立せず待機が発生しないため、繰り上げ対象とし SHALL NOT する。

#### Scenario: 空きに収まる最古の待機者が選定される
- **WHEN** `capacity=18`、繰り上げ後の booked が 17、待機列の先頭が `guest_count=0`（必要 1 名）
- **THEN** 先頭の待機者が繰り上げ対象となる（1 <= 1）

#### Scenario: 収まらない待機者はスキップして次を繰り上げる
- **WHEN** `available=1` で、待機列が先頭から `guest_count=1`（必要 2 名）/ `guest_count=0`（必要 1 名）の順
- **THEN** 先頭はスキップされ、2 番目の待機者が繰り上げられる（後続の少人数を活用して枠を埋める）

#### Scenario: まとまった空きで複数名を順に繰り上げる
- **WHEN** `available=3` で、待機列が先頭から `guest_count=0`（必要 1）/ `guest_count=1`（必要 2）の順
- **THEN** 2 名とも繰り上げられる（1 + 2 = 3 が収まる）

#### Scenario: 残り空きに大人数が入らなければスキップして埋め切る
- **WHEN** `available=2` で、待機列が先頭から `guest_count=2`（必要 3）/ `guest_count=1`（必要 2）/ `guest_count=0`（必要 1）の順
- **THEN** 先頭（必要 3）はスキップされ、2 番目（必要 2）が繰り上げられて `available=0` となり、3 番目は繰り上げられない

#### Scenario: capacity NULL は対象外
- **WHEN** `capacity IS NULL` のイベントで繰り上げ処理が起動される
- **THEN** 繰り上げは行われない

### Requirement: waitlist から reserved への昇格

繰り上げ処理は選定した待機者の `reservations.status` を `'waitlist' → 'reserved'` に SHALL UPDATE する。本 UPDATE は service_role で実行し（昇格対象は起動者本人とは別の会員であり得るため）、`guest_count` / `note` / `phone_at_booking` のスナップショットは保持する MUST（登録時の値を引き継ぐ）。

昇格により当該会員の予約は通常の `reserved` 予約と同等に扱われる（履歴の予約中グループ・NEXT カード・キャンセル動線の対象となる）MUST。

#### Scenario: 昇格で status が reserved になる
- **WHEN** 待機者が繰り上げ対象として選定される
- **THEN** 当該行の `status` が `'reserved'` に更新され、`guest_count` / `note` は登録時の値が保持される

#### Scenario: 昇格後は通常予約として扱われる
- **WHEN** 会員が繰り上げ後にホーム / 履歴を開く
- **THEN** 当該予約は予約中（`reserved` 未来）として表示され、キャンセル動線の対象となる

### Requirement: 繰り上げ通知メール（システム起点）

繰り上げ処理は昇格した各会員に対し、繰り上げ成立を伝える通知メールを SHALL 送信する。本メールは昇格した本人以外の操作（他会員のキャンセル / admin のキャンセル代行）で発火するシステム起点の送信であり、呼び出し元 JWT の本人検証を行う既存の自己宛通知経路 (`send-reservation-notification`) を流用 SHALL NOT する。送信先は昇格した会員の `members.email` を service_role で引いて決定する MUST。

メール本文は、キャンセル待ちから繰り上がり予約が確定したこと、イベント情報（名称・日時・会場・参加費）、当日連絡の LINE オープンチャット導線を含む MUST。メール送信の失敗は昇格の成立を取り消しては SHALL NOT ならない（昇格は成立させ、失敗はログに記録する）。複数名を昇格する場合、1 件の送信失敗が他の昇格・送信を妨げては SHALL NOT ならない。

#### Scenario: 昇格した会員に繰り上げメールが届く
- **WHEN** 待機者が繰り上げで `reserved` に昇格する
- **THEN** 当該会員のメールアドレス宛に、繰り上げ確定とイベント情報・LINE 導線を含む通知メールが送られる

#### Scenario: メール送信失敗でも昇格は成立する
- **WHEN** 昇格は成功したがメール送信が SMTP エラーで失敗する
- **THEN** 当該会員の `status` は `'reserved'` のまま保たれ、失敗はログに記録される

#### Scenario: 1 件の送信失敗が他の昇格を妨げない
- **WHEN** 複数名を昇格する途中で 1 件のメール送信が失敗する
- **THEN** 他の会員の昇格とメール送信は継続される

### Requirement: 冪等性とセキュリティ

繰り上げ処理は冪等である MUST: 現在の空き容量に基づいて昇格するため、重複起動しても既に枠が埋まっていれば何も昇格 SHALL NOT する。処理の昇格 UPDATE は service_role で行い、クライアントへ service_role キーを露出しては SHALL NOT ならない。起動（Edge Function 呼び出し）は認証済みユーザーに限定する MUST。認証済みユーザーが本処理を不正に連打しても、空き容量に収まる待機者しか昇格しないため、capacity を超える過剰昇格が発生しては SHALL NOT ならない（並行起動時の soft-capacity 超過は別要件で扱う）。

#### Scenario: 重複起動は二重昇格しない
- **WHEN** 同一イベントに対して繰り上げ処理が枠が埋まった状態で再度起動される
- **THEN** 昇格は発生しない

#### Scenario: service_role はクライアントに露出しない
- **WHEN** クライアント側コードを確認する
- **THEN** 繰り上げの昇格 UPDATE は Edge Function 内（service_role）でのみ行われ、クライアントに service_role キーは存在しない

### Requirement: 並行キャンセル時の soft-capacity 方針

システムは、同一イベントへの並行キャンセルにより繰り上げ処理が並走した場合に、capacity を一時的に超える昇格が起こり得ることを MUST 許容する（既存の予約 INSERT も capacity を DB レベルで強制しない soft 制約のため、整合性方針を変えない）。本 change では DB レベルの capacity 強制 / advisory lock による厳格化は導入 SHALL NOT する。厳格化は将来課題とする。

#### Scenario: 並行起動での超過は許容される
- **WHEN** 同一イベントへの複数キャンセルがほぼ同時に発生し、繰り上げ処理が並走する
- **THEN** 一時的に capacity を超える昇格が起こり得るが、システムはこれを許容する（hard エラーにはしない）

### Requirement: 管理画面のキャンセル待ち可視化（read-only タブ）

管理画面のイベント詳細画面は「キャンセル待ち」タブを有効化し、当該イベントの待機者一覧を read-only で SHALL 表示する。一覧は `status='waitlist'` の予約のみを `created_at ASC`（＝繰り上げ順）で並べ、各行に登録順・会員表示名・同伴者数（および本人＋同伴の計人数）・登録日時を表示する MUST。

本タブは read-only とし、手動繰り上げ・上書き等の操作 UI は提供 SHALL NOT する（繰り上げはキャンセル発生時に自動実行されるため、本タブの目的は「誰が待っているか」の可視化に限定する）。「当日チェックイン」タブは本 change の対象外であり、無効状態を維持する MUST。

「参加者一覧」タブは実参加者（`status IN ('reserved','attended','no_show')`）のみを表示し、`status='waitlist'` の待機者を含めては SHALL NOT ならない（待機者は本「キャンセル待ち」タブに集約する）。これにより参加者一覧でキャンセル待ちが予約済みと混在して見分けがつかない事態を避け、待機者に対する無意味なチェックイン操作も排除する。

待機者 0 件のときは空状態（「キャンセル待ちはいません」相当）を表示する MUST。取得失敗時はエラー表示と再試行操作を SHALL 提示する。

#### Scenario: キャンセル待ちタブに待機者が登録順で並ぶ
- **WHEN** admin が満員イベント詳細で「キャンセル待ち」タブを開く
- **THEN** `status='waitlist'` の待機者が `created_at` 昇順（繰り上げ順）で、表示名・同伴者数・計人数・登録日時とともに表示される

#### Scenario: 予約済み等は混ざらない
- **WHEN** イベントに reserved / attended / waitlist が混在する
- **THEN** キャンセル待ちタブには `waitlist` の行のみが表示される

#### Scenario: 待機者 0 件
- **WHEN** キャンセル待ちが 0 件のイベントで本タブを開く
- **THEN** 「キャンセル待ちはいません」相当の空状態が表示される

#### Scenario: 待機者がいるとき件数を強調する
- **WHEN** イベントにキャンセル待ちが 1 名以上いる
- **THEN** 「キャンセル待ち」タブの件数が強調表示（accent）される。0 名のときは通常表示

#### Scenario: 当日チェックインタブは無効のまま
- **WHEN** イベント詳細のタブを確認する
- **THEN** 「当日チェックイン」タブは無効状態であり、本 change では有効化されない

#### Scenario: 参加者一覧にキャンセル待ちが混ざらない
- **WHEN** reserved / attended / waitlist が混在するイベントで「参加者一覧」タブを開く
- **THEN** `waitlist` の行は表示されず、実参加者のみが並ぶ（待機者はキャンセル待ちタブで確認する）

### Requirement: テストカバレッジ

繰り上げの選定ロジック（FIFO + 同伴者数フィッティング）は unit test レベルで SHALL 検証される。検証対象:

- 空きに収まる最古の待機者が選定される
- 収まらない待機者はスキップして後続を繰り上げる（空きを埋め切る）
- 残り空きに大人数が入らなければスキップして埋め切る
- まとまった空きで複数名が順に繰り上がる
- `capacity NULL` は対象外
- 空き 0 のとき昇格 0

Edge Function の昇格 + メール送信の結合は、可能な範囲で検証する MUST（送信失敗が昇格を妨げないこと、本人検証を伴わずシステム起点で送ること）。

#### Scenario: 選定ロジックの unit test
- **WHEN** 繰り上げ選定の純関数を各ケースで実行する
- **THEN** 上記シナリオに対応するテストが pass する

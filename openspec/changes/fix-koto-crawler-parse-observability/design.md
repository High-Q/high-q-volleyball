## Context

江東区スポーツネット crawler（`packages/court-crawler`）は 20 分間隔で稼働しているが、本番の全 run が「読めたグリッド日数 39 / 新規通知 0 / 記録解除 0」で推移し、空き枠を一件も検知できていない。監視絞り込みを外した run（全室場対象）でも 0 件のため、監視室場フィルタや土日祝フィルタは原因から排除できている。ログイン〜結果グリッド表示までは到達しており、グリッドの器（時間帯の列・会場の行）は取得できている（グリッド判定は 39 日分すべて成立）。にもかかわらず「空き」セルだけを 0 件しか抽出できていない。

重要な既知事実として、driver のコメント通り**空きセルの見た目（○）はサーバが返す HTML には無く、描画スクリプトが hidden 入力から計算して後付けする**。つまり原因は「パースのセレクタが実 DOM と食い違っている」か「描画が終わる前に HTML を読んでいる（タイミング）」のどちらかに絞られる。現時点で実 HTML を手元に持っていないため、**まず本番の実 HTML を取得して切り分ける**ことが起点になる。

現状のコアは施設非依存の crawl オーケストレーションと江東区アダプタ（照会 driver + パース）に分離済みで、パース関数は「時間帯 = 見出し行 / 会場 = 行頭 / 空き = 特定 class のセル」という前提で書かれている（合成 fixture ではこの前提で緑）。

### 診断結果（実 HTML ダンプ・2026-08-11 実施で確定）

診断モード（KOTO_DIAGNOSE）で本番 39 日分の構造を sanitize ダンプし、**独立した 2 つの根本原因**を特定した:

- **原因 A（パース・空きシグナル）**: 空きセルの `class="ok"` が実サイトから**消滅**していた。予約可能な枠は `class` を持たず（`classes:[]`）、**予約ボタン画像（`timetable-o.gif`）+ `onclick` のみ**で表現される。埋まり（`ng`）class は健在。パーサが `class="ok"` を探すため、空きを永久に 0 件と誤判定していた。→ 決定 2 の仮説が的中。
- **原因 B（driver・検索スコープ）**: 結果グリッドが 39 日すべて**「スポーツ会館 大体育室 全面」の 1 行のみ**で、監視対象の 6 施設・「半面」室場が一つも含まれていない。`openVolleyballGrid` の「施設 全選択 / 室場 全選択」が効いておらず、既定の 1 施設・1 室場しか検索できていない。ground truth（8/11 東砂スポーツセンター 大体育室 半面 18:00-21:30 の空き）はグリッドに存在すらしなかった。原因 A だけ直しても監視スコープ（大体育室 半面）は 0 件のままで通知は届かない。

## Goals / Non-Goals

**Goals:**
- 本番実 HTML を取得し、空き枠を 0 件しか拾えない根本原因（セレクタ不一致 / 読み取りタイミング）を一次データで特定する
- 特定した食い違いに合わせ、空き枠抽出（必要なら日ごとのグリッド確定待ち）を根本修正する
- 実 HTML を PII・セッション情報除去済みの回帰 fixture にし、再発を止めるテストを追加する
- 「グリッドは取れているのに空きが 0 件」という静かな失敗を、Sentry 設定の有無にかかわらず気づける観測性にする
- 修正後、空き枠が実在する状態で LINE 通知が届くことを実 run で確認する

**Non-Goals:**
- Bumb アダプタ（#287）の実装（本修正のパース改善が波及する前提は保つが実装はしない）
- crawl 間隔・politeness・通知メッセージ整形・監視室場スコープの変更
- 通知履歴ストアのスキーマ変更

## Decisions

### 決定 1: 修正前に実 HTML を一次データで診断する（推測で直さない）
不具合修正は応急手当て禁止・根本原因起点の原則に従い、パースを当てずっぽうで書き換えない。fix ブランチに**副作用のない診断モード**（LINE 送信・ストア更新をせず、対象日のグリッド構造だけを安全に出力）を一時追加し、既存 workflow の手動 dispatch（feature branch から実行可）で本番実 HTML の構造を採取する。空きが実在する日（直近の土日祝）を狙い、複数日分をダンプして「その日のセル class 分布 / 空きボタンの持ち方」を観測する。

- **出力は sanitize する**: HTML 全文を生ログしない。会場名・時刻・セルのタグ名 / class / 空き判定に使えるシグナル（予約ボタン画像・onclick の有無）だけを構造として出す。認証情報・セッション ID・個人情報は出力しない。
- 代替案（棄却）: fixture を眺めて推測修正 → 過去にパースずれで本番 0 件を出した実績があり、一次データなしの修正は再発リスクが高い。

### 決定 2: 空き判定を予約導線シグナルに寄せる（原因 A の修正・診断で確定）
診断で `class="ok"` の消滅が確定したため、空きセルの判定を class 名依存から**予約導線そのもの（空きに現れる予約ボタン画像 `timetable-o.gif` / その `onclick`）**という意味的シグナルへ切り替える。これにより class 名がまた変わっても空きが取れなくなりにくい。埋まり（`ng`）は明示 class が健在なので、空き = 予約導線あり、埋まり/対象外 = 予約導線なし、で判定する（記号テキストにも依存しない）。

- 代替案（棄却）: 新しい class 名に貼り替える → 実サイトは空きに class を付けなくなったため貼り替え先が無い。また同種の class 変化で再度静かに 0 化する。予約導線シグナルの方が堅い。

### 決定 3: 読み取りタイミング説は棄却（診断で確定）
当初の仮説「日送り後にセル描画が追いつかず空きが読めない」は、診断で棄却した。ダンプでは各日とも `ng` class・予約画像が正しく描画済みで観測できており、読み取りタイミングは原因ではない。したがって日ごとの追加待機は入れない（不要な変更を避け、politeness を維持する）。

### 決定 8: 検索スコープの取りこぼし（原因 B）を driver で根治する
結果グリッドに監視対象（6 施設 × 大体育室 半面）が現れず、既定の 1 施設・1 室場（スポーツ会館 大体育室 全面）しか出ていない。`openVolleyballGrid` の「施設 全選択 / 室場 全選択」の実操作が実サイトで意図どおり効いていないためで、**もう一段の診断**（施設選択後・室場選択後の選択状態と、結果グリッドの行数を sanitize ダンプ）で「どのステップで全選択が落ちているか」を特定してから修正する。推測で全選択のセレクタを差し替えない。

- 監視スコープの唯一の正は `isMonitoredVenue`（大体育室 && 半面）。driver 修正後、少なくとも監視対象施設の「大体育室 半面」行が結果グリッドに現れることを ground truth（8/11 東砂 半面）で確認する。
- 代替案（棄却）: 施設ごとに 6 回検索を回す → サイト負荷増・実装複雑化。まず「全選択が効かない原因」を診断で突き止め、1 検索で全施設を並べる本来の導線を直す方が筋が良い（負荷面でも有利）。

### 決定 4: 結果サマリに「空き検知 funnel」を通す（観測性の核）
crawl 結果に段階ごとの件数を必ず載せ、GitHub Actions のログ・job summary に出す:

1. 読めたグリッド日数
2. **絞り込み前に抽出した生の空き枠数**（新規・最重要指標）
3. 監視室場フィルタ後の枠数
4. 土日祝・リードタイム絞り込み後（＝通知候補）の枠数
5. 新規通知した枠数 / 記録解除した枠数

これにより「どの段で 0 に落ちたか」が一目で分かる。今回のように生の空き枠が 0 なら「パース／読み取りの問題」、生は取れているのに通知が 0 なら「フィルタ・重複排除の問題」と切り分けられる。

### 決定 5: 「静かな 0」を単一 run のヒューリスティックで異常化する（横断状態を持たない）
グリッドは複数日読めているのに**絞り込み前の生の空き枠が 0 件**なら、それ自体を異常として記録する。監視は 6 施設 × 多日の土日祝を横断して見るため、全施設・全時間帯が丸ごと埋まって生の空きが厳密に 0 になることは実運用上ほぼ起きない。したがって「読めたグリッド日数 > 0 かつ 生の空き枠数 = 0」を単一 run で異常として送る（従来の失敗種別を活かしつつ、グリッド 0 件とは文言・context で区別する）。

- 代替案（棄却 / 将来余地）: 「N run 連続で 0」を永続カウンタで判定 → 横断状態の持ち回りが必要で、MVP には過剰。生の空き枠を絞り込み前に見る本ヒューリスティックはステートレスで十分強い。誤検知が問題化したら将来「連続 N 日」等に閾値調整する。

### 決定 6: 送出先未設定でも気づけるよう二段構えにする
- **DSN 非依存**: 決定 4 の funnel と決定 5 の異常を GitHub Actions の job summary に必ず出す。Sentry を設定していなくても run 一覧で「生 0」バナーが見える。
- **DSN 推奨設定**: あわせて Sentry 送出先の設定を運用手順として明記し、設定を推奨する（アラート通知の常設化）。

### 決定 7: 診断用の一時コードは同 PR 内で除去、恒久観測だけ残す
決定 1 の診断モードは切り分け専用の足場であり、原因特定後は同 PR 内で撤去する。恒久的に残すのは funnel（決定 4）と静かな 0 の異常化（決定 5）のみ。生 HTML をログに残す経路は本番に残さない。

## Risks / Trade-offs

- **診断時に本当に空きが 0（閑散期・全埋まり）だと切り分け不能** → 空きが実在すると確認できる直近の土日祝を狙って dispatch し、複数日をダンプする。Issue に実在例（山の日・東砂スポーツセンター 大体育室 半面）があるので基準日に使える。
- **画像 / onclick シグナルへ寄せると、空きの別表現（改装中・貸出区分なし）に対する誤判定リスク** → 実 HTML で「空き」「埋まり」「対象外」の三態それぞれの見た目を確認し、空きの正シグナルと除外シグナルの両面を fixture に固定する。
- **静かな 0 の異常化が閑散期に誤検知** → 6 施設横断・多日での生 0 は実質起きない前提を明記。運用で誤検知が続く場合のみ「連続 run」閾値へ格上げする（将来余地として記録）。
- **診断ダンプの PII / セッション情報漏れ** → content 全文は出さず、タグ名・class・時刻・会場名・空きシグナル有無だけを sanitizer 経由で出力。認証情報・g_sessionid は対象外。
- **feature branch dispatch は本番 Secrets を使う** → 診断モードは読み取りのみで LINE 送信・ストア更新をしない副作用ゼロ設計にし、本番運用への影響を出さない。

## Migration Plan

- パース／driver／サマリの修正のみで、DB スキーマ・データ移行は無い。
- ロールバックは revert のみ（通知履歴ストアや外部契約に不可逆変更を持ち込まない）。
- 手順: fix ブランチで診断モード追加 → dispatch で実 HTML 採取 → 原因特定 → パース/driver 修正 + fixture/回帰テスト + funnel/異常化 → 診断モード撤去 → CI 緑 → dispatch で実 run し LINE 到達確認 → ship。

## Open Questions

- Sentry 送出先（`KOTO_SENTRY_DSN`）を今回あわせて実設定するか、job summary の可視化で当面運用するか — 決定 6 の二段構えを前提に、設定するかどうかは翔太郎くんの判断を仰ぐ（推奨は設定）。

## Context

予約サイトの予約完了 / キャンセル経路は完成しているが、会員にメール通知を返す手段が存在しない。Epic #170 のユーザージャーニーで前提となっている「メールで受け取った情報を当日朝に見返して会場へ向かう」体験が成立しておらず、その結果として LINE オープンチャットへの当日連絡経路も会員側で失われやすい状態が続いている。

一方、Supabase 側は signup フローで Gmail SMTP + nodemailer 構成の送信ヘルパー（`supabase/functions/_shared/mailer.ts`）を既に稼働させており、Edge Function から日本語本文を送信する基盤は揃っている。本 change はこの既存基盤の上に予約系の送信パスを足す範囲にとどめる。

Phase 2 で独自ドメイン取得 + Resend 移行が予定されている（参考: #183）ため、本 change のメール送信抽象は「将来 Resend 等への差し替えで送信元コードに影響が出ない」粒度に保つ。

## Goals / Non-Goals

**Goals:**
- 予約成立 / 予約キャンセルの 2 イベントで、会員が当日朝に必要とする情報を含むメールを自動配信する
- 送信失敗が予約成立そのものを妨げない（会員の操作完了を遅延・失敗にしない）構造にする
- 既存 signup 送信パスとの実装重複を避け、共有ヘルパー層に文面レンダラを足す形に統一する
- メール本文は Phase 2 で HTML / ドメイン変更が起きてもレンダラ層で差し替え可能な抽象に保つ

**Non-Goals:**
- 開催前リマインダーメール（別 Issue）
- カレンダー添付 (.ics) ファイルの同梱
- HTML メール / マルチパート対応（テキストのみ）
- 独自ドメイン取得 / Resend 移行 / Auth テンプレートの HQ デザイン化
- 一斉メール（#153）/ 通知設定 UI（#157）との連携
- 送信失敗時の自動リトライ・キュー機構 / 送信ログテーブル化

## Decisions

### Decision 1: 送信トリガーは「アプリ層の予約確定経路から fire-and-forget で Edge Function を呼ぶ」

**選定理由:**
- 予約確定 / キャンセル成立は会員が CTA を押した直後の限定的なタイミングであり、現状のアプリ層 composable（`useReserveBooking` / `useCancelBooking`）から成功後に Edge Function を fetch する形が最短経路
- メール送信失敗が予約成立を妨げない設計のため、呼び出しは await しない（または await + 例外を握りつぶしてログのみ）
- Edge Function 側で会員 ID / 予約 ID から最新情報を SELECT し直すため、アプリ層が大きなペイロードを渡す必要がない

**却下した案:**
- DB トリガー + `pg_net` / Supabase Database Webhook で `reservations` の INSERT / UPDATE をフックする案: 再活性化（cancelled → reserved）のフックが UPDATE で発火するため検知ロジックがやや込み入る。また「予約成立」と「メール送信」の責務境界が DB に染み出すと、後で送信先選別ロジック（通知設定 #157 等）を入れにくい。Phase 2 で通知設定が増えるなら最初からアプリ層に置く方が拡張余地が広い

### Decision 2: Edge Function は 1 本にまとめ、`event_type` で完了 / キャンセルを分岐する

**選定理由:**
- 受け取るペイロード（会員 ID / 予約 ID）は完了とキャンセルで同形。SELECT する関連エンティティ（events / venues / members / reservations）も共通
- 文面レンダラと送信本体は `_shared` に切り出すため、関数本体は薄い分岐に収まる
- function 数が増えると Supabase の deploy 単位・secret 管理単位が増える。1 本に集約する方が運用・観測容易

**却下した案:**
- 完了用 / キャンセル用に function を分ける案: 責務が明確になるメリットはあるが、deploy / secret / CORS / 認証 の重複コストが上回る

### Decision 3: 送信失敗は予約成立を妨げない（ベストエフォート）。失敗はログに残し、UI には出さない

**選定理由:**
- 予約完了画面に既に情報は出ているため、メール未着 = 予約未成立ではない。UI でメール送信エラーを赤く出すと会員の不安を煽る
- Gmail SMTP は短時間の送信スパイクや Google 側の一時 4xx で散発的に失敗する。これを UI に通知すると会員のリトライ操作で重複送信を誘発する
- 再送機構は Phase 2 で「管理画面から手動再送」を別 Issue として切り出す方が筋

**却下した案:**
- 送信成功を確認してから完了画面に遷移する案: 応答時間が SMTP 側に律速され、UX が著しく悪化する
- 送信失敗時にローカル再試行をかける案: 重複送信のリスクが大きく、MVP1 のスコープを越える

### Decision 4: 完了画面に「予約完了メールをお送りしました」相当の薄い案内を含める

**選定理由:**
- 会員が「迷惑メールに入っていないか」を能動的に確認する手がかりとして必要
- 案内は予約番号や会場情報の下に 1 行で添えるだけにし、UI を圧迫しない
- 既存 spec は「メール文言を含めない MUST NOT」と書かれていたが、メール送信パスが存在する前提に変わるため当該記述は更新する

**却下した案:**
- 完了画面に何も書かない案: メールが届かなかった会員（迷惑メール / アドレスタイポ）に救済の手がかりがない
- 「届かない場合は LINE オープンチャットへ」を完了画面に併記する案: 既に LINE 動線は別アクションとして出ているため、メール文言に重ねるとノイズになる

### Decision 5: 送信ヘルパーは既存 `_shared/mailer.ts` に文面レンダラを足す形で拡張

**選定理由:**
- 既存 `loadMailEnv()` / `sendMail()` がそのまま流用可能
- `renderSignupCodeMail` と同じ命名規則で `renderReservationConfirmedMail` / `renderReservationCancelledMail` を追加する形が一貫
- レンダラを純粋関数として独立させると、unit test が容易（DB / SMTP モック不要で文面検証できる）

**却下した案:**
- 文面を Edge Function 本体に埋める案: テスト・再利用性が落ちる
- 別ファイルに mailer 2 系統を作る案: 既存資産との重複を生む

## Risks / Trade-offs

- **[リスク] Gmail SMTP の送信レート制限（日 500 通）に予約数の増加で到達する可能性** → Mitigation: MVP1 期間の見込みは月数百通で余裕がある。到達兆候を捕捉できるように Edge Function の成功 / 失敗ログにタイムスタンプと会員 ID を残し、超過時は Phase 2 (Resend) 移行を前倒しできる体制にする
- **[リスク] 送信元が `@gmail.com` のため迷惑メール判定が起きやすい** → Mitigation: 完了画面に「メールが届かない場合は迷惑メールフォルダもご確認ください」相当の薄い案内を添える。本格対策は Phase 2 の独自ドメイン取得時に DKIM / SPF / DMARC で行う
- **[リスク] アプリ層 fire-and-forget は Edge Function 呼び出し自体がネットワーク失敗した場合の再送がない** → Mitigation: MVP1 では受け入れる。Phase 2 で送信ログテーブル + 再送 UI を別 Issue として切り出す
- **[リスク] 再活性化（cancelled → reserved）時にもう 1 通完了メールが送られると、会員が違和感を持つ可能性** → Mitigation: 再活性化は会員自身の意思操作（過去のキャンセル予約を上書き予約する明示的フロー）であるため、本人の操作直後のメールは「予約完了」として整合する。文面は同一テンプレートで良いと判断
- **[リスク] テスト環境 (dev / preview) からも本番 Gmail 経由でメールが送られると、会員に意図せぬメールが届く** → Mitigation: Edge Function 起動時の環境変数で「送信先を許可リスト宛のみに制限する dry-run モード」を切り替えられるようにする（具体的な変数名・挙動は tasks.md で決める）

## Migration Plan

- 本 change は新規 capability の追加と既存 capability の Scenario 軽微修正のため、データ移行や RLS 変更は発生しない
- 既存予約 / 過去予約への遡及送信は行わない（適用は change ship 以降の新規 INSERT / cancel UPDATE から）
- ロールバックは Edge Function を未呼び出しに戻すだけで成立する（予約成立は影響を受けない）

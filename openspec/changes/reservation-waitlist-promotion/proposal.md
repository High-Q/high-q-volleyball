## Why

#344 で満員イベントへのキャンセル待ち登録・撤回・可視化は実装したが、**枠が空いたときに待機者を繰り上げる仕組みが無い**。予約がキャンセルされても、誰も通知されず（オーナーも会員も）、待機者を予約成立（`reserved`）にしてあげる経路も存在しない。結果、会員はキャンセル待ちに入っても音沙汰なしとなり、登録時の「空きが出た場合に繰り上げのご連絡をします」という案内が果たせない。

本 change はこのループを閉じる: **キャンセルで枠が空いたら、最古の待機者を自動で予約成立に昇格し、繰り上げ通知メールを送る**。#344（登録側）と stack して 1 PR で同時出荷し、本番にキャンセル待ち CTA が出る時点で繰り上げが機能している状態にする。

## What Changes

- 予約がキャンセルされて枠が空いたとき、当該イベントのキャンセル待ちから待機者を自動で `reserved` に昇格する。昇格判定は **同伴者数込み**（本人＋同伴 = `1 + guest_count` 名分が空きに収まる場合に昇格）。
- 昇格判定は **「空きを埋め切る」方式**: 待機列を最古から全員スキャンし、残りの空きに `1 + guest_count` が収まる人を順に昇格する。**同伴者数が多くて空きに収まらない人はスキップし、後続のより少人数の待機者を昇格** して枠を活用する（半端な空きを残さない方針）。空きが埋まる（または列を走査し切る）まで続ける。
- 昇格した会員に **繰り上げ通知メール** を送る。このメールはシステム起点（昇格した本人以外の操作で発火）であり、既存の自己宛通知 (`send-reservation-notification`) は呼び出し元 JWT の本人検証を行うため流用できない。**新規の system 起点 Edge Function** で送信する。メール送信の失敗は昇格の成立を妨げない。
- 繰り上げ処理は、会員サイト（自分の予約キャンセル）・管理画面（キャンセル代行）の **両方のキャンセル経路から起動** される。
- 凝った管理画面の手動繰り上げ・上書き UI は本 change のスコープ外（admin のキャンセル待ち人数表示は既存。手動操作は後続）。

## Capabilities

### New Capabilities

- `reservation-waitlist-promotion`: キャンセルで空いた枠への自動繰り上げの振る舞いを規定する。繰り上げ対象の選定（最古の待機者・`1 + guest_count` の枠フィッティング・厳格 FIFO）、`waitlist → reserved` への昇格、繰り上げ通知メール（システム起点）、キャンセル経路からの起動、冪等性・失敗時の安全性を含む。

## Impact

- 影響コード: 繰り上げを行う server 側処理（Supabase Edge Function、service_role）。会員サイト・管理画面のキャンセル成功後に繰り上げを起動する fire-and-forget 呼び出しの追加。繰り上げ通知メールのテンプレート追加。
- DB / セキュリティ: 昇格は Edge Function が service_role で `reservations.status` を `waitlist → reserved` に UPDATE する（RLS bypass）。テーブル列・スキーマ変更は無し。capacity の DB レベル強制は本 change でも導入しない（既存どおり集計 view + アプリ層の soft 制約を維持）。
- 連携: #344（登録側）と stack して同時出荷する。両者で 1 つの完結したキャンセル待ち機能となる。メール配信は既存の Gmail SMTP 基盤 (`_shared/mailer`) を流用する。
- 通知: 繰り上げ通知メールを新設（`confirmed` / `cancelled` / `updated` に続く 4 種類目の通知シナリオ）。

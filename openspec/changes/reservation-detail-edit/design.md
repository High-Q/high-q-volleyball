## Context

#213 で完成した予約詳細画面 (`/reservations/:reservationId`) はキャンセル動線のみを備え、同伴者数・連絡事項の後追い修正手段がない。当日「同伴者 1 名が来られなくなった」場合に予約全体をキャンセル → 再予約しなければならず、ユーザー体験上の負荷が大きい。一方で、新規予約時には既に Bottom Sheet で確認 UI（同伴者数 stepper・連絡事項 textarea・合計金額カード）が提供されており、その意匠と入力体験を**そのまま編集動線にも転用すれば設計コストを抑えつつ UX の一貫性も確保**できる。

本設計の論点は以下に集約される:

1. 既存の確認 sheet と編集 sheet を物理的にどう共有するか（同一コンポーネントのモード切替か、別コンポーネントか）
2. 編集可能期限とキャンセル可能期限の関係をどう定義するか
3. 「変更なし保存」抑止と localStorage 復元の扱い
4. UPDATE のサーバー側経路（直接 Supabase クエリ vs エッジ関数）と RLS 整合性

## Goals / Non-Goals

**Goals:**
- 予約詳細画面から同伴者数・連絡事項を後追い修正できる動線を提供し、当日キャンセル → 再予約の手間を解消する
- 新規予約時の確認 sheet と編集 sheet の意匠・入力体験を完全に共通化し、ユーザーが「同じ操作で同じことができる」と認識できる状態にする
- 編集可能期限をキャンセル可能期限と同一にし、「キャンセルできる予約 = 編集できる予約」とユーザーへ説明できる単純なルールに統一する

**Non-Goals:**
- 予約日時 / 会場 / イベント自体 / 経験レベル の変更（キャンセル → 再予約で対応する設計を維持）
- メール通知 / .ics 再生成 / カレンダー連動（MVP1 全体スコープアウト方針を維持）
- 編集履歴の監査ログ保存（admin 側で必要になった時点で別 capability として検討）
- 当日 0:00 JST 以降の編集動線（LINE オープンチャットへの導線一元化方針を維持）
- 予約 sheet の localStorage 復元仕様の編集モードへの拡張（編集モードでは復元しない）

## Decisions

### 1. 確認 sheet と編集 sheet の共通化方式

**採用**: 既存の Booking Sheet コンポーネントに「mode」概念を導入し、`create` / `edit` の二択で初期値供給元・kicker 文言・CTA ラベル・確定処理経路を切り替える。

**代替案**: 編集専用の別コンポーネントを `features/booking` 配下に新設する案も検討した。実装の独立性は高くなるが、stepper / textarea / 合計金額カード / sheet 表示制御が完全に二重化され、片方だけデザイントークン更新が漏れるリスクが残る。本サービスの規模では共通化のメリット（デザイン保守・a11y 対応・テスト資産の共有）が独立化のメリット（責務分離）を明確に上回ると判断。

**Mode による主な差分**:

| 項目 | create モード | edit モード |
|---|---|---|
| 初期値 | localStorage 復元 → 空欄 | サーバーから取得した現在値 |
| Kicker 文言 | 確認系（内容に間違いがないか） | 編集系（変更したい箇所を編集） |
| 確定 CTA ラベル | 「予約を確定する」 | 「変更を保存する」 |
| 確定経路 | reservations への INSERT (UNIQUE 衝突時は cancelled 行を再活性化) | 自分の `status='reserved'` 行への UPDATE |
| 成功遷移 | 完了画面 (`booking-done`) へ `router.push` | sheet を閉じて詳細画面に留まる + 完了トースト |
| ローカル保持 | localStorage 復元あり | 復元なし（毎回サーバー値で初期化） |

### 2. 編集可能期限の定義

**採用**: 編集可能期限はキャンセル可能期限と完全一致させ、JST カレンダー基準で「`now の JST 日 < events.start_at の JST 日`」（= 開催前日 23:59 JST まで）のときのみ可能とする。判定関数も `useCancelBooking.isCancellable` をそのまま流用し、`useEditBooking` 側で**新規関数を作らない**。

**代替案**: Issue 本文の `events.start_at > now()`（= 開催開始まで編集可）案も検討。当日 1 名減らしたいケースに UI 内で対応できるメリットはあるが、キャンセル不可の予約だけ編集可になる UX の歪みと、当日連絡を LINE に集約してきた従来方針との不整合が大きく、却下。

「キャンセル可能 = 編集可能 = 開催前日まで」と一直線に説明できる単純さを最優先する。期限超過時の表示文言・LINE オープンチャット誘導も既存キャンセル不可ダイアログと整合させ、ユーザーから見て「期限切れの後追い操作はすべて LINE に集約」と受け取れる構造にする。

### 3. 「変更なし保存」抑制

**採用**: 編集モードでは初期値（サーバー由来）と現在の入力値を浅く比較し、両フィールドとも同一であれば保存 CTA を非活性とする。差分が一つでもあれば活性化する。

**理由**: 不要な UPDATE を発行しないことでサーバー負荷と監査観点の汚染を防ぎつつ、ユーザーに「変更がない状態では保存しても何も起きない」ことを CTA の状態だけで伝えられる。エラーメッセージで弾く方式（押した後で「変更がありません」と返す）と比べ、未然に手を止めさせるほうが UX 上明らかに優れる。

### 4. localStorage 復元の扱い

**採用**: 編集モードでは localStorage 復元を行わず、sheet を開いた時点で必ずサーバーから取得した現在値で初期化する。閉じた時点でも localStorage への保存を行わない。

**理由**: 編集対象の正本は DB 側であり、ローカルに古い入力を残すと「サーバーが既に変わっているのに古いローカル値が表示される」混乱を招く。新規予約 sheet が localStorage を使うのは「INSERT 前の入力中断を許容する」目的であり、編集モードでは中断しても DB が無傷なため復元の必然性自体がない。

### 5. UPDATE 経路と RLS 整合

**採用**: クライアントから直接 Supabase クライアント経由で `reservations` 行を UPDATE する。エッジ関数は経由しない。`reservations` テーブルの既存 UPDATE RLS ポリシー（自分の `status='reserved'` 行のみ UPDATE 可）に依存する。アプリ層クエリでも `member_id = auth.uid()` AND `status = 'reserved'` を明示的に WHERE 句に含めて二重防衛する。

**確認事項（Apply 時に検証）**: 既存 UPDATE ポリシーが `guest_count` / `note` の更新を実際に許容するかを実 DB で確認する。キャンセル動線のみを想定した制約（例: 「`status` 列の更新時のみ通す」）が入っている場合、ポリシーを `guest_count` / `note` も含めて許可するよう拡張する必要がある。Design 段階では「ポリシーが想定通りに動く前提で進めるが、Apply の早い段階で検証する」と明記しておく。

### 6. 編集 CTA の配置と文言

**採用**: 予約詳細画面の Meta テーブル直下に「予約内容を変更する」ラベルの CTA を配置する。視覚的な強さはキャンセル CTA より控えめ（neutral / outlined 系）にし、画面末尾のキャンセル CTA（destructive）と階層を明確に分ける。

**代替案**: 「同伴者数・連絡事項を変更する」「同伴者を変更する」などの長文 / 限定文言も検討したが、編集対象が増えにくいこと（MVP1 では 2 項目固定）と、ユーザーが「予約内容＝同伴者数・連絡事項」と直感的に対応付けやすいことから「予約内容を変更する」に統一。Sheet を開いた段階で何が編集可能かは UI で明示する。

### 7. 保存成功時のフィードバック

**採用**: sheet を閉じた直後にトースト（「変更を保存しました」相当）を表示し、Meta テーブルは取得済みデータを再取得 or ローカル更新で新値で再描画する。画面遷移は行わず、ユーザーが文脈を失わないようにする。

## Risks / Trade-offs

- **既存 UPDATE RLS ポリシーが `guest_count` / `note` 編集を許容しない可能性** → Apply フェーズの先頭タスクで実 DB に対する UPDATE 動作確認を実施し、不足があればポリシー拡張を同 PR 内で行う
- **create / edit モードを 1 コンポーネントに同居させる結果、props・状態が肥大化するリスク** → mode に依存する分岐は composable に切り出し、テンプレート側の条件分岐は kicker・CTA ラベル・確定 CTA ハンドラの 3 箇所程度に限定する。component test で create / edit 両系統のシナリオを並行カバーし、片方の改修で他方が壊れないことを担保
- **保存成功後の Meta テーブル再描画でちらつきが発生するリスク** → 楽観的更新（UPDATE 成功とみなしたタイミングで Meta テーブルのローカルキャッシュを差し替え）を採用し、再 fetch は補助的役割に留める
- **同時編集（複数タブ）時の競合** → 楽観的に「最後勝ち」とする。サークル運営の規模では実害が極めて小さく、悲観ロックを入れる労力に見合わない
- **編集期限切れ直前のレース（編集 sheet を 23:58 に開き 0:01 に保存）** → サーバー側の判定に依存させず、保存ボタン押下時にクライアント側で再度 `isCancellable` を評価して期限切れなら保存 CTA を不活性化 + 「期限切れ」案内に切替

## Migration Plan

1. **DB / RLS の事前確認**: dev 環境の `reservations` UPDATE RLS ポリシーで `guest_count` / `note` の編集が通るか確認。通らなければポリシー拡張用 SQL を Apply 第 1 タスクで追加
2. **コード変更は単一 PR で完結**: 共通化された Booking Sheet の mode 拡張・詳細画面 CTA 追加・edit 用 composable・component test まで 1 PR にまとめる
3. **ロールバック戦略**: 編集 CTA を非表示にする feature flag は導入しない（実装コストと釣り合わない）。問題発生時は PR を revert する。RLS ポリシーを拡張した場合は、ポリシーのみを元に戻す migration を別途用意する

## Open Questions

- 編集成功時のトースト表示位置（画面下部 / sheet 直下）はデザイントークンに沿った既存トースト基盤に従う想定だが、Apply 時に既存実装を確認して追従する
- 編集可能期限切れ後の「予約内容を変更する」CTA を非表示にするか、押下時にキャンセル不可ダイアログ相当の案内を出すかは UI 一貫性の観点で Apply 段階で実機確認しながら最終決定する（spec では非活性 + 案内のいずれも許容する書き方とする）

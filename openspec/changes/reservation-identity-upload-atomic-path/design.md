## Context

現行のアップロードは 3 段階で動く:

1. 仮パス (`__pending__`) で行を INSERT し、DB 採番の id を受け取る
2. その id からパスを組み立て、Storage に表裏を並列 upload する
3. 成功後に「仮パス → 実パス」の確定 UPDATE を行う

id を DB 採番に依存しているため、パスを確定できるのが upload の後になり、確定用の UPDATE ステップが不可避になっている。この最終 UPDATE が失敗すると、行は仮パスのまま・画像実体は保存済みという食い違いが残り、管理画面で画像を取得できなくなる。既存 spec もこの残留を「異常だが許容」として明文化してしまっている（`storage_path UPDATE 失敗時の挙動` シナリオ）。

商用で同一会員の 3 件がこの状態で滞留した。画像実体は健在だったため、DB のパスを実オブジェクトへ貼り直して復旧済み。本設計は再発防止のみを対象とする。

## Goals / Non-Goals

**Goals:**
- 「保存は成功したがパス確定だけ失敗し、仮パスの行が残る」失敗モードを構造的に消す
- DB 行が存在するなら、そのパスが指す画像実体も必ず存在する状態を保証する
- スキーマ・RLS・Storage 構成・パス命名規則は一切変えず、アップロード手順のみを差し替える
- 再発を検知する回帰テストを残す

**Non-Goals:**
- 管理画面・通知 Edge Function の変更（読み取り側は保存パスをそのまま使うだけ）
- 画像の中身（本人確認書類として妥当か）の検証。これは別課題
- 既存滞留データの移行（復旧済み）

## Decisions

### D1: 確定 UPDATE を廃止し、id をクライアント採番する

パスに必要な id を DB 採番ではなくクライアントで採番する（Web 標準の UUID 生成）。これにより upload の前に最終パスが確定でき、「後から実パスに UPDATE する」ステップが不要になる。

- 代替案: 従来の 3 段階のまま、確定 UPDATE をリトライ＋最終失敗時ロールバックで強化する。→ 手順の脆さは残り、リトライ全滅時は結局ロールバックで会員のやり直しになる。根本を断てないため不採用。

### D2: 手順を「Storage upload → 行 INSERT（実パス確定済み）」の順にする

行の作成を最後に置く。つまり:

1. クライアントで id を採番し、最終パスを組み立てる
2. Storage に表裏を並列 upload する
3. 両方成功したら、実パスを最初から入れた行を 1 回だけ INSERT する
4. upload 失敗時は保存済みオブジェクトを撤去してエラーを返す（行は作られていない）
5. INSERT 失敗時は保存済みオブジェクトを撤去してエラーを返す

**行が「コミット」に相当し、それが書かれる時点で画像実体は既に揃っている。** よって「行はあるが画像が無い / 仮パスのまま」という管理画面から見える壊れた状態が発生し得ない。

- 代替案（行 INSERT → upload → ロールバック）: upload 前に行を作るため、upload 中の一瞬だけ「行はあるが実体が未保存」の窓が開き、二重失敗（upload 失敗かつロールバック削除も失敗）で壊れた行が残り得る。管理画面から見える壊れ方を完全には消せないため不採用。行を最後に書く D2 のほうが degrade が綺麗（失敗時に残るのは、どの行からも参照されない孤立オブジェクトのみ＝管理画面に一切見えない無害なゴミ）。

### D3: 失敗時に残り得るのは「孤立オブジェクトのみ」に限定する

D2 の順序では、失敗時に残るのは最悪でも「どの行からも参照されない Storage オブジェクト」だけになる。これは管理画面・会員体験に一切影響しない不可視のゴミで、必要なら別途バッチ等で掃除できる（本変更では掃除自体はスコープ外、無害なため）。会員には従来どおりエラーを見せ、やり直してもらう。

### D4: エラー種別の整理

確定 UPDATE ステップが消えるため、「保存成功後の DB 更新失敗」という固有の失敗（従来の `db_failed` のうち確定 UPDATE 由来のもの）は無くなる。行作成そのものが失敗するケースは引き続き DB 失敗として扱う。upload 失敗の表裏別エラーは従来どおり維持する。

## Risks / Trade-offs

- [クライアント採番 id が既存行と衝突する] → 実質ゼロ（UUID）。万一 INSERT が一意制約で失敗しても、D2 の手順ではオブジェクトを撤去してエラーを返すだけで壊れた状態は残らない。
- [upload 成功後、行 INSERT 直前にタブが閉じる等で中断] → 孤立オブジェクトが残るが管理画面には見えない。会員は再アップロードでき、体験上の破綻は無い（従来はこの中断で仮パス行が残り、管理画面に壊れて見えていた）。
- [パス確定を upload 前に行うため、パス組み立てロジックの取り違えが即保存パスに直結する] → 命名規則は不変。表裏スロットと拡張子導出のユニットテストで固定し、回帰テストで実パスと行の一致を検証する。

## Migration Plan

- スキーマ変更なし・migration なし。アプリコード（アップロード統括 composable と DB/Storage client）の差し替えのみ。
- ロールバック戦略: 問題があれば当該コミットを revert すれば旧手順に戻る（DB 側の変更が無いため安全）。
- 既存滞留 3 件は復旧済みのため本変更に data fix は含めない。

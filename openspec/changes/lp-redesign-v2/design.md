## Context

LP（`apps/lp`）は High Q が訪問者と最初に出会う入口でありながら、Vuetify 既定テーマと旧構造のままになっている。一方で admin / reservation は `@high-q/design-tokens` と `@high-q/ui` を軸に HQ ブランド統一を達成している。

Issue #160 で求められているのは「初めての訪問者が躊躇せず一歩を踏み出せる温度感の演出」と「既存メンバーが次の予定に最短で辿り着ける情報設計」の両立であり、これは見た目の刷新と外部動線（LP → reservation）の再配線まで含めて初めて完成する。

本変更は Issue #160 の中核（UI 刷新 + reservation 接続）を担い、データ層の改修（AWS → Supabase 切替、過去データ移行）と reservation 側の入口受け取りは別 Issue（B / C / D）に切り出している。

## Goals / Non-Goals

**Goals:**
- LP の主要セクションを HQ デザイントークン基盤で全面刷新し、admin / reservation と同じ視覚体験に揃える
- ヒーロー直下に「次回開催」帯を常設し、初訪問者向けの長いストーリーとリピーター向けの即時情報を同一ページ上に共存させる
- 最終 CTA の主動線を reservation サイト（会員登録／ログイン）に切り替え、LINE オープンチャットは補助動線として残す
- 各イベントカードから reservation サイトへ「どのイベントの予約か」の文脈（イベント識別子）を渡す動線を整備する

**Non-Goals:**
- 画像素材の差し替え（プレースホルダーで構造を完成させ、差し替えは別 Issue）
- ModeToggle（初訪問／リピーターの全画面切替）の実装。デザインサンプル上の表現に留め、リピーター向け情報は「次回開催」帯で吸収する
- LP のイベント取得元を Supabase に切替えること（Issue B）
- AWS イベントデータの Supabase 移行（Issue D）
- reservation 側で「特定イベント指定の遷移」を受け取って認証分岐するルート実装（Issue C）
- LP のページ追加・ルーティング再編（既存のホーム／プライバシー／外部送信ポリシーの構成は維持）
- アナリティクス・SEO・OGP の再設計（既存設定の維持を確認する）

## Decisions

### LP セクション構成は「初訪問者を主軸、リピーターは帯で吸収」

デザインサンプルの ModeToggle は採用せず、初訪問者向けの主軸構成にヒーロー直下の「次回開催」帯を常設配置する。**理由**: 全画面切替の UX は離脱リスクが高く、リピーターのニーズはヒーロー直下の帯と「全予定を見る」ボタンで十分に満たせる。

### デザイントークン参照は CSS variables 経由を基本とする

セクション内のスタイリングは `var(--hq-color-*)` / `var(--hq-font-*)` を基本とし、ロジックで分岐する箇所のみ `@high-q/design-tokens` の TS export を使う。**理由**: Vue SFC の `<style scoped>` 内では CSS variables が読みやすく、デザインサンプルとの対応が一意で追える。Tailwind preset utility は LP では原則使わない（Vuetify と Tailwind の両立を避ける）。

### 意匠系プリミティブは `@high-q/ui` を採用、機能系は LP で取り込まない

`Button` / `Kicker` / `Badge` / `Photo` 相当は `@high-q/ui` から取り込む。フォーム系やダイアログなど機能系プリミティブは LP では原則不要のため取り込まない。**理由**: 3 アプリ間で「ボタンの見え方が違う」を許さないため。

### Vuetify は段階的に剥がし、本変更では「テーマ依存からの脱却」までを完遂する

Vuetify 自体の撤去は次フェーズに残し、本変更ではテーマ・色・書体への依存を全て HQ トークン経由に置き換える。`v-app` / `v-container` 等のレイアウト用コンポーネントは当面残し、`v-btn` 等の意匠依存コンポーネントは `@high-q/ui` の `Button` に置換する。**理由**: Vuetify 撤去まで含めると変更幅が肥大化し、レビューが困難になる。

### イベント取得は本変更内では現行経路を維持

新カード UI が表示するイベントデータは、本変更着手時点での既存取得経路（AWS API もしくは Issue B 完了済みなら Supabase 直結）から受け取る。本変更ではデータ取得ロジック自体には踏み込まない。**理由**: UI 刷新とデータ層切替を同じ PR に混ぜるとレビュー困難になるため、Issue B（Supabase 切替）に責務を切り出す。

### LP → reservation のディープリンクは「クエリパラメータでイベント識別子を渡す」だけを担う

LP のイベントカードは reservation サイトの所定 URL に `event` パラメータを付けて遷移する。reservation 側での認証状態判定とリダイレクト出し分けは Issue C の責務。LP 側に認証状態を持ち込まない。**理由**: 「LP は事実だけ渡す、reservation 側が状態判定と画面選択を担う」と責務を分離する方が破綻しない。

**留意**: Issue C 未完了の状態で本変更が先に merge されると、reservation 側は `event` パラメータを無視してトップ表示する挙動になる（破綻しない最低限の振る舞い）。利用者は会員登録・ログイン経由で予約に到達できる。理想的な着手順は C → A だが、A 先行でも機能継続性は保たれる。

### 環境変数で reservation URL を渡す

LP には reservation サイトの URL を環境変数（`VITE_RESERVATION_URL`）で注入する。値は dev / prd で分離する。**理由**: ハードコードしないことで Preview / dev / prd の各環境で正しい URL に向けられる。

## Risks / Trade-offs

- **[リスク] LP の Vuetify 残骸が新トークンと干渉する**: テーマ依存の Vuetify コンポーネントを段階的に `@high-q/ui` の意匠系に置換し、置換できないレイアウト系は HQ トークンを CSS variables で当てる → Vitest と Playwright の既存テストでリグレッションを検出
- **[リスク] Issue C 未完了で本変更だけ merge した場合の動線が中途半端**: reservation 側は `event` パラメータを無視するため利用者はトップに着地。会員登録経由で予約に到達できる → 着手順は C → A を推奨。A 先行でも障害には至らない
- **[リスク] Issue B 未完了で本変更だけ merge した場合のイベント識別子の整合性**: AWS イベントの ID を reservation（Supabase 参照）に渡しても解決できず、reservation 側がフォールバックしてトップへ → Issue B 完了を本変更の着手前提条件にする
- **[トレードオフ] ModeToggle 非採用によりリピーター UX がやや弱まる**: 「次回開催」帯と「全予定を見る」CTA で代替し、効果を観測後に必要なら別 Issue で追加
- **[トレードオフ] 画像素材を別 Issue にすることで MVP2 完成時点の見た目は未完**: プレースホルダーは HQ トークンで余白・タイポを完成させ、写真差し替えだけで仕上がる状態を確実にする

## Migration Plan

1. **前提確認**: Issue B（LP のイベント取得を Supabase に切替）が完了済みであることを確認。完了していない場合は着手を保留する
2. **意匠系プリミティブ取り込み**: LP の package.json に `@high-q/ui` を依存追加（本変更内で実施済み）
3. **新 widget 群の実装**: ヒーロー〜フッターまでの 14 セクションを順次実装
4. **HomePage 再編**: セクション順を新デザインに合わせて差し替え、旧 widget を撤去
5. **環境変数追加**: `VITE_RESERVATION_URL` を .env.example / Render 環境変数に追加（手動依頼）
6. **検証**: Render プレビューで全セクション・全デバイス幅・主要動線を確認
7. **本番反映後**: 必要に応じて Issue C / D の着手・進行を継続

ロールバック: LP 側は前バージョンに戻すだけで旧構成（Vuetify テーマ + 旧 CTA）に戻る。

## Open Questions

- 「次回開催」帯の「次回」判定ロジック（最も近い未来の開催イベント 1 件か）の確定 → 実装時に「最も近い未来 1 件」で進め、Render プレビュー確認時に翔太郎くんと再確認
- Vuetify レイアウトコンポーネント（`v-container` 等）の残置範囲。本変更で剥がせる箇所はどこまでか → 段階剥がしを基本に、新 widget 内では `v-container` を使わず HQ トークン直書きを採用
- reservation 側ディープリンク入口の URL パス形式（Issue C で確定する）。本変更では暫定で `?event=<id>` 形式を採用し、Issue C で URL 仕様が変わったら本変更側を追従修正

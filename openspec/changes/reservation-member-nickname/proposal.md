## Why

Issue #200 は Epic #170「メンバーが High Q に参加し、繰り返す」のうち、会員サイト内でのアイデンティティ表現を整えるための変更である。会員登録フォームでは本人確認・運営連絡用に氏名を必須収集しているが、会員サイト上で会員自身が呼ばれる名称はサークル文化に合った**任意のニックネーム**で運用できるほうが望ましい。

本 change のねらいは、後続 Issue #91 (予約導線完了) や #148 (プロフィール編集 / 履歴) で会員自身の名前を画面に出していくときに、各画面が機械的に「ニックネームがあればニックネーム、なければ氏名」を選んで表示できる**データ層 + 入力フォーム + spec 規約**を先に整えておくことにある。

### Issue #200 原案からの変更提案（PO 合意済）

Issue #200 の原案には「会員サイトの会員視点表示（イベント詳細・予約導線・履歴等）でニックネームを優先表示する**画面切替**」が含まれていたが、本 change では切替対象とする画面の**実体が現状ゼロ**であることが確認された。会員サイトの全ページを確認した結果、会員自身の名前を表示している箇所は 1 つも存在しない（イベント情報・予約番号・連絡先 LINE オープンチャットのみ）。そのため本 change のスコープは以下の 3 点に純化する:

1. データ層（会員エンティティへのニックネーム属性追加 + 文字種・文字数の妥当性チェック）
2. 会員登録フォームへのニックネーム入力欄追加（任意・空欄 OK）
3. 「ニックネームがあればニックネーム、なければ氏名」を会員視点表示の正準ルールとして spec に固定

実画面での表示反映は #148 (プロフィール編集 / 履歴) や将来の予約サマリ強化時に、本 change が固定する spec 規約を機械的に踏ませる形で漸進的に行う。

### MVP1 スコープオフ済み機能の事前確認結果

本 change の起票にあたり、関連 spec を全件確認し MVP1 スコープオフ項目を抽出した。これらに依存する UI / DB 機能は本 change に**一切含めない**:

| スコープオフ項目 | 出典 | 本 change での扱い |
|---|---|---|
| ニックネームの**変更機能** | Issue #200 / 後続 #148 | プロフィール編集画面 (#148) で対応するため、本 change では新規入力のみ実装し編集 UI は作らない |
| 一意性チェック（同名禁止） | Issue #200 | DB の UNIQUE 制約・アプリ層の重複バリデーションは入れない |
| admin 側の表示変更 | Issue #200 | admin は引き続き氏名表示のままとし、admin spec / 画面に手を入れない |
| 任意の Avatar / 自己紹介文 | （関連 spec に存在しない） | 本 change ではテキスト 1 項目（ニックネーム）に純化する |

## What Changes

| 観点 | 変更前 | 変更後 |
|------|--------|--------|
| 会員エンティティが持つ自己呼称 | 氏名 (display_name) のみ | 氏名 + 任意のニックネーム |
| 会員登録フォーム (`/signup/profile`) | 氏名 / 生年月日 / 電話 / 経験レベル / 規約同意 の 5 項目 | 上記 + 任意ニックネーム の 6 項目 |
| 会員視点表示の名称ルール | 規約として未確定 (実装も未存在) | 「ニックネームがあればニックネーム、なければ氏名」を仕様として固定 |
| 既存 dev 環境の会員データ | ニックネーム未保持 | migration により翔太郎くん 1 名に初期ニックネームを投入済 |
| ニックネームの文字種・文字数 | 制約なし (列が存在しない) | 1〜15 文字、日本語（ひらがな・カタカナ・漢字）+ 英字のみ。絵文字・数字・記号は不可 |
| ニックネームの変更 / 削除 | （存在しない） | 後続 #148 (プロフィール編集) で対応。本 change では新規入力のみ |

## Capabilities

### New Capabilities

なし（本 change は新規 capability を作らず、既存 2 つに対するルール追加で完結する）。

### Modified Capabilities

- `reservation-member-auth`: 会員登録フォーム（段階 2 / `/signup/profile`）の入力項目に**任意のニックネーム**を追加する。任意のため空欄送信を許容し、文字種・文字数の妥当性チェックを UI とアプリ層の両方で持たせる。会員エンティティのキャッシュ・取得経路にニックネーム属性を流す。会員視点表示の正準ルール「ニックネームがあればニックネーム、なければ氏名」を本 capability に固定し、後続 Issue で会員自身の名前を画面に出す際の参照点とする
- `data-schema`: 会員テーブルにニックネーム属性を追加し、CHECK 制約として文字数 1〜15 + 文字種（日本語 + 英字のみ）を強制する。NULL 許容（任意項目）。**Issue #200 の Non-Goals に従い一意性制約は付与しない**。既存 dev 環境の会員 1 名（翔太郎くん）に対し migration 内で初期ニックネームを投入する

## Impact

### 影響するコンポーネント・ファイル

- 会員サイト (`apps/reservation`)
  - 会員エンティティ層（型・取得・更新ロジック・Smart constructor）
  - 会員登録フォーム段階 2 のページ・composable・テスト
- DB スキーマ
  - members テーブルへの列追加（NULL 許可 + CHECK 制約）
  - 既存 dev 環境会員への初期値投入（migration 内で 1 行 UPDATE）
- spec
  - `reservation-member-auth` の段階 2 入力項目要件と表示ルール
  - `data-schema` の members テーブル列定義
- RLS: 既存 members ポリシーで成立。新規ポリシー追加は不要

### 影響しない範囲（Non-Goals）

- 管理画面 (`apps/admin`) の表示・運用（admin は氏名表示のまま）
- ニックネームの変更 / 削除 UI（#148 で対応）
- ニックネームの一意性チェック（同名 OK の運用）
- 会員サイトの既存ページ UI（現状名前を表示する場所が 0 件のため、本 change 内では UI 切替を行わない）
- 後続 Issue で会員自身の名前を画面に出す際の各画面実装（本 change はルール固定までで止める）

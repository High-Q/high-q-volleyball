## Why

Phase 1 で採用した Supabase 標準のマジックリンク方式は、メール送信の API 呼び出し時点で `auth.users` に未確認行を作る仕様のため、メールを開かない / プロフィール入力を途中で離脱した会員候補の行が DB に滞留する。Phase 1 期間中は別 Issue（#190）の cleanup ジョブで実害を抑える設計だが、サービスIN前に根本解決して、未完成の会員行が DB に**一切残らない**signup フローへ置き換える。

会員獲得の入口の体験品質と、`auth.users` / `members` テーブルの「正規化された会員のみが入っている」という不変条件を、サービスIN時点で同時に成立させたい。

## What Changes

- 会員登録の入口を「メール先送信 → リンク → プロフィール入力」の 2 段階から、「全項目入力 → 6 桁コード認証 → 一括登録」の 1 ページ + 検証ステップへ作り替える
- 全項目入力済みのフォーム送信から、6 桁コードの検証成功までは `auth.users` / `members` を**作成しない**。検証成功時に初めて両テーブルへ正式値で書き込む
- 「中途離脱した場合 DB に何も残らない」「最終的に登録される会員はプロフィール完成済み」という不変条件をシステムレベルで担保する
- 未確認の会員候補が滞留しないため、Issue #190 の 48h cleanup ジョブはサービスIN前に**不要**となる。本 change マージ後に #190 を Close 候補として再評価する
- 既存会員の**ログイン**フローはマジックリンクのまま据え置き（中途滞留問題はログイン側では発生しないため、変更範囲を最小化する）
- 認証コードメールの送信は Supabase 組み込みの認証メール基盤を踏襲し、追加の外部メール配信サービス契約は持ち込まない
- **BREAKING（会員サイトの登録動線のみ）**: 既存の `/signup/profile`（段階 2 のプロフィール入力ページ）は廃止し、入力は `/signup` 1 ページに集約する。会員視点では「メールを送信 → メールを開く → 戻ってきて再入力」という往復がなくなる

## Capabilities

### New Capabilities
（なし — 既存 capability への差分として実装する）

### Modified Capabilities

- `reservation-member-auth`: signup フローを「Edge Function + 6 桁コード方式」に差し替える。`/signup` 1 ページ全項目入力 + `/signup/verify` 6 桁コード検証の 2 ルートで構成し、既存の `/signup/profile` 段階を撤廃する。auth guard の「プロフィール未完成→ /signup/profile 強制誘導」分岐は到達不能になるため削除する。プロフィール完成判定（`signup_completed = true`）のフィールド自体は既存会員との互換性のため維持する
- `data-schema`: 認証コード検証待ちの payload を一時保管する `signup_pending` テーブルを追加する（短期 KV 用途、TTL 30 分で自動削除）
- `rls-policies`: `signup_pending` テーブルへのクライアント直接アクセスを完全禁止し、Supabase の特権ロールからのみ操作可とする

## Impact

- **会員登録 UX**: 入力ページがコンパクトになり、メールリンクを開きに行く往復がなくなる。一方で 6 桁コードを画面に手で入力する 1 ステップが追加される
- **DB**: `auth.users` / `members` に未完成行が原理的に発生しなくなる。`signup_pending` のみが新設されるが PII を 30 分以上保持しない
- **運用**: cleanup ジョブ（#190）の運用が不要になる。手動 SQL での月次掃除も廃止できる
- **既存 Phase 1 動線**: ログイン / ログアウト / 本人確認書類アップロード（Step 3）/ 既存会員のセッション復元は据え置き。影響を受けるのは**新規 signup 動線のみ**
- **メール基盤**: Supabase 組み込み SMTP の送信上限・テンプレート設定の運用範囲内で完結
- **後続 Issue**:
  - Issue #190（48h cleanup ジョブ）: 本 change マージ後に Close 判定（実装は不要となる見込み）
  - Phase 1 期間に発生していた未確認 / 中途離脱の `auth.users` 行は本 change リリース時に**ワンショット SQL** で清掃する（design.md で削除条件を確定）
- **セキュリティ**: 個人情報（氏名 / 電話 / 生年月日）は `signup_pending` に最大 30 分のみ保持し、Supabase の特権ロール経由でしかアクセスできない。`localStorage` に payload を持たせる Phase 1 の暫定実装は撤去される

## Context

予約完了メール（および予約内容変更メール）は `supabase/functions/send-reservation-notification` が Gmail SMTP 経由で送信し、文面は `_shared` の純粋関数レンダラが生成する。現状の本文は事務的事実（予約番号・イベント名・日時・会場・住所・集合地点・金額・連絡事項）のみで、当日の実用案内（会場周辺の注意事項・懇親会・集合補足）が含まれない。

既存資産として、会場マスタ `venues` には `access_note`（アクセスメモ・改行可の自由文）列があり admin の会場編集画面で編集可能だが、メール文面では未使用。一方、イベント単位の自由文を保持する列は存在しない（`events.description` は AWS 移行スクリプトが `[Legacy ID: ...]` マーカーを埋め込む列として使用しているため会員向け文面には転用不可）。

## Goals / Non-Goals

**Goals:**
- 会場固有の注意事項（飲み物が近くで買えない等）を会場マスタ 1 箇所の設定で全イベントの完了/変更メールに自動掲載する。
- イベント固有の任意の案内（懇親会・集合補足）を admin のイベントフォームから自由文 1 枠で設定し、メール末尾に掲載する。
- いずれも空のときはセクションごと非表示にし、既存メールの体裁を崩さない。

**Non-Goals:**
- 会場の `access_note` 編集 UI の新設（既存の会場編集画面で完結済み）。
- キャンセルメールへの当日案内掲載（キャンセル時は不要）。
- リッチテキスト / HTML メール化（現行どおりプレーンテキスト）。
- イベント固有案内の構造化（懇親会・集合を別フィールドに分けない。自由文 1 枠で運用）。

## Decisions

### Decision 1: 会場固有注意事項は `venues.access_note` を再利用（新カラムを作らない）

会場が同じなら毎回同じ内容になる注意事項は会場マスタに属する情報であり、既存の `access_note` がまさにこの用途（改行可の自由文・admin 編集可能）。新カラムを足すと二重管理になるため再利用する。

- **代替案**: events に会場注意事項を都度入力 → 同じ会場で毎回打ち直す手間と転記ミスのリスク。却下。
- **影響**: Edge Function のメール入力取得クエリに `venues.access_note` を追加し、レンダラで「注意事項」セクションとして掲載。

### Decision 2: イベント固有案内は `events.email_note` 新列（自由文 1 枠）

懇親会の有無・案内文・当日集合の補足はイベントごとに変わるため events に属する。構造化（懇親会／集合を分離）より自由文 1 枠が最小・最柔軟で、運営者の入力負荷も最小。

- **列**: `events.email_note text NULL`。空（NULL / 空文字）はメール非掲載。
- **`description` 転用却下**: AWS Legacy ID マーカー用途と衝突するため別列とする。
- **掲載位置**: メール末尾（事務情報の後）に「ご案内」見出しで掲載。

### Decision 3: 掲載対象は完了メールと変更メールのみ

予約完了メール・予約内容変更メールはどちらも「これから参加する」文脈なので当日案内が有用。キャンセルメールは参加しない文脈なので掲載しない。

### Decision 4: レンダラの純粋関数性を維持

`_shared` の文面レンダラは「同一入力 → 同一出力」の純粋関数。入力 DTO に `venueAccessNote` と `eventEmailNote`（いずれも optional）を追加し、空判定で出し分ける。SMTP / DB モックなしでユニットテスト可能な性質を維持する。

## Risks / Trade-offs

- [`access_note` が会員に見せる前提で書かれていない可能性] → 既存の会場編集画面のアクセスメモは元々会員開示を想定した運用メモ。本 change で「メールに会員へ掲載される」旨を会場編集画面の hint に追記し、運用者へ周知する。
- [自由文 email_note にプレーンテキストとして不適切な長文/制御文字が入る] → フォームで最大文字数バリデーション（design 上は数百文字程度）と前後トリムを行う。HTML エスケープはプレーンテキスト送信のため不要だが、改行はそのまま尊重する。
- [既存メールスナップショットテストが文面追加で壊れる] → テスト側で空欄ケース（従来どおり）と設定ありケースの両方を網羅し、意図した差分であることを担保する。

## Migration Plan

1. `events` に `email_note text NULL` を追加する ALTER migration を作成（`-- ROLLBACK:` コメント付き）。既存行は NULL のまま影響なし。RLS は既存 events ポリシーを継承し変更不要。
2. `packages/shared` の `Event` 型に `email_note: string | null` を追加。
3. admin イベントフォームに入力欄・バリデーション・mutation 反映を追加。
4. Edge Function のメール入力取得に `events.email_note` / `venues.access_note` を追加し、レンダラ・テストを拡張。
5. デプロイは通常フロー（migration は prd-db-push CI の承認ゲート経由、Edge Function は手動 sync が必要な点に留意）。
- **ロールバック**: 列追加のみで破壊的変更なし。メール文面側は空欄なら従来表示に戻るため、列を残したままでも安全。

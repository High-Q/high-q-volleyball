## MODIFIED Requirements

### Requirement: 予約完了通知メールの送信

会員サイト (`apps/reservation`) は予約成立イベント時に会員へ予約完了メールを SHALL 送信する。送信対象イベントは以下の両方を MUST 含む:

- `reservations` 行が新規 INSERT され `status='reserved'` で確定したとき
- 既存の `status='cancelled'` 行が同一会員 / 同一イベントの再予約により `status='reserved'` に再活性化されたとき

送信先は **当該予約の会員自身のメールアドレス** とする MUST。`auth.users.email` または `members.email` から決定し、第三者の任意メールに送信できる経路を持たせてはならない MUST NOT。

メール本文に **MUST 含める** 要素:

- 予約番号（reservations.id を表示用フォーマット `#HQ-XXXX-XXXX` に変換した文字列。生 UUID を含めてはならない MUST NOT）
- イベント名
- 開催日時（JST、和暦・西暦どちらかに統一）
- 会場名
- 会場住所（venues.address）— `data-schema` spec で「有明会場の実住所秘匿」運用が定義されており、未認証ページから取得できる住所は駅住所等にマスクされる。本メール本文では DB に保管されている `venues.address` をそのまま含める MUST。秘匿会場の場合これがメールで会員に初めて開示される情報となる
- 参加人数および参加費（同伴者数を反映した合計金額、当日現金払いの旨を併記）— 予約番号〜会場住所と同じ「予約内容」ブロックにまとめて掲載する MUST（会員の連絡事項より前）
- 連絡事項（reservations.note）— 予約内容ブロックの直後に配置する MUST。主催側の案内（注意事項・ご案内）より前に出し、会員記載と主催案内が混ざらないようにする。空のときは当該セクションを出さない MUST
- 注意事項（venues.access_note）— 登録されていれば連絡事項の後に「注意事項」セクションとして本文に含める MUST。集合場所・アクセス・会場周辺の注意事項（例: 飲み物が近くで買えないため駅で購入する案内）等を会員へ伝える用途。空のときは当該セクションを出さない MUST。改行はそのまま尊重する MUST
- ご案内（events.email_note）— 設定されていれば「注意事項」（会場）の直後に「ご案内」セクションとして含める MUST。主催側の案内（注意事項・ご案内）は隣接させて掲載する MUST。懇親会の案内や当日の集合補足等のイベント固有メッセージを会員へ伝える用途。空（NULL / 空文字）のときは当該セクションを出さない MUST。改行はそのまま尊重する MUST

集合地点（venues.meeting_point）の専用行および会場マップ URL（venues.map_url）の専用行はメール本文に **含めない**。集合場所・地図・アクセスは会場の「注意事項」（venues.access_note・会場メールテンプレート）に自由文として記載する運用とする。
- 当日連絡用 LINE オープンチャットの URL（`shared/lib/contact-channels` 定数経由、ハードコード禁止 MUST NOT）。予約者は当日の集合・時間変更・緊急連絡をすべて LINE オープンチャットで受け取るため、**必ず参加する** よう必須トーンで案内する MUST（「任意のお願い」ではなく参加を促す文言とする）
- マイページ / 予約詳細画面の URL（自分の予約を確認・キャンセルできる導線）
- 迷惑メールフォルダ確認の案内（届かない場合の救済導線）

メール本文に **MUST NOT 含める** 要素:

- 運営オーナー個人連絡先（電話・SNS ID 等。連絡経路は LINE オープンチャットに一元化する MUST）
- 他会員の個人情報
- 生の UUID / 内部 ID / Service Role キー等のシークレット

メール件名は予約番号またはイベント名を含む日本語の固定書式とし、Gmail SMTP の Q-encode 文字化けを避けるため UTF-8 が安全に通る形式で生成する MUST（既存 signup メール送信と同じ送信パスを使う）。

送信は Supabase Edge Function を経由し、`supabase/functions/_shared/mailer.ts` の `sendMail` を利用する MUST。直接 SMTP 接続をクライアント側 / アプリ側で開いてはならない MUST NOT。

#### Scenario: 新規予約成立時の送信
- **WHEN** 会員が予約 Bottom Sheet で「予約を確定する」を押下し、reservations に新規 `status='reserved'` 行が成立
- **THEN** 当該会員のメールアドレス宛に予約完了メールが送信され、本文には予約番号 / イベント名 / 開催日時 / 会場名 / 会場住所 (venues.address) / 合計金額 / LINE オープンチャット URL が含まれる

#### Scenario: 集合地点・会場マップの専用行を出さない
- **WHEN** 予約完了メールが送信される
- **THEN** 本文に「集合地点:」「会場マップ:」の専用行は描画されない（集合場所・地図は会場の「注意事項」に自由文として含める運用）

#### Scenario: 会場アクセスメモの掲載
- **WHEN** 予約したイベントの venues.access_note が空でない状態で予約完了メールが送信される
- **THEN** 連絡事項の後に「注意事項」セクションとして access_note の内容が改行を保持して描画される

#### Scenario: 会場アクセスメモが空のときの非表示
- **WHEN** venues.access_note が NULL または空文字
- **THEN** メール本文に「注意事項」セクション自体が描画されない

#### Scenario: イベント追記メッセージの掲載
- **WHEN** 予約したイベントの events.email_note が空でない状態で予約完了メールが送信される
- **THEN** 「注意事項」（会場）の直後に「ご案内」セクションとして email_note の内容が改行を保持して描画され、会員の連絡事項（会場情報の直後）→ 注意事項 → ご案内 の順に並ぶ

#### Scenario: イベント追記メッセージが空のときの非表示
- **WHEN** events.email_note が NULL または空文字
- **THEN** メール本文に「ご案内」セクション自体が描画されない

#### Scenario: LINE オープンチャット参加を必須として案内
- **WHEN** 予約完了メールが送信される
- **THEN** 本文に「必ずご参加ください」相当の必須トーンの文言と LINE オープンチャット URL が含まれ、当日連絡が LINE 一本であることが伝わる

#### Scenario: 予約内容が 1 ブロックにまとまる
- **WHEN** 予約完了メールが送信される
- **THEN** 予約番号 / イベント名 / 開催日時 / 会場名 / 会場住所 / 参加人数 / 参加費 が連続した予約内容ブロックとして並び、会員の連絡事項より前に置かれる

#### Scenario: 秘匿会場の実住所をメールで初めて開示
- **WHEN** 公開ページで住所が秘匿されている会場（例: 有明会場）に対する予約完了メールが送信される
- **THEN** 本文の会場住所欄には venues.address に保管されている実住所が描画される

#### Scenario: 再活性化（キャンセル後の再予約）時の送信
- **WHEN** 会員が過去にキャンセル済み (`status='cancelled'`) の予約を持つ状態で同一イベントを再予約し、当該行が `status='reserved'` に再活性化
- **THEN** 新規予約成立時と同様の予約完了メールが当該会員のメールアドレス宛に再送信される

#### Scenario: 予約成立はメール送信失敗の影響を受けない
- **WHEN** 予約は成立したが Edge Function 経由のメール送信が SMTP エラーで失敗
- **THEN** 予約完了画面への遷移と reservations 行の整合性は保たれ、UI にはメール送信失敗エラーが描画されない

#### Scenario: 生 UUID の非露出
- **WHEN** 送信されたメール本文を確認
- **THEN** 予約番号は `#HQ-XXXX-XXXX` 形式で記載され、UUID 形式 (8-4-4-4-12 hex) の文字列は本文 / 件名のどこにも存在しない

#### Scenario: 連絡事項が空のときの非表示
- **WHEN** reservations.note が NULL または空文字で予約が成立
- **THEN** メール本文には連絡事項のセクション自体が描画されない

#### Scenario: 送信先は会員自身のメールアドレスに限定
- **WHEN** リクエスト改ざんで他会員の reservation_id を指定してメール送信 Edge Function を直接呼び出す
- **THEN** Edge Function は呼び出し元の認証情報から会員 ID を取得し、reservations.member_id が一致しないリクエストは拒否する

### Requirement: 予約内容変更通知メールの送信

会員サイト (`apps/reservation`) は予約内容変更 (edit) の成立イベント時に会員へ通知メールを SHALL 送信する。送信対象イベントは `reservations` 行の `guest_count` または `note` を `status='reserved'` の状態で UPDATE して成功したときに限定する MUST。

送信先・送信経路・件名のエンコード方針・送信抑制モードおよび許可リストの挙動は予約完了通知メール (本 spec 「予約完了通知メールの送信」Requirement) と同一とする MUST。

メール本文に **MUST 含める** 要素:

- 予約番号（表示用フォーマット `#HQ-XXXX-XXXX`、生 UUID を含めてはならない MUST NOT）
- イベント名 / 開催日時（JST） / 会場名
- 会場住所 (venues.address) — 秘匿会場の場合の取り扱いは予約完了通知メールと同一
- 変更後の連絡事項 (reservations.note) — 会場情報の直後に配置する MUST。主催側の案内より前に出す。空のときは当該セクションを出さない MUST
- 注意事項 (venues.access_note) — 登録されていれば連絡事項の後に「注意事項」セクションとして本文に含める MUST。空のときは当該セクションを出さない MUST。取り扱いは予約完了通知メールと同一
- ご案内 (events.email_note) — 設定されていれば「注意事項」（会場）の直後に「ご案内」セクションとして含める MUST。主催側の案内は隣接掲載する。空のときは当該セクションを出さない MUST。取り扱いは予約完了通知メールと同一
- 変更後の同伴者数および変更後の合計金額（参加費 × 人数、当日現金払いの旨を併記）
- 当日連絡用 LINE オープンチャットの URL（`shared/lib/contact-channels` 定数経由、ハードコード禁止 MUST NOT）
- マイページ / 予約詳細画面の URL
- 迷惑メールフォルダ確認の案内

集合地点 (venues.meeting_point) / 会場マップ URL (venues.map_url) の専用行は予約完了通知メールと同様に **含めない**。集合場所・地図・アクセスは会場の「注意事項」(venues.access_note) に記載する。

メール本文・件名は **予約完了通知メールと取り違えない文言** とする MUST。冒頭は「予約完了」ではなく「予約内容を更新しました」が分かる表現を採用し、件名にも更新であることを示す語を含める MUST。

メール本文に **MUST NOT 含める** 要素は予約完了通知メールと同一とする（運営オーナー個人連絡先、他会員の個人情報、生 UUID / 内部 ID / シークレット）。

送信は予約完了通知メールと同じ Edge Function を経由し、eventType による分岐で文面を切り替える MUST。直接 SMTP 接続をクライアント側 / アプリ側で開いてはならない MUST NOT。

#### Scenario: 編集成立時の送信
- **WHEN** 会員が予約詳細画面の edit 操作で同伴者数または連絡事項を編集し、reservations の UPDATE が `status='reserved'` の行に対して成功
- **THEN** 当該会員のメールアドレス宛に予約内容変更通知メールが送信され、本文には予約番号 / イベント名 / 開催日時 / 会場名 / 会場住所 / 変更後の同伴者数 / 変更後の合計金額 / LINE オープンチャット URL / マイページ URL が含まれる

#### Scenario: 連絡事項が空に変更されたときの非表示
- **WHEN** 編集前に値があった連絡事項を空文字に更新して保存
- **THEN** 通知メール本文には連絡事項のセクション自体が描画されない

#### Scenario: 会場アクセスメモ・イベント追記メッセージの掲載
- **WHEN** venues.access_note または events.email_note が空でない状態で変更通知メールが送信される
- **THEN** それぞれ「注意事項」「ご案内」セクションとして改行を保持して描画され、空の項目はセクションごと描画されない

#### Scenario: 秘匿会場の実住所をメールで開示
- **WHEN** 公開ページで住所が秘匿されている会場の予約を編集し、変更通知メールが送信される
- **THEN** 本文の会場住所欄には venues.address に保管されている実住所が描画される

#### Scenario: 編集が成立しないときは送信されない
- **WHEN** RLS 違反 / 編集期限切れ (開催当日 0:00 JST 以降) / 既にキャンセル済み等で UPDATE の影響行数が 0 行
- **THEN** 予約内容変更通知メールは送信されない

#### Scenario: 編集成立はメール送信失敗の影響を受けない
- **WHEN** 編集の UPDATE は成立したが Edge Function 経由のメール送信が SMTP エラーで失敗
- **THEN** 編集成功トーストと画面遷移は通常どおり完了し、UI にはメール送信失敗エラーが描画されない

#### Scenario: 送信先は会員自身のメールアドレスに限定
- **WHEN** リクエスト改ざんで他会員の予約 ID を指定して変更通知 Edge Function を直接呼び出す
- **THEN** Edge Function は呼び出し元の認証情報から会員 ID を取得し、reservations.member_id が一致しないリクエストは拒否する

#### Scenario: 件名 / 本文が完了メールと混同されない
- **WHEN** 送信された予約内容変更通知メールの件名と本文冒頭を確認
- **THEN** 件名と本文冒頭は「予約内容を更新した」ことが分かる文言で、「ご予約完了」「予約完了」表現は使用されない

#### Scenario: 送信抑制モードのとき実送信されない
- **WHEN** 送信抑制モードが有効な環境で編集が成立
- **THEN** Edge Function は送信処理を実行せず、ログに「抑制モードのためスキップ」を残す

#### Scenario: 生 UUID の非露出
- **WHEN** 送信された変更通知メール本文を確認
- **THEN** 予約番号は `#HQ-XXXX-XXXX` 形式で記載され、UUID 形式 (8-4-4-4-12 hex) の文字列は本文 / 件名のどこにも存在しない
